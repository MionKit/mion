title: Caveats
description: Common pitfalls when using RunTypes and how to avoid them with ESLint rules.
---

RunTypes resolves your types at build time. There are still a few pitfalls that can stop it generating what you expect, and mion provides [ESLint rules](/devtools/eslint-rules) to catch them at development time.

## Type-Only Imports (no longer a problem)

`import type { X }` is **safe**. RunTypes resolves your types at build time by reading the
TypeScript program, and injects the compiled functions at the `route()` / `middleFn()` call site --
so it does not matter that the import itself is erased from the emitted JavaScript.

```ts
// ✅ Both of these work identically
import type { User } from './types';
import { User } from './types';

route((ctx, id: number): User => getUser(id));
```

::note
This used to be a real pitfall. Before the `@ts-runtypes` migration, mion emitted reflection metadata
from the import statement itself, so `import type` erased it and silently broke validation. The
`@mionjs/no-type-imports` ESLint rule existed to catch exactly that, and has been removed.
::

---

## Missing Type Annotations

RunTypes needs explicit type annotations on route/middleFn parameters and return types. Without them, TypeScript cannot emit the type metadata needed for runtime validation.

```ts
// ❌ WRONG: Missing type annotations
route((ctx, user) => user.name);

// ✅ CORRECT: Explicit type annotations
route((ctx, user: User): string => user.name);
```

::note
Use the [`@mionjs/strong-typed-routes`](/devtools/eslint-rules#mionkitstrong-typed-routes) ESLint rule to catch this issue.
::

---

## Unreachable Union Types

When deserializing union types, RunTypes tries to match against each type in order. If a less specific type appears before a more specific type, the more specific type will never be matched.

```ts
// ❌ WRONG: {id: string} matches first, {id: string; name: string} is unreachable
type User = { id: string } | { id: string; name: string };

// ✅ CORRECT: Most specific type first
type User = { id: string; name: string } | { id: string };
```

::note
Use the [`@mionjs/no-unreachable-union-types`](/devtools/eslint-rules#mionkitno-unreachable-union-types) ESLint rule to catch this issue.   
This rule will only check Types that are used in routes/middleFns.
::

## Recommended ESLint Configuration

To catch all these issues automatically, add the mion ESLint plugin to your project:

```bash
npm install @mionjs/eslint-plugin -D
```

Then use the recommended configuration:

```json [.eslintrc.json]
{
  "extends": ["plugin:@mionjs/recommended"]
}
```

This enables all the rules mentioned above with `error` severity.
