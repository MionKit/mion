When your Drizzle tables are the source of truth, `@mionjs/drizzle` derives validation schemas straight from them. This follows the same convention as `drizzle-zod` and `drizzle-typebox`, but validation runs on mion's compiled validators, so there is no schema library in between and nothing new to learn.

::note
The schema factories need the mion build plugin (`@mionjs/devtools`) active in your build, the same requirement as the rest of mion. The plugin compiles the validators for each table's row type at build time.
::

## The Four Factories

| Factory | Validates | Rules |
|---------|-----------|-------|
| `createSelectSchema(table)` | A full row, as returned by a select | Every column present; nullable columns accept null |
| `createInsertSchema(table)` | An insert payload | Required only when not null and without a default; generated columns cannot be sent |
| `createUpdateSchema(table)` | An update payload | Any subset of the insert payload, including nothing |
| `createEnumSchema(pgEnum)` | One enum value | Must be a member of the enum |

Each schema gives you:

- `validate(value)`: true or false, using the compiled validator plus column checks.
- `getErrors(value)`: a list of structured errors, each with the path of the failing column.
- `hasUnknownKeys(value)` and `unknownKeyErrors(value)`: catch keys that do not belong in the payload.
- `mock(options?)`: a realistic fake row for tests. Generated strings respect column lengths.
- `runType` and `typeId`: the reflection data for the row type, for advanced use.
- `['~standard']`: a [Standard Schema](https://github.com/standard-schema/standard-schema) surface, so the schema plugs into any library that accepts Standard Schema validators.

Column metadata that only the table knows is checked on top of the compiled validator. Today that means text length: a value longer than its `varchar(n)` column fails validation with a max length error.

## Insert and Update Payloads

The optionality rules come straight from the table definition, matching what Drizzle itself accepts:

<code-import path="packages/examples/src/drizzle/drizzle-insert-update-schema.ts" lang="ts" />

| Column definition | In the insert payload |
|-------------------|----------------------|
| `.notNull()` without a default | Required |
| Nullable | Optional, accepts null |
| `.default(...)`, `.defaultNow()`, `.$defaultFn(...)` | Optional |
| `.$onUpdate(...)` | Optional |
| `.generatedAlwaysAs(...)` | Cannot be sent (unknown key) |
| `.generatedAlwaysAsIdentity()` | Cannot be sent (unknown key) |

Update payloads accept any subset of the insert payload, so a partial update with a single column, or even an empty object, is valid.

## Refinements

Pass a second argument to add your own per column checks. A refinement runs only after the compiled validator accepted the value, and is skipped when the value is null or missing. Return false for a generic error, or a string to use it as the error message:

```ts
const userSelect = createSelectSchema(users, {
  name: (name) => name.trim().length > 0 || 'name cannot be blank',
});
```

::note
Refinements here are plain functions on the schema, not composable schema objects like in drizzle-zod. Mock rows do not know about your refinements, so a mocked row can fail a refinement check.
::
