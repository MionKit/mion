One package per database gives you the [Drizzle ORM](https://orm.drizzle.team) table authoring surface for that dialect: the same column builders, the same names and parameters, the same modifier chains, the same indexes and constraints. You write your tables exactly as you would with drizzle.

| Database | Package |
|----------|---------|
| PostgreSQL | `@mionjs/drizzle-orm-pg-core` |
| MySQL | `@mionjs/drizzle-orm-mysql-core` |
| SQLite | `@mionjs/drizzle-orm-sqlite-core` |

Each package version follows drizzle-orm, not mion: version 0.45.x works with drizzle-orm 0.45.x, and the package declares that range as a peer dependency. Pick the package line that matches the drizzle-orm version in your project. A new version is published only when the package itself changes, so the same version can stay current across several mion releases.

Install the dialect package with its shared core. Drizzle itself is an optional peer: your schema, models and validators work without it, and you add it when you talk to a database:

```bash
npm install @mionjs/drizzle-orm-pg-core @mionjs/drizzle-orm @ts-runtypes/core
npm install drizzle-orm   # only needed to run queries or migrations
```

The difference is under the hood. Drizzle's own table types are heavy, and they forget most column parameters (a varchar length, whether an int is unsigned). Our builders record your calls instead of running drizzle, and their types carry exactly what your API needs: the matching format type from `@ts-runtypes/core/formats` with the parameters you wrote, plus the not-null and default flags. Inferred models are small flat types, editors stay fast, and the compiled validators enforce every captured parameter with no extra runtime checks.

Because routes and tables share the same model types, a route typed with the inferred model uses the exact same compiled validator function as any other consumer of that model.

## The real drizzle table, on demand

Your table records everything drizzle needs, and `toDrizzle` builds the real drizzle table from that record the first time you ask for it (every later call returns the same object). That is the one place drizzle runs, so its heavy types are paid only in the files that run queries, never in your routes or your client:

```ts
import {drizzle} from 'drizzle-orm/node-postgres';
import {toDrizzle} from '@mionjs/drizzle-orm-pg-core/drizzle';
import {users} from './schema.ts';

const db = drizzle(process.env.DATABASE_URL);
const rows = await db.select().from(toDrizzle(users));   // fully typed, formats included
```

The same call feeds migrations: a drizzle-kit schema file exports `toDrizzle(users)` (and the materialized enums, for `pgEnum`). Everything on the query side of drizzle (operators, relations, getTableConfig) works on the `toDrizzle` result as usual.

## Refine tables for your API

Your API often needs stricter rules than the database column: a name column can hold 100 characters, but the signup form wants at least 10. `refineTableType` adds those rules at the type level. It returns the same table object (nothing about the SQL changes) with the extra format parameters merged into the captured ones. Derive your model types from the refined table and the whole toolbox compiles from them: validators that enforce both the database rules and the refined ones, mock data that respects every bound, and JSON serializers that keep Date columns real Dates across the wire. This works with or without mion:

<code-import path="packages/examples/src/drizzle/drizzle-refine-example.ts" lang="ts" />

A refinement that does not fit the column is a compile error, never a silent override: you cannot put a number rule on a string column, invent an unknown parameter, or change whether a column accepts null (that stays with notNull in the table itself). Columns without a format (booleans, JSON, enums) are not refinable.

`InferSelect`, `InferInsert` and `InferUpdate` derive the row, insert and update payload types from a table (refined or not): inserts drop generated columns and make defaulted ones optional, updates accept any subset of the insert payload.

## Use the models in mion routes

Type your routes with the derived models and the whole default behavior is already generated from the types: payloads are validated before the handler runs (the refined bounds included), Dates are serialized and revived on both ends of the wire, the update route accepts any subset while still validating present keys, and the client gets full types from the exported api type. ## Semantic types by hand

Columns whose values have no matching format (geometry, vectors, MAC addresses, binary data, plain booleans and JSON) keep their plain data type. For JSON columns, `.$type<T>()` stays the escape hatch to declare a semantic type by hand, exactly as in drizzle:

```ts
import {pgTable, jsonb, uuid} from '@mionjs/drizzle-orm-pg-core';

const events = pgTable('events', {
  id: uuid('id').primaryKey(),
  payload: jsonb('payload').$type<{kind: string; at: number}>().notNull(),
});
```
