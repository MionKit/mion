The package `@mionjs/drizzle` connects Drizzle ORM and mion validation in **both directions**:

1. **Schemas from tables** (the usual Drizzle workflow, like `drizzle-zod`). Your tables are the source of truth, and `createSelectSchema`, `createInsertSchema`, `createUpdateSchema` and `createEnumSchema` derive validation schemas from them. See [Validation Schemas](/drizzle-orm/validation-schemas).
2. **Tables from types**. Your TypeScript types are the source of truth, and `toDrizzlePGTable`, `toDrizzleMySqlTable` and `toDrizzleSqliteTable` generate the table configuration from them, with optional overrides. This page covers that direction.

Validation always runs with the same compiled validators the rest of mion uses. There is no schema library in between and no extra codegen step, the mion build plugin does the work.

::note
Column types are derived from Typescript types and [`@ts-runtypes/core/formats`](https://runtypes.pages.dev) - when you use format types like `UUIDv7`, `Email`, `Integer`, etc., the package automatically selects the most appropriate database column type for each database.
::

::tip
**Quick Tip:** 
This package is designed to work with [flat types that reflect the columnar structure of a database table]{.text-highlighted}, not deeply nested JavaScript objects with relationships. 
Use foreign key IDs instead of embedded entity references. Nested objects are stored as JSON columns.
::

Types should only contain information related to type and format, this will be used for validation and serialization.
Any columns asn SQL logic like primary, foreign keys, indexes, etc. should be defined in the tableConfig override.
::

#### Length Buffer

The `lengthBuffer` option multiplies the `maxLength` defined in custom string formats (`String`) to provide extra capacity for the database column. This is useful when you want to allow for some flexibility in the data length prevent resizing in the future, but still want to validate the correct length at runtime.

::note
The `lengthBuffer` only applies to custom `String` types with a `maxLength` constraint. Well-known formats like `Email`, `StrURL`, and `Domain` use their standard maximum lengths without any buffer.
::

#### Table Config Validation

The function validates that your tableConfig matches the TypeScript type

```ts
interface User {
    id: string;
    name: string;
}

// ❌ Error: Column "email" exists in tableConfig but not in type "User"
const users = toDrizzlePGTable<User>('users', {
    id: uuid('id').primaryKey(),
    email: text('email'), // This property doesn't exist in User!
});
```

## Important Notes

#### Import Format Types Correctly

::info
When using format types from `@ts-runtypes/core/formats`, you must use **regular imports** (not `import type`) for the runtime type metadata to be preserved.
::

```ts
// ✅ Correct - regular import preserves metadata
import {UUIDv7, Email} from '@ts-runtypes/core/formats';

// ❌ Wrong - type import strips metadata
import type {UUIDv7, Email} from '@ts-runtypes/core/formats';
```

#### Nested Objects vs Foreign Keys

Nested objects are stored as JSON. Use foreign key IDs for entity references:

```ts
// ✅ Good: Profile is a value object - stored as JSON
interface User {
    id: string;
    profile: {bio: string; avatar: string};
}

// ❌ Bad: Don't embed entire entities
interface Book {
    id: string;
    owner: User; // This stores the entire User as JSON!
}

// ✅ Good: Use foreign key ID instead
interface Book {
    id: string;
    ownerId: string; // Reference by ID
}
```

#### Column Names and Casing

Generated columns and schemas are keyed by your TypeScript property names. If you want snake_case names in the database, use Drizzle's own `casing: 'snake_case'` option on the `drizzle()` connection config. That option renames columns at the SQL layer only, so your code and the schemas keep using the TypeScript names.
