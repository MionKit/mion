The package `@mionjs/drizzle` auto generates Drizzle ORM table schemas directly from TypeScript types.
Unlike `drizzle-zod` or other drizzle plugins that generate schemas FROM drizzle tables, this package works in the **opposite direction**: your TypeScript types are the source of truth, and the drizzle table configuration is generated from them, with optional overrides.

This direction is deliberate. A table can only describe base shapes (text, length, enum values), while your types carry the full validation vocabulary (Email, URL, integer ranges, patterns). Types to tables keeps everything; the other way around would lose it. Because routes and tables share the same types, the compiled validators mion uses for a route are the exact same functions that describe your database rows.

::note
Column types are derived from Typescript types and [`@ts-runtypes/core/formats`](https://runtypes.pages.dev) - when you use format types like `UUIDv7`, `Email`, `Integer`, etc., the package automatically selects the most appropriate database column type for each database.
::

::tip
**Quick Tip:** 
This package is designed to work with [flat types that reflect the columnar structure of a database table]{.text-highlighted}, not deeply nested JavaScript objects with relationships. 
Use foreign key IDs instead of embedded entity references. Nested objects are stored as JSON columns.
::

## How To Use

#### Primary and Foreign Keys

Primary keys and foreign keys should always be defined in the tableConfig. This gives you full control over key constraints and relationships:

::tip
**Quick Tip:** 
Types should only contain information related to type and format, this will be used for validation and serialization.
Any columns asn SQL logic like primary, foreign keys, indexes, etc. should be defined in the tableConfig override.
::

#### Length Buffer

The `lengthBuffer` option multiplies the `maxLength` defined in custom string formats (`String`) to provide extra capacity for the database column. This is useful when you want to allow for some flexibility in the data length prevent resizing in the future, but still want to validate the correct length at runtime.

::note
The `lengthBuffer` only applies to custom `String` types with a `maxLength` constraint. Well-known formats like `Email`, `StrURL`, and `Domain` use their standard maximum lengths without any buffer.
::

#### Insert, Select and Update Types

Drizzle expects different payload shapes per operation: an insert may omit columns with defaults and must not include generated columns, an update accepts any subset, and a select returns every column with nullable ones as null. The `InsertModel`, `SelectModel` and `UpdateModel` utilities derive those shapes from your type, so route inputs and outputs stay fully formatted AND flow straight into drizzle:

<code-import path="packages/examples/src/drizzle/drizzle-model-types.ts" lang="ts" />

Since these are plain type transforms over your type, every format and its params survive. The validator compiled for a route input typed with them enforces the full rules (email shape, max lengths, integer ranges), and the same compiled function is shared by every consumer of that type.

::note
Defaults and generated columns are defined in your tableConfig, not in the type, so you name those keys explicitly in the utility (`InsertModel<User, 'id', 'createdAt'>`). TypeScript then catches any drift between the payload type and what the table actually accepts.
::

#### Table Config Validation

The function validates that your tableConfig matches the TypeScript type

```ts
interface User {
    id: string;
    name: string;
}

// ❌ Error: Column "email" exists in tableConfig but not in type "User"
const users = toDrizzlePGTable<User>('users', {
    id: uuid('id').primaryKey(),
    email: text('email'), // This property doesn't exist in User!
});
```

## Important Notes

#### Import Format Types Correctly

::info
When using format types from `@ts-runtypes/core/formats`, you must use **regular imports** (not `import type`) for the runtime type metadata to be preserved.
::

```ts
// ✅ Correct - regular import preserves metadata
import {UUIDv7, Email} from '@ts-runtypes/core/formats';

// ❌ Wrong - type import strips metadata
import type {UUIDv7, Email} from '@ts-runtypes/core/formats';
```

#### Nested Objects vs Foreign Keys

Nested objects are stored as JSON. Use foreign key IDs for entity references:

```ts
// ✅ Good: Profile is a value object - stored as JSON
interface User {
    id: string;
    profile: {bio: string; avatar: string};
}

// ❌ Bad: Don't embed entire entities
interface Book {
    id: string;
    owner: User; // This stores the entire User as JSON!
}

// ✅ Good: Use foreign key ID instead
interface Book {
    id: string;
    ownerId: string; // Reference by ID
}
```

#### Column Names and Casing

Generated columns are keyed by your TypeScript property names. If you want snake_case names in the database, use Drizzle's own `casing: 'snake_case'` option on the `drizzle()` connection config. That option renames columns at the SQL layer only, so your code keeps using the TypeScript names.
