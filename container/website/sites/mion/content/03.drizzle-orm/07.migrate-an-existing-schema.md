---
title: Migrate an Existing Schema
description: Move a schema file you already wrote with Drizzle ORM onto the slim packages, in one command.
---

If you already have tables written with Drizzle ORM, you do not have to move them by hand. One command rewrites them onto the slim packages and leaves every query alone.

```bash
npx mion drizzle-migrate src/db/schema.ts
```

Point it at a file or a whole directory. Add `--check` to see what it would change without writing anything, and `--out-dir converted/` to write the result somewhere else and keep your sources untouched.

## What it does to a table

Your table keeps its name. A second binding, with a `$table` suffix, holds the slim declaration:

```ts
// before
import {pgTable, uuid, varchar} from 'drizzle-orm/pg-core';

const users = pgTable('users', {id: uuid().primaryKey(), name: varchar({length: 50})});

// after
import {pgTable, uuid, varchar} from '@mionjs/drizzle-orm-pg-core';
import {toDrizzle} from '@mionjs/drizzle-orm-pg-core/drizzle';

const users$table = pgTable('users', {id: uuid().primaryKey(), name: varchar({length: 50})});
const users = toDrizzle(users$table);
```

That split is the whole idea. `users` still holds the real Drizzle table, so every query, every operator and every config reader keeps working with no edits at all:

```ts
await db.select().from(users).where(eq(users.id, someId));
getTableConfig(users);
```

And `users$table` is the slim one, which is what your models and your routes take their types from.

The suffix names what the binding holds, so a view becomes `$view`, an enum `$enum`, and so on for schemas, sequences, roles and policies.

## What moves and what stays

Imports split by what the slim packages actually wrap. Column builders, tables, views, indexes and constraints move; operators, config readers and everything on the query side stay on `drizzle-orm`:

```ts
import {alias, except, getTableConfig} from 'drizzle-orm/pg-core';
import {foreignKey, index, integer, text} from '@mionjs/drizzle-orm-pg-core';
```

One name lives on both sides. Drizzle's `sql` builds queries, and the slim `sql` records a default or a check, so both are imported and the slim one arrives as `rtSql`:

```ts
import {sql} from 'drizzle-orm';
import {sql as rtSql} from '@mionjs/drizzle-orm';

const docs$table = pgTable('docs', {at: timestamp().default(rtSql`now()`)});
await db.execute(sql`select 1`);
```

## What it will not touch

A view built from a query builder stays with Drizzle, and the command tells you so rather than guessing:

```
schema.ts: DRZ001 error [newYorkers:42]: a view built from a query builder stays on drizzle:
its columns come from drizzle's select typing. Declare the columns explicitly to migrate it.
```

Those views take their columns from Drizzle's select typing, which is exactly the machinery the slim packages exist to remove. Declare the columns yourself if you want the view to be slim, or leave it as it is. Either way the file it is in still runs.

The same goes for anything else the command cannot place: it reports it and leaves the code as written, so you are never handed a file that no longer works.

## Going all the way to types

The migrated file is ordinary slim code, so the second command works on it too. `mion convert --to type` rewrites each table as a pure type plus a one line bridge:

```bash
npx mion convert --to type src/db/schema.ts
```

```ts
// after drizzle-migrate
const users$table = pgTable('users', {id: uuid('id').primaryKey(), name: varchar('name', {length: 50})});
const users = toDrizzle(users$table);

// after convert --to type
type Users$tableTable = PgTable<'users', {
  id: Uuid<'id', {primaryKey: true}>;
  name: Varchar<'name', {length: 50}>;
}>;
const users$table = tableFromType<Users$tableTable>();
const users = toDrizzle(users$table);
```

It works on the imports you already have (no namespace import required) and on tables declared inside a function or a test, not only at the top of a file. `--to builders` goes back the other way, and a file that has been through both directions lands exactly where it started.

A column that points at another table keeps working wherever that table is declared. When the target sits further down the file, the bridge takes a small function instead of the value, which is the same laziness Drizzle's own `references: () => cities.id` has:

```ts
const children$table = tableFromType<ChildrenTable>({tables: {cities: () => cities$table}});
```

Some tables have no type spelling, and the command says which and why rather than guessing: a table built by a table creator, a table declared on a schema, `$type` on a column, a column name that is not a literal, or the same modifier applied twice. Those stay exactly as they are and keep working, so a file is never left half converted. Pass `--report report.json` to get the whole list in one place.

## Checking the result

Read the diff, then run your type checker and your tests. Nothing about the command is magic, and the point of keeping your original names bound to the real Drizzle tables is that there is very little left to check.
