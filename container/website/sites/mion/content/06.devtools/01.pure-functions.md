**Pure functions** — functions that follow strict purity rules (no closures, no external variables, no side effects) so they can be serialized, moved between builds, and executed safely — are a `mion run-types` feature. mion registers none of its own.

What mion adds is the one place where a pure function crosses the network boundary: **`serverMapFrom()`**, which lets client code name a mapper that runs on the *server*, mid-flow, between two routes.

| API | Defined in | Direction | Purpose |
|-----|-----------|-----------|---------|
| `registerPureFn()` | `@mionjs/run-types`, server code | Server-side registry | Register a pure utility under a `<namespace>::<name>` id |
| `serverMapFrom()` | `@mionjs/client`, client code | Client → Server | Map the output of one route to the input of another inside a `routesFlow` |
| `allowServerMapper()` | `@mionjs/core`, server code | — | Opt a registered pure fn into being reachable as a mapper |

## serverMapFrom (client → server data mapping)

`serverMapFrom()` is used in **client** code inside a `routesFlow` to map the output of one route into the input of another. The mapper is written in the client but harvested at build time and executed on the **server**, enabling GraphQL-style data composition without extra round trips:

<code-import path="packages/examples/src/introduction/pure-functions-examples.ts" lang="ts" commentStart="start:map-from-basic" commentEnd="end:map-from-basic" />

`serverMapFrom(sourceRequest, mapperFn)` returns a reference whose `.asArg()` produces a typed placeholder that satisfies the TypeScript compiler, while at runtime the server runs the mapper to extract the actual value from the source result. See [Routes Flow](/client/client-flow) for the full data-composition guide and the `serverMappers` build wiring.

The wire carries only the mapper's registry **key**, never its body — the server runs only functions its own build baked in.

::warning
`allowServerMapper()` is not boilerplate. The key a `routesFlow` request names arrives in the URL query string and is parsed without schema validation, so it is attacker-controlled. mion resolves it only against an allow-list — otherwise a request could name **any** entry in the shared `mion run-types` registry, including built-ins and entries registered by unrelated libraries sharing the process. Registering a pure function is deliberately *not* enough to make it reachable.
::

Inline mappers are opted in automatically: the build harvested them, so mion knows they came from your own client.

The [`@mionjs/no-vite-client`](./eslint-rules#mionjsno-vite-client) ESLint rule enforces that these name arguments are present and are string literals.

## Purity rules

Every function passed to a `mion run-types` registrar or to `serverMapFrom` must be **pure**:

::stylish-list
---
type: check
---
- [Only its parameters and locals:]{.text-highlighted} no closures over outer-scope or module variables
- [No side effects:]{.text-highlighted} no `this`, no `await`, no dynamic `import()`
- [No forbidden globals:]{.text-highlighted} no `eval`, `fetch`, `setTimeout`, `process`, `window`, etc.
- [Allowed globals only:]{.text-highlighted} `JSON`, `Math`, `RegExp`, `console`, and other pure built-ins are fine
::

```ts
// ✅ Pure — only uses the input parameter
serverMapFrom(order, (o) => o!.userId)

// ✅ Pure — inline computation with an allowed global
serverMapFrom(order, (o) => Math.round(o!.totalUSD * 100))

// ❌ NOT pure — references an external variable (closure)
const multiplier = 2;
serverMapFrom(order, (o) => o!.totalUSD * multiplier)
```

## Lint integration

Purity is checked at lint time by the `runtypes/pure-functions` rule from `mion run-types/devtools/eslint`, which surfaces the resolver's own diagnostics: `PFE9006`–`PFE9011` for `this` / `await` / `yield` / dynamic import / forbidden globals / closures, and `PFN001`–`PFN002` for a function literal that is not inline or is reachable from elsewhere. See the [ESLint Rules](./eslint-rules) page.
