## Which keywords map to what

Draft 2020-12, and these tables are total: every keyword the dialect defines appears exactly once below, with the two spellings it maps to. Every constraint accepted is a constraint enforced, at build time when a type can carry it and inside the generated validator when it cannot.

A shape can therefore migrate from a JSON Schema to a TypeScript type (or back) without changing what gets enforced, and matching spellings land on one generated function. `TF` comes from `@ts-runtypes/core/formats` and `RT` from `@ts-runtypes/core/schema`.

### Types

| Keyword | In a schema | As a type | As a builder |
| --- | --- | --- | --- |
| `type` | `{type: 'string'}` | `string`, `number`, `boolean`, `null` | `TF.string()`, `TF.number()`, `RT.boolean()`, `RT.literal(null)` |
| `type` (integer) | `{type: 'integer'}` | `TF.Integer` | `TF.integer()` |
| `type` (array form) | `{type: ['string', 'null']}` | `string \| null` | `RT.union([TF.string(), RT.literal(null)])` |
| `const` | `{const: 'pending'}` | `'pending'` | `RT.literal('pending')` |
| `enum` | `{enum: ['red', 'blue']}` | `'red' \| 'blue'` | `RT.union([RT.literal('red'), RT.literal('blue')])` |

A bare `true` or `{}` as a subschema recovers `unknown` (`RT.unknown()`), and `false` recovers `never` (`RT.never()`).

### Objects

| Keyword | In a schema | As a type | As a builder |
| --- | --- | --- | --- |
| `properties` | `{properties: {id: {...}}}` | an object type with those members | `RT.object({id: ...})` |
| `required` | `{required: ['id']}` | a member left out gets `?` | `RT.optional(...)` on the members left out |
| `additionalProperties` (schema) | `{additionalProperties: {type: 'number'}}` | an intersection with `Record<string, V>` | `RT.intersection([shape, RT.record(v)])` |
| `additionalProperties: false` | `{additionalProperties: false}` | the shape really closes | `RT.object(config)` stays exact |
| `minProperties` / `maxProperties` | `{minProperties: 1}` | `TF.FormattedObject<Base, {minProperties: 1}>` | `RT.object(config, {minProperties: 1})` |
| `patternProperties` | `{patternProperties: {'^col_': {...}}}` | `TF.FormattedObject<Base, {patternProperties: {'^col_': number}}>` | `RT.record(inner, {patternProperties: {'^col_': TF.number()}})` |
| `propertyNames` | `{propertyNames: {pattern: '^[a-z]+$'}}` | `TF.FormattedObject<Base, {propertyNames: Key}>` | `RT.record(inner, {propertyNames: keys})` |
| `dependentRequired` | `{dependentRequired: {card: ['cvv']}}` | a union of the allowed combinations | `RT.union([...])` |
| `dependentSchemas` | `{dependentSchemas: {card: {...}}}` | a union of the allowed combinations | `RT.union([...])` |

### Arrays and tuples

| Keyword | In a schema | As a type | As a builder |
| --- | --- | --- | --- |
| `items` | `{items: {type: 'string'}}` | `Item[]` | `RT.array(item)` |
| `prefixItems` | `{prefixItems: [a, b], items: r}` | `[A, B, ...Rest[]]` | `RT.tuple([a, b], rest)` |
| `prefixItems` (boolean slots) | `{prefixItems: [true, false]}` | `true` leaves a position unconstrained, `false` forbids it | the matching tuple slots |
| `minItems` | `{minItems: 2}` | that many required slots, `[T, T, ...T[]]` | `RT.tuple([t, t], t)` |
| `maxItems` | `{maxItems: 5}` | `TF.FormattedArray<T[], {maxItems: 5}>` | `RT.array(item, {maxItems: 5})` |
| `uniqueItems` | `{uniqueItems: true}` | `TF.FormattedArray<T[], {uniqueItems: true}>` | `RT.array(item, {uniqueItems: true})` |
| `contains` | `{contains: {format: 'uuid'}}` | `TF.FormattedArray<Base, {contains: Item}>` | `RT.array(item, {contains: TF.uuid()})` |
| `minContains` / `maxContains` | `{contains: c, minContains: 2}` | `TF.FormattedArray<Base, {contains: Item; minContains: 2}>` | `RT.array(item, {contains: c, minContains: 2})` |

Trailing optional slots come from `prefixItems` entries past `minItems`: two prefix entries with `minItems: 1` recover `[A, B?]`, written `RT.tuple([a], [b])`.

### Strings

| Keyword | In a schema | As a type | As a builder |
| --- | --- | --- | --- |
| `format` | `{format: 'email'}` | `TF.Email`, `TF.UUID`, `TF.StringDate`, `TF.StringTime`, `TF.StringDateTime`, `TF.Domain`, `TF.IPv4`, `TF.IPv6`, `TF.Url` | `TF.email()`, `TF.uuid()`, `TF.stringDate()` and the rest |
| `minLength` / `maxLength` | `{minLength: 2, maxLength: 60}` | `TF.String<{minLength: 2; maxLength: 60}>` | `TF.string({minLength: 2, maxLength: 60})` |
| `pattern` | `{pattern: '^[a-z]+$'}` | `TF.String<{pattern: {source: '^[a-z]+$'}}>` | `TF.string({pattern: {source: '^[a-z]+$'}})` |
| `contentEncoding` | `{contentEncoding: 'base64'}` | `TF.Base64`, `TF.Base32`, `TF.Base16` | `TF.base64()`, `TF.base32()`, `TF.base16()` |
| `contentMediaType` | `{contentMediaType: 'application/json'}` | `TF.JsonContent`, or `TF.JsonContentBase64` behind an encoding | `TF.jsonContent()`, `TF.jsonContentBase64()` |

Length is counted in characters, not in the units a JavaScript string happens to store. An emoji counts as one, so `'💩💩'` fits `maxLength: 2`.

A `pattern` is a regular expression read in unicode mode, which is what lets `\p{Letter}` and the other property escapes mean what they say.

### Numbers

| Keyword | In a schema | As a type | As a builder |
| --- | --- | --- | --- |
| `minimum` / `maximum` | `{minimum: 0, maximum: 120}` | `TF.Number<{min: 0; max: 120}>` | `TF.number({min: 0, max: 120})` |
| `exclusiveMinimum` / `exclusiveMaximum` | `{exclusiveMinimum: 0}` | `TF.Number<{gt: 0; lt: 1}>` | `TF.number({gt: 0, lt: 1})` |
| `multipleOf` | `{multipleOf: 5}` | `TF.Number<{multipleOf: 5}>` | `TF.number({multipleOf: 5})` |

The JSON spellings are accepted on the type side too, so `TF.Number<{minimum: 0}>` and `TF.Number<{min: 0}>` are the same type.

`multipleOf` takes any positive number, whole or not, so `{multipleOf: 0.01}` on a price works. A value counts as a multiple when dividing it by the step gives a whole number, which is the rule the spec states.

### Combinators and negation

| Keyword | In a schema | As a type | As a builder |
| --- | --- | --- | --- |
| `anyOf` | `{anyOf: [a, b]}` | a plain union `A \| B`, or `RT.AnyOf<[A, B]>` | `RT.union([a, b])` or `RT.anyOf([a, b])` |
| `oneOf` | `{oneOf: [a, b]}` | `RT.OneOf<[A, B]>`, exactly one branch, enforced | `RT.oneOf([a, b])` |
| `allOf` | `{allOf: [a, b]}` | an intersection `A & B` | `RT.intersection([a, b])` |
| `not` | `{not: {format: 'email'}}` | `TF.Not<TF.Email>` | `RT.not(TF.email())` |

A `not` over a value list rather than a format recovers a string with disallowed values, written `TF.string({disallowedValues: {...}})`.

### Conditionals

| Keyword | In a schema | As a type | As a builder |
| --- | --- | --- | --- |
| `if` / `then` / `else` | `{if: c, then: t, else: e}` | a union of the two outcomes | `RT.union([...])` |

### References

| Keyword | In a schema | As a type | As a builder |
| --- | --- | --- | --- |
| `$defs` | `{$defs: {Node: {...}}}` | named types referring to each other | schema values held in variables |
| `$ref` | `{$ref: '#/$defs/Node'}` | the referenced type | the variable holding that schema |
| `$ref` to the root | `{$ref: '#'}` | a recursive type | `RT.circular(...)` with `RT.self()` |
| `$anchor` / `$dynamicAnchor` | `{$anchor: 'node'}` | a name a `$ref` can target | the same variable, named |
| `$dynamicRef` | `{$dynamicRef: '#node'}` | the anchored type, resolved statically | the variable it resolves to |

### Unevaluated

| Keyword | In a schema | As a type | As a builder |
| --- | --- | --- | --- |
| `unevaluatedProperties` | `{unevaluatedProperties: false}` | the shape closes, wherever the evaluated set is knowable from the document | `RT.object(config)` stays exact |
| `unevaluatedItems` | `{unevaluatedItems: false}` | the tuple closes, same condition | the matching fixed tuple |

### Annotations

These describe the schema rather than the data, so they are read and ignored. The one exception is `readOnly`, which has a faithful TypeScript spelling.

| Keyword | In a schema | As a type | As a builder |
| --- | --- | --- | --- |
| `readOnly` | `{readOnly: true}` on a property | a `readonly` member | `RT.propMod({readonly: true}, field)` |
| `title`, `description`, `examples`, `default`, `$comment`, `deprecated`, `writeOnly` | `{title: 'User'}` | nothing, the type is unchanged | nothing |
| `$schema`, `$id`, `$vocabulary` (at the root) | `{$schema: '...2020-12/schema'}` | nothing, the type is unchanged | nothing |

Accepted string formats are `email`, `uuid` (any version, as the spec intends), `date`, `time`, `date-time`, `hostname`, `ipv4`, `ipv6` and `uri`. Any other `format` value is treated as the annotation the spec defaults it to: the type stays a plain string and nothing is silently half-checked.

Each keyword lowers to the format of the same name, and those formats read the keyword the way the spec does. `ipv4` accepts a dotted quad and turns down the word `localhost`, because the spec calls it an address. Where a format offers a wider reading, it is an option you turn on yourself rather than something the keyword assumes.

Keywords that assert something no TypeScript type can express, like `uniqueItems` or a `contains` count, still validate exactly: the generated function carries the check even though the recovered type stays the closest expressible shape. Annotations are read and ignored; they describe the schema rather than the data. The one exception is `readOnly: true` on a property, which has a faithful TypeScript spelling: the recovered member gains the `readonly` modifier and matches the same type written by hand, readonly and all.

::note
Anything the dialect does not define is rejected where you wrote it, not silently dropped. A misspelled `minLen` is a type error on that key, so a constraint can never go missing without you hearing about it.
::

A few corners are turned away loudly instead of guessed at. An embedded `$id` re-scopes references, so it is rejected at the key. `contentSchema` would validate decoded content against a second schema in one pass, which has no honest single-pass story. `unevaluatedProperties` and `unevaluatedItems` beside `if`, `dependentSchemas`, `anyOf`, `oneOf` or a reference depend on which branch matched at run time, so those combinations resolve to an impossible type rather than a validator that quietly checks less than the schema says. The same principle covers `oneOf` next to a constraining sibling (a `type` gate, another combinator, or a keyword like `minLength`): rather than quietly dropping the exclusivity, the combination resolves to an impossible type, and the fix is to move the shared constraint into each branch.

## Things worth knowing

Both combinators mean exactly what the spec says. `anyOf` accepts a value that matches at least one branch, which is what a plain union already does. `oneOf` requires exactly one branch: a value matching two branches is rejected, just as a strict JSON Schema validator would reject it. Exclusivity counts branches as you wrote them, so in `oneOf: [A, {anyOf: [B, C]}]` a value matching both B and C still matched only one branch and passes.

Constraints spread across `allOf` branches really combine. When two branches each describe tuple positions with `prefixItems`, the positions merge one by one into a single tuple, and the generated validator enforces the merged shape. A combination that no value could satisfy is rejected outright instead of being half-checked.

Only draft 2020-12 is accepted, and a `$schema` naming another dialect is a type error. References to other documents are out of scope; `$ref` and `$dynamicRef` resolve inside the schema you passed, including `$anchor` and `$dynamicAnchor` targets.

Some things simply have no JSON Schema spelling: `bigint`, `Date` and the other native class types, `Map`, `Set`, and template literal types. Those still work, you just describe them with a TypeScript type or an `RT.*` builder instead. You can mix all three forms in one file.
