## Which keywords map to a type

Draft 2020-12, and the table below is total: every keyword the dialect defines has exactly one disposition here. Every constraint accepted is a constraint enforced, at build time when a type can carry it and inside the generated validator when it cannot.

| Area | Keywords |
| --- | --- |
| Types | `type` (including the array form), `const`, `enum` |
| Objects | `properties`, `required`, `additionalProperties` (`false` really closes the shape), `minProperties`, `maxProperties`, `patternProperties`, `propertyNames`, `dependentRequired`, `dependentSchemas` |
| Arrays and tuples | `items`, `prefixItems` (boolean slots included: `true` leaves a position unconstrained, `false` forbids it), `minItems`, `maxItems`, `uniqueItems`, `contains`, `minContains`, `maxContains` |
| Combinators and negation | `anyOf`, `oneOf` (exactly one branch, enforced), `allOf`, `not` |
| Conditionals | `if`, `then`, `else` |
| References | `$defs`, `$ref` (the root, a root definition, or an anchor), `$anchor`, `$dynamicAnchor`, `$dynamicRef` |
| Strings | `format`, `minLength`, `maxLength`, `pattern`, `contentEncoding` (`base64`, `base32`, `base16`), `contentMediaType` (`application/json`, decoded first when an encoding is declared) |
| Numbers | `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`, `multipleOf` |
| Unevaluated | `unevaluatedProperties`, `unevaluatedItems` (the `false` form, wherever the evaluated set is knowable from the document) |
| Annotations | `$schema`, `title`, `description`, `examples`, `default`, `$comment`, `deprecated`, `readOnly`, `writeOnly`, plus `$id` and `$vocabulary` at the root |

Accepted string formats are `email`, `uuid` (any version, as the spec intends), `date`, `time`, `date-time`, `hostname`, `ipv4`, `ipv6` and `uri`. Any other `format` value is treated as the annotation the spec defaults it to: the type stays a plain string and nothing is silently half-checked.

Keywords that assert something no TypeScript type can express, like `uniqueItems` or a `contains` count, still validate exactly: the generated function carries the check even though the recovered type stays the closest expressible shape. Annotations are read and ignored; they describe the schema rather than the data. The one exception is `readOnly: true` on a property, which has a faithful TypeScript spelling: the recovered member gains the `readonly` modifier and matches the same type written by hand, readonly and all.

::note
Anything the dialect does not define is rejected where you wrote it, not silently dropped. A misspelled `minLen` is a type error on that key, so a constraint can never go missing without you hearing about it.
::

A few corners are turned away loudly instead of guessed at. An embedded `$id` re-scopes references, so it is rejected at the key. `contentSchema` would validate decoded content against a second schema in one pass, which has no honest single-pass story. `unevaluatedProperties` and `unevaluatedItems` beside `if`, `dependentSchemas`, `anyOf`, `oneOf` or a reference depend on which branch matched at run time, so those combinations resolve to an impossible type rather than a validator that quietly checks less than the schema says. The same principle covers `oneOf` next to a constraining sibling (a `type` gate, another combinator, or a keyword like `minLength`): rather than quietly dropping the exclusivity, the combination resolves to an impossible type, and the fix is to move the shared constraint into each branch.

## Moving between schemas and types

Every schema feature has a matching spelling on the type side, so a shape can migrate from a JSON Schema to a TypeScript type (or the other way) without changing what gets enforced, and matching spellings land on one generated function. In the table, `TF` comes from `@ts-runtypes/core/formats` and `RT` from `@ts-runtypes/core/schema`.

| JSON Schema | As a type | As a builder |
| --- | --- | --- |
| `type: 'string'` and the other primitives | `string`, `number`, `boolean`, `null` | `TF.string()`, `TF.number()`, `RT.boolean()`, `RT.literal(null)` |
| `type: 'integer'` | `TF.Integer` | `TF.integer()` |
| `type: ['string', 'null']` | `string \| null` | `RT.union([TF.string(), RT.literal(null)])` |
| `true` or `{}` as a subschema | `unknown` | `RT.unknown()` |
| `false` as a subschema | `never` | `RT.never()` |
| `const: 'pending'` | `'pending'` | `RT.literal('pending')` |
| `enum: ['red', 'blue']` | `'red' \| 'blue'` | `RT.union([RT.literal('red'), RT.literal('blue')])` |
| `properties` and `required` | an object type; a member not listed in `required` gets `?` | `RT.object({...})` with `RT.optional(...)` members |
| `additionalProperties` holding a schema | an intersection with `Record<string, V>` | `RT.intersection([shape, RT.record(v)])` |
| `patternProperties` | `RT.PatternProperties<Base, {'^col_': number}>` | `RT.patternProperties(inner, {'^col_': TF.number()})` |
| `propertyNames` | `RT.PropertyNames<Base, Key>` | `RT.propertyNames(inner, keys)` |
| `minProperties` / `maxProperties` | `RT.ObjectFormat<Base, {minProperties: 1}>` | `RT.objectFormat(inner, {minProperties: 1})` |
| `dependentRequired` / `dependentSchemas` | a union of the allowed combinations | `RT.union([...])` |
| `items` | `Item[]` | `RT.array(item)` |
| `prefixItems` with `items` | `[A, B, ...Rest[]]` | `RT.tuple([a, b], rest)` |
| `prefixItems` beyond `minItems` | trailing optional slots, `[A, B?]` | `RT.tuple([a], [b])` |
| `minItems` past the prefix | that many required slots, `[T, T, ...T[]]` | `RT.tuple([t, t], t)` |
| `maxItems` / `uniqueItems` | `RT.ArrayFormat<T[], {maxItems: 5; uniqueItems: true}>` | `RT.arrayFormat(inner, {maxItems: 5, uniqueItems: true})` |
| `contains` with `minContains` / `maxContains` | `RT.Contains<Base, Item, Min, Max>` | `RT.contains(inner, item, {minContains: 2})` |
| `anyOf` | a plain union `A \| B`, or `RT.AnyOf<[A, B]>` | `RT.union([a, b])` or `RT.anyOf([a, b])` |
| `oneOf` | `RT.OneOf<[A, B]>` | `RT.oneOf([a, b])` |
| `allOf` | an intersection `A & B` | `RT.intersection([a, b])` |
| `not` over format constraints | `TF.Not<TF.Email>` | `RT.not(TF.email())` |
| `not: {const: ...}` / `not: {enum: [...]}` | a string format with `disallowedValues` | `TF.string({disallowedValues: {...}})` |
| `if` / `then` / `else` | a union of the two outcomes | `RT.union([...])` |
| `$defs` and `$ref` | named types referring to each other | schema values held in variables |
| a `$ref` back to the root | a recursive type | `RT.circular(...)` with `RT.self()` |
| `format` | `TF.Email`, `TF.UUID`, `TF.StringDate`, `TF.StringTime`, `TF.StringDateTime`, `TF.Domain`, `TF.IPv4`, `TF.IPv6`, `TF.Url` | `TF.email()`, `TF.uuid()`, `TF.stringDate()` and the rest |
| `minLength` / `maxLength` / `pattern` | `TF.String<{minLength: 2; maxLength: 60}>` | `TF.string({minLength: 2, maxLength: 60})` |
| `minimum` / `maximum` | `TF.Number<{min: 0; max: 120}>` | `TF.number({min: 0, max: 120})` |
| `readOnly: true` on a property | a `readonly` member | `RT.propMod({readonly: true}, field)` |
| `exclusiveMinimum` / `exclusiveMaximum` | `TF.Number<{gt: 0; lt: 1}>` | `TF.number({gt: 0, lt: 1})` |
| `multipleOf: 5` | `TF.Number<{multipleOf: 5}>` | `TF.number({multipleOf: 5})` |

A few things stay schema-only on purpose. Closing a shape (`additionalProperties: false`, or the `unevaluated` pair) is derived from the schema's own property list, so it has no hand-written twin; on the type side the unknown-keys helpers cover the same ground. The content keywords (`contentEncoding`, `contentMediaType`) have no named type spelling either, though a pattern format can express the same alphabet check. The annotations never constrained anything, so there is nothing to migrate.

## Things worth knowing

Both combinators mean exactly what the spec says. `anyOf` accepts a value that matches at least one branch, which is what a plain union already does. `oneOf` requires exactly one branch: a value matching two branches is rejected, just as a strict JSON Schema validator would reject it. Exclusivity counts branches as you wrote them, so in `oneOf: [A, {anyOf: [B, C]}]` a value matching both B and C still matched only one branch and passes. The same semantics are available outside the schema door as the OneOf and AnyOf types and the oneOf and anyOf builders, and all three spellings of a shape land on one generated function. The structural keywords travel the same way: arrayFormat, objectFormat, contains, patternProperties and propertyNames each have a builder and a type, so a constraint like uniqueItems can be authored in whichever mode fits the file.

Constraints spread across `allOf` branches really combine. When two branches each describe tuple positions with `prefixItems`, the positions merge one by one into a single tuple, and the generated validator enforces the merged shape. A combination that no value could satisfy is rejected outright instead of being half-checked.

Only draft 2020-12 is accepted, and a `$schema` naming another dialect is a type error. References to other documents are out of scope; `$ref` and `$dynamicRef` resolve inside the schema you passed, including `$anchor` and `$dynamicAnchor` targets.

Some things simply have no JSON Schema spelling: `bigint`, `Date` and the other native class types, `Map`, `Set`, and template literal types. Those still work, you just describe them with a TypeScript type or an `RT.*` builder instead. You can mix all three forms in one file.
