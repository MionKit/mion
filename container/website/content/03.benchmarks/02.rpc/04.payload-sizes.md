The other benchmarks all send a small body. This one sends the same route four
different payload sizes, from about 1 KB up to 4 MB, to show how each mion server
adapter behaves when the request stops fitting in a single read from the network.

::tip
Only the mion adapters run here. The question is how mion's own body handling scales,
not how it compares with another framework.
::

## What is tested?

Every request is the heavy validation route, an `updateUser` call whose payload is
padded to the target size by growing its `tags` list. The padding is part of the
model, so the whole body is validated at every size rather than skipped over.

Three servers run the identical routes:

- **mion** on the Node adapter (`@mionjs/platform-node`)
- **mion.uws** on the uWebSockets.js adapter (`@mionjs/platform-uws`)
- **mion.bun** on the Bun adapter (`@mionjs/platform-bun`)

### Notes

::note{icon="i-heroicons-light-bulb"}
**Why these sizes?** A body larger than 512 KB cannot arrive in one read from the
socket. The uWebSockets adapter takes a different, copy-free path for those, so the
sizes here sit deliberately on both sides of that line: the 500 KB case is the last
one that still arrives in a single read, and the 4 MB case cannot.
::

::note{icon="i-heroicons-light-bulb"}
**Fewer connections on the largest payload.** Every size keeps the same cap on how many
request-body bytes are in flight at once, so the bigger the payload, the fewer requests
run at the same time. Without that, 4 MB bodies would spend the run queueing rather than
being handled, which measures the queue instead of the server.
::
