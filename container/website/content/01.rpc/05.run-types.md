mion does not ask you to write schemas. Your route handlers are typed, and that is
all the information mion needs to validate incoming parameters, serialize results,
and generate mock data.

The engine behind that is **RunTypes**, a standalone library that reads your
TypeScript program at build time and generates the matching runtime functions. mion
depends on it and wires it up for you, so most of the time you never call it directly.

::note
The complete RunTypes documentation lives in its own section:
[the RunTypes docs](/runtypes). This page only covers what changes
when you use it through mion.
::

## What you get for free

Because RunTypes reads the types on your route handlers, mion can do all of this
without a single schema declaration:

::stylish-list
---
type: check
---
- [Validation]{.text-highlighted} of every route parameter, with detailed errors. See [Validation](/rpc/server/validation).
- [JSON serialization]{.text-highlighted} that survives `Date`, `BigInt`, `Map` and `Set`. See [Serialization](/rpc/server/serialization).
- [Binary serialization]{.text-highlighted} for smaller, faster payloads. See [Binary Serialization](/rpc/articles/binary-serialization).
- [Mock data]{.text-highlighted} generated straight from your types, for tests and fixtures.
::

:read-more{to="/runtypes/guide/validation" title="The RunTypes validation guide"}

## Reading the API directly

Nothing stops you from using the RunTypes factories yourself, inside a route or
anywhere else in your project. They are the same functions mion calls:

::::twoslash-code
---
path: packages/examples/src/_homepage/home-run-types.ts
title: run-types.ts
---
::::

| What you want | Factory |
| --- | --- |
| Check a value against a type | `createValidateFn<T>()` |
| Detailed validation errors | `createGetValidationErrorsFn<T>()` |
| Value to JSON string, and back | `createJsonEncoderFn<T>()` / `createJsonDecoderFn<T>()` |
| Value to bytes, and back | `createBinaryEncoderFn<T>()` / `createBinaryDecoderFn<T>()` |
| Sample data from a type | `createMockDataFn<T>()` |

Each of these is documented in full, with options and edge cases, in the
[RunTypes guide](/runtypes/guide/type-builders).

## Things to watch out for in mion routes

RunTypes resolves types at build time. Three mion specific pitfalls can stop it
generating what you expect, and the [ESLint plugin](/rpc/devtools/linter)
catches all of them while you type.

### Type-only imports are fine

`import type { X }` is safe. RunTypes reads the TypeScript program and injects the
compiled functions at the `route()` or `middleFn()` call site, so it does not matter
that the import itself is erased from the emitted JavaScript.

```ts
// Both of these work identically
import type {User} from './types';
import {User} from './types';

route((ctx, id: number): User => getUser(id));
```

::note
This used to be a real pitfall. Before mion moved to RunTypes, reflection metadata was
emitted from the import statement itself, so `import type` erased it and silently broke
validation. The `@mionjs/no-type-imports` rule that guarded against it has been removed.
::

### Parameters and return types need annotations

RunTypes reads the types you write. An unannotated parameter has nothing to read, so
no validation is generated for it.

```ts
// Wrong: nothing to read, so nothing is generated
route((ctx, user) => user.name);

// Right: explicit annotations
route((ctx, user: User): string => user.name);
```

::note
The [`@mionjs/strong-typed-routes`](/rpc/devtools/linter#mionkitstrong-typed-routes)
rule catches this.
::

### Order union members from most specific to least

Deserializing a union tries each member in declaration order and takes the first
match. A less specific member listed first makes the later ones unreachable.

```ts
// Wrong: {id: string} matches first, so the second member is never used
type User = {id: string} | {id: string; name: string};

// Right: most specific first
type User = {id: string; name: string} | {id: string};
```

::note
The [`@mionjs/no-unreachable-union-types`](/rpc/devtools/linter#mionkitno-unreachable-union-types)
rule catches this, for types reachable from a route or middleFn.
::

## Turning the rules on

```bash
npm install @mionjs/devtools -D
```

```json [.eslintrc.json]
{
  "extends": ["plugin:@mionjs/recommended"]
}
```

That enables every rule above at `error` severity. The full rule catalogue is in
[ESLint Rules](/rpc/devtools/linter).
