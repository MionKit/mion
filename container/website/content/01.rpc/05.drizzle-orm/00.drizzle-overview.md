Mion's Drizzle integration follows RunTypes: TypeScript types express database settings and TypeFormats metadata. Those types describe your schema and generate validation, mock data and JSON conversion for server and client.

One package per database gives you the [Drizzle ORM](https://orm.drizzle.team) table functions for that database, with the same names, config, indexes and constraints. A column takes all its settings in one object instead of a chain of calls.

| Database | Package |
|----------|---------|
| PostgreSQL | `@mionjs/drizzle-orm-pg-core` |
| MySQL | `@mionjs/drizzle-orm-mysql-core` |
| SQLite | `@mionjs/drizzle-orm-sqlite-core` |
| Cloudflare D1, Durable Objects | `@mionjs/drizzle-orm-sqlite-core` |

Cloudflare's two databases are both SQLite, so they use the SQLite package and only change the driver: see [Cloudflare D1 and Durable Objects](/rpc/drizzle-orm/cloudflare-storage).

Package versions follow drizzle-orm, not mion: version 0.45.x works with drizzle-orm 0.45.x and declares that range as a peer dependency. Pick the version that matches your drizzle-orm. A new version ships only when the package changes, so one version can stay current across several mion releases.

Install the database package with its shared core. drizzle-orm is an optional peer: your schema, models and validators work without it.

```bash
npm install @mionjs/drizzle-orm-pg-core @mionjs/drizzle-orm @mionjs/run-types
npm install drizzle-orm   # only needed to run queries or migrations
```

## Column Settings

A column builder takes the database column name, then one object with drizzle's config and its modifiers. A modifier with no arguments is `true`, one with arguments is its argument list.

```ts
// drizzle
varchar('name', {length: 100}).notNull().default('anon');
// mion
varchar('name', {length: 100, notNull: true, default: ['anon']});
```

::tip
Leave out the database name when it matches the key: `name: varchar({length: 100})`.
::

## Writing a Table as a Type

Each column builder has a column type of the same name, first letter uppercased, that takes the same settings object: `Varchar<{length: 100; notNull: true}>`. A builder table's `typeof users` equals the same table written by hand, so you can mix both forms per table. `mion convert` translates a table between the two forms in either direction.

## Organising Schema and Database Files

Keep slim tables and the models your routes and client use in a schema file. Put `toDrizzle`, relations, the database connection and queries in a database file that imports it. The [linter](/rpc/devtools/linter#separating-database-code) enforces the split: `drizzle-mixed-types` fails the build when a file defining slim tables or models imports Drizzle or `toDrizzle`, and `drizzle-type-not-allowed` warns when a route takes or returns a Drizzle type.

## Recorded Tables From a Type

Where you need the recorded table without drizzle (models, refinement, mion routes), use `tableFromType<UsersTable>()` from the package root. Its options take the two runtime inputs a type cannot hold: the tables a column references (`{tables: {parents: parents}}`, or `{tables: {parents: () => parents}}` when that table is declared further down the file) and the runtime callbacks described below.

## Refining Tables for Your API

`refineTableType` adds API rules stricter than the database column: a name that holds 100 characters can require at least 10. It returns the same table object with the extra rules added, and the SQL does not change. Build validators, mock data and JSON round trip functions from the refined models, with or without mion.

A refinement that does not fit the column is a compile error, never a silent override: a number rule on a string column, an unknown parameter, or a change to whether the column accepts null (that stays with notNull on the table). Columns without a format (booleans, JSON, enums) cannot be refined.

## Refined Table Types

`RefinedTable` does the same refinement as a type, with no table value: it takes the table type and the per-column rules, so a types-only file can export the API view of a table.

```ts
import type {RefinedTable} from '@mionjs/drizzle-orm';
import type {UsersTable} from './schema.ts';

type ApiUsersTable = RefinedTable<UsersTable, {name: {minLength: 10}; age: {min: 18}}>;
```

## Insert, Select and Update Payloads

`InferSelectModel` and `InferInsertModel` keep drizzle's names, so a schema file ports by changing only the import. They come from `@mionjs/drizzle-orm`, with refineTableType and the sql template, and work on any table, refined or not: inserts drop generated columns and make defaulted ones optional. As in drizzle, an update is `Partial<InferInsertModel<typeof users>>`. From a table type, the file is types only.

## Runtime Column Callbacks

A builder takes Drizzle's `$default`, `$defaultFn`, `$onUpdate` and `$onUpdateFn` callbacks as a one-item list: `$defaultFn: [() => crypto.randomUUID()]`. A type cannot hold a function, so a table type sets the same prop to `true` and the callback goes in the `runtime` option of tableFromType or toDrizzle. A column with any of these props counts as having a default, so it is optional on insert, even in files that only import the type.

## Custom JSON Types

Columns with no matching format (geometry, vectors, MAC addresses, binary data, plain booleans and JSON) keep their plain data type. For a JSON column, declare your own type with the `$type` prop.

::code-group
```ts [Builders]
import * as DZ from '@mionjs/drizzle-orm-pg-core';
import {$type} from '@mionjs/drizzle-orm';

const events = DZ.pgTable('events', {
  id: DZ.uuid({primaryKey: true}),
  payload: DZ.jsonb({$type: $type<{kind: string; at: number}>(), notNull: true}),
});
```

```ts [Types]
import * as DZ from '@mionjs/drizzle-orm-pg-core';

type EventsTable = DZ.PgTable<
  'events',
  {
    id: DZ.Uuid<{primaryKey: true}>;
    payload: DZ.Jsonb<{$type: [{kind: string; at: number}]; notNull: true}>;
  }
>;
```
::

::note
Every column builder's format, per database and column mode, is listed in [Column Formats](./column-formats).
::
