The client half of [fetchMetadata](/rpc/middlewares/fetch-metadata). It fetches each route's metadata from the server, so your client build does not bundle it.

## Disabling Routes Metadata Bundling

Disable routes metadata bundling with `client: {routes: 'fetch'}` in your client build. Then call `useFetchMetadata` once, next to `initClient`, with the client's `middlewares.mionFetchMetadata`. The server must also [add the middleware](/rpc/middlewares/fetch-metadata#adding-the-middleware).

This is also how you build a client apart from its API. The server sends its own compiled functions, so they always match it.

| --- | --- |
| [Vite plugin](/rpc/devtools/vite#all-plugin-options) | `client: {routes: 'fetch'}` |
| [Next.js](/rpc/devtools/nextjs#options) `withMion` | `client: {routes: 'fetch'}` |

| tsconfig plugin entry | `clientRoutes: 'fetch'` |

::note
The code that fetches metadata is a separate file, downloaded only when a call first needs metadata. If it fails to load, the call gets `metadata-load-error` in its [`@thrownErrors`](/rpc/client/error-handling#the-result-pattern), and the next call tries again.
::

## Fetching Only What the Build Misses

If you keep bundling on and also call `useFetchMetadata`, the client fetches metadata only for calls the build could not bundle: calls whose route a generic helper hides. Fetched metadata never replaces a bundled route. To keep every call bundled, see [Generic Call Helpers](/rpc/devtools/vite#generic-call-helpers).

| Client | A call whose route the build cannot see |
| --- | --- |
| Without `useFetchMetadata` | Stops the build with MET003. If it runs anyway, it gets `route-metadata-not-found` in its `@thrownErrors`, naming the fix. |
| With `useFetchMetadata` | Fetches its metadata instead, so a strict Content Security Policy blocks it. The build reports MET004, an Info message shown only with [`levels: 'all'`](/runtypes/diagnostics/error-levels#showing-info-messages). |

## The First Call

A route's first call goes out right away and asks for the metadata in the same request. The server validates the params and answers with the result and the metadata. The client saves the metadata, so later calls also validate in the browser before sending.

| Case | What the client does |
| --- | --- |
| Params that `JSON.stringify` cannot write | Fetches the metadata first, then sends the call. |
| A param that needs its type to be encoded, like a `string \| Date` union | Sends the call once more with the right encoding. The route did not run. |
| `typeErrors()` on a route it has not seen | Fetches the metadata alone. The route does not run. |
| A saved copy that no longer matches the server | Drops the saved copy and sends the call once more. |

::note
The client sends a call again at most once, only when the server could not read or validate the params, and never after a mutation in that call succeeded. After the route's own error, a network error, a timeout or an abort, it never sends again.
::

## Saving Fetched Metadata

The client saves what it fetched, per server, so a later visit does not ask again. Pick where with the `storageEngine` client option. Where the store cannot open, like on the server or in a browser that blocks IndexedDB, the client keeps it in memory.

<code-import path="packages/private-examples/src/client/fetch-metadata-storage.ts" lang="ts [client.ts]" />

| `storageEngine` | Where it saves |
| --- | --- |
| `'indexeddb'` (default) | The browser's IndexedDB, kept between visits. |
| `'memory'` | Memory, for this page load or process only. |
| A function | [Your own store](#using-your-own-store). |

::note
Each server's cache holds up to 8 MB and drops its oldest entries first. If the browser still refuses a write, a later call gets a `metadata-cache-error` in its `@thrownErrors`, once.
::

::tip
The browser can clear the cache (low disk space, or Safari after 7 days without a visit), and the client then fetches again. mion never shows a permission popup itself: call `requestPersistentStorage()` yourself, as in the example.
::

## API Version Check

The server sends its API version with every response, and the client compares it with the version it was built with. A mismatch does not stop the call: reload the app or rebuild the client to fix it. To stop such calls, use [mionSyncRoutes](/rpc/middlewares/sync-routes). To catch a mismatch before you deploy, run [mion api-check](/rpc/devtools/cli#checking-a-client-against-its-server).

| Client | On a mismatch |
| --- | --- |
| Without `useFetchMetadata` | The call that sees it gets an `api-version-mismatch` error in its `@thrownErrors`, once per server. |
| With `useFetchMetadata` | Each route is checked once, on its first call after the mismatch. A changed route whose metadata was fetched is fetched again. A changed bundled route gets `api-version-mismatch`, naming the route. |

::tip
Set `apiVersionCheck: false` in `createMionRouter` to stop sending the version. The client then checks nothing.
::

## Build Checks

The build fails on a setup that would fail at runtime. Look up any code in [All Diagnostics](/runtypes/diagnostics/all-diagnostics).

| Code | When |
| --- | --- |
| MET001 | The client is not typed with `PublicApi<typeof routes>`. |
| MET002 | A call names a route the API type does not declare. |
| MET003 | A generic helper hides a call's route, and the client does not fetch metadata. |
| MET007 | A client and an API in one program are typed with different APIs. |
| MET008, MET009 | A called route runs a middleware the client never sets up. |
| MET010 | The client fetches metadata, but the API does not add `mionFetchMetadata`. |
| MET011 | The client builds with `client: {routes: 'fetch'}`, but never calls `useFetchMetadata`. |
