Fetch route metadata from the server instead of bundling it in the client.

The client needs a route's metadata to validate and send a call: its param and return types, its options and the functions that validate and serialize them. By default the build bundles it into the client. Use this middleware to keep the bundle small for a large API, or to call your API from a client built without the mion build plugin.

## Getting Route Metadata

The client gets route metadata in one of two ways.

| Mode | How the client gets it | What you set up |
| --- | --- | --- |
| Bundled (default) | The build ships it with the client, for every route the client calls. | Nothing. |
| Fetched | The `mionMethodsMetadata` middleware sends it on a route's first call, and the client saves it. | The middleware in your routes, `useMethodsMetadata` in the client, and `bundleApi: false`. |

## Choosing a Mode

Bundle unless you need something only the fetched mode gives you.

| What Matters | Bundled | Fetched |
| --- | --- | --- |
| Strict Content Security Policy | Works: the client ships ready functions. | Blocked: the client builds functions at runtime with `new Function`. |
| Bundle size | Grows with each route the client calls. | Stays small: no route functions ship. |
| First call to a route | Nothing extra. | Asks the server, then saves the answer for later visits. |
| Browser storage | None. | IndexedDB by default. |
| A new server release changes a route | The client reports a version mismatch until you reload or rebuild it. | The client relearns the route. |
| mion build plugin | Required. | Optional, but a client without it cannot send batches. |

### What the Middleware Answers

Given route ids, it answers with the metadata of each route and of every middleware in that route's chain.

| It describes | It never describes |
| --- | --- |
| Every route | Your handler code |
| Middleware that takes params or headers, or returns data | Raw middleware, and middleware with no params and no return data |
| The compiled validation and serialization functions of those | mion's internal routes |

### Why Metadata Is Public

Any client can ask for any route's metadata, without logging in. A bundled client carries the same metadata in its JavaScript. Treat it like a public API schema: it shows your types, never your data.

::note
Route metadata is not access control. Protect your routes with your own middleware, as usual.
::

### Listing Every Method

A hand-written client can ask for every public method at once. POST this body to any route path, and the route does not run:

```json
{"mionMethodsMetadata": [[], "all"]}
```

The answer lists every public method and the registered [batch](/rpc/client/batch) ids, so the client can call a batch by id.

Past the `getAllRemoteMethodsMaxNumber` router option, the answer has only the ids you sent, no batch ids, and `truncated: true`.

## Frontend

### Bundling the API

Bundling is on by default. The build ships the metadata of every route your client calls. Every build tool takes the same two settings:

| Tool | Turn bundling on or off | API in a separate project |
| --- | --- | --- |
| [Vite plugin](/rpc/devtools/vite#bundled-client) | `bundleApi: true` or `false` | `api: {tsConfig}` |
| [Next.js](/rpc/devtools/nextjs#options) `withMion` | `bundleApi: true` or `false` | `api: {tsConfig}` |
| [mion CLI](/rpc/devtools/cli#compiling-a-bundled-client) | `--bundle-api bundled` or `off` | `--api-tsconfig` |
| tsconfig plugin entry | `bundleApi: true` or `false` | `apiTsconfig` |

::tip
Set the API project when your client and API have separate tsconfigs. The build then reads the route types with the API's own settings, so the client ships the exact functions the server runs.
::

### The First Call

A route's first call goes out right away and asks for the metadata in the same request. The server validates the params and answers with the result and the metadata. The client saves the metadata, so later calls also validate in the browser before sending.

| Case | What the client does |
| --- | --- |
| A body plain JSON cannot write | Fetches the metadata first, then sends the call. |
| A param that needs its type to be written, like a `string \| Date` union | Sends the call once more with the right encoding. The route did not run. |
| `typeErrors()` on a route it has not seen | Fetches the metadata alone. The route does not run. |
| A saved copy that no longer matches the server | Drops the saved copy and sends the call once more. |

::note
The client sends a call again at most once, only when the server could not read or validate the params, and never once a mutation in it succeeded. After the route's own error, a network error, a timeout or an abort, it never sends again.
::

### Saving Fetched Metadata

The client saves what it fetched, per server, so a later visit does not ask again. Pick where with the `storageEngine` client option. Any choice falls back to memory where it cannot open, like on the server or in a browser that blocks IndexedDB.

| `storageEngine` | Where it saves |
| --- | --- |
| `'indexeddb'` (default) | The browser's IndexedDB, kept between visits. |
| `'memory'` | Memory, for this page load or process only. |
| A function | [Your own store](#using-your-own-store). |

<code-import path="packages/private-examples/src/client/methods-metadata-storage.ts" lang="ts [client.ts]" />

::note
Each server's cache holds up to 8 MB and drops its oldest entries first. If the browser still refuses a write, a later call gets a `metadata-cache-error` in its `undeclared` slot, once.
::

::tip
The browser can clear the cache (low disk space, or Safari after 7 days without a visit), and the client then fetches again. `requestPersistentStorage()` asks it to keep the cache; mion never shows a permission popup itself.
::

### API Version Check

The server sends the version of the API it was built from with every response. The client compares it with the version it was built against, so it can tell a new server release.

| Client | On a mismatch |
| --- | --- |
| Without `useMethodsMetadata` | The call that sees it gets an `api-version-mismatch` error in its `undeclared` slot, once per server. |
| With `useMethodsMetadata` | Each route is checked once, on its first call after the mismatch. A changed fetched route is relearned. A changed bundled route gets `api-version-mismatch`, naming the route. |

The call itself still runs. Reload the app or rebuild the client to clear it. To stop such a call before it runs, see [mionSyncRoutes](/rpc/middlewares/mion-sync-routes). To catch a mismatch before you deploy, run [mion api-check](/rpc/devtools/cli#checking-a-client-against-its-server).

::tip
Set `apiVersionCheck: false` in `createMionRouter` to stop sending the version. The client then checks nothing.
::

### Build Checks

The build stops on a setup that would fail at runtime. Look up any code in [All Diagnostics](/runtypes/diagnostics/all-diagnostics).

| Code | When |
| --- | --- |
| MET001 | The client is not typed with `PublicApi<typeof routes>`. |
| MET002 | A call names a route the API type does not declare. |
| MET003 | A call hides its route, and the client does not fetch metadata. |
| MET005 | The API project has no `initRoutes` call, or more than one. |
| MET007 | A client and an API in one program are typed with different APIs. |
| MET008, MET009 | A called route runs a middleware the client never sets up. |
| MET010 | The client fetches metadata, but the API does not add `mionMethodsMetadata`. |
| MET011 | The client builds with `bundleApi: false`, but never calls `useMethodsMetadata`. |
