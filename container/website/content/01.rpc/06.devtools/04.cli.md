`mion compile` runs the same compiler as the Vite plugin, the way `tsc` does: it rewrites your mion calls, emits `.js` files to your tsconfig `outDir`, and writes the generated modules and the batch transport under the gen dir. Use it when a project has no bundler, or when you want plain emitted files.

## Compiling a Server

Run it from the server project. When the client is a separate project, name its tsconfig, like `client.tsConfig` on the Vite plugin. Leave `--client-tsconfig` out when client and server are one project.

```bash
mion compile --tsconfig tsconfig.json --client-tsconfig ../client/tsconfig.json
```

The command reads every `batch([...])` and inline `inputFrom` mapper out of the client program, and adds the batch table's import to the emitted file that calls `createMionRouter`.

## Client Project in tsconfig

The same client pointer can live in your tsconfig, so the flag is only needed when a single build differs:

```json
{
  "compilerOptions": {
    "plugins": [{"name": "mion", "clientTsconfig": "../client/tsconfig.json"}]
  }
}
```

## Compiling a Client

Run it from the client project. The emitted files carry every batch id and inline mapper hash from the same source the server reads, so build order does not matter:

```bash
mion compile --tsconfig tsconfig.json
```

## Compiling a Bundled Client

A client ships the compiled functions of the routes it calls instead of fetching them at runtime (see [Bundling the API Into the Client](/rpc/client/bundled-api)). `bundled` is the default; pass `--bundle-api mixed` or `--bundle-api off` to change it, and the API project's tsconfig when it is a separate project, like `bundleApi` and `api.tsConfig` on the Vite plugin:

```bash
mion compile --tsconfig tsconfig.json --bundle-api bundled --api-tsconfig ../api/tsconfig.json
```

Each emitted route call imports its route's bundled module, and the file that starts the client imports one more module that sets the mode you built.

::note
Both options can live in the tsconfig plugin entry instead, as `bundleApi` (`false` turns it off) and `apiTsconfig`.
::

## Checking a Client Against Its Server

Both compiles write `<genDir>/api/manifest.json`: the server's lists every route it initializes with the ids of its compiled types, the client's lists what it bundled. `mion api-check` compares them:

```bash
mion api-check --server-gen-dir ../api/.mion --client-gen-dir .mion
```

It exits `0` when every bundled route matches the server, `1` with one line per difference (the route, the field, both values), and `2` when a manifest is missing or invalid, or a flag is wrong.

## API Check in CI

`mion api-check` needs no network, only the two build outputs, so it fits any CI job that has both:

```yaml
- run: mion compile --tsconfig api/tsconfig.json --gen-dir api/.mion
- run: mion compile --tsconfig web/tsconfig.json --gen-dir web/.mion --bundle-api bundled --api-tsconfig api/tsconfig.json
- run: mion api-check --server-gen-dir api/.mion --client-gen-dir web/.mion
```

## Output Locations

The gen dir defaults to `.mion` in the directory you run from. Set `genDir` in the tsconfig entry or pass `--gen-dir` to change it. Every import between these files is relative, so the emitted tree runs wherever you deploy it.

| Output | Location |
| --- | --- |
| Emitted `.js` (and source maps when the tsconfig asks for them) | The tsconfig `outDir` |
| Generated validators and serializers | `<genDir>/types/` |
| Batch table and mapper modules (server only) | `<genDir>/rpc/` |
| Bundled route modules (bundled client only) and the manifest (both) | `<genDir>/api/` |

::note
`mion compile --no-emit` checks a project and reports the build diagnostics without writing anything, like `tsc --noEmit`.
::

## Shared Options

Every project option from the [RunTypes configuration](/runtypes/introduction/configuration) works as a kebab-case flag (`--emit-mode`, `--gen-dir`, `--hash-length`). A flag wins over the tsconfig entry, which wins over the default. Run `mion compile -h` for the full list.
