---
title: Linter
description: Lint rules that catch mistakes in mion routes as you write them.
---

mion ships an ESLint plugin with rules that catch common mistakes in mion routes and middleFns. It comes with `@mionjs/devtools`, on the `/eslint` entry, so there is no separate package to install.

The rules come from the mion compiler, the same one that builds your validation and serialization. That is what lets them read your types, so a handler is checked however you wrote it: written straight into the call, passed by name, typed with `Handler`, wrapped in `satisfies`, or tagged with JSDoc.

## Summary

| Rule | Description | Recommended |
|------|-------------|-------------|
| `strong-typed-routes` | Ensures handlers have explicit type annotations | ✅ Error |
| `no-throw-in-handlers` | Refuses a `throw` inside a route or middleFn handler | ✅ Error |
| `returned-error-type` | Refuses a declared error that is not an `RpcError` | ✅ Error |
| `no-unsafe-property-names` | Refuses properties named `__proto__`, `prototype` or `constructor` | ✅ Error |

## Installation

```bash
npm install @mionjs/devtools -D
```

## Configuration

The plugin needs ESLint's flat config (`eslint.config.js`). It is ESM only, so the older
`.eslintrc.json` format cannot load it.

Pick the rules yourself:

```js [eslint.config.js]
import {mionPlugin} from '@mionjs/devtools/eslint';

export default [
  {
    plugins: {'@mionjs': mionPlugin},
    rules: {
      '@mionjs/strong-typed-routes': 'error',
      '@mionjs/no-throw-in-handlers': 'error',
      '@mionjs/returned-error-type': 'error',
      '@mionjs/no-unsafe-property-names': 'error',
    },
  },
];
```

Or use the recommended config, which registers the mion rules together with the type
diagnostics from the compiler (the default export is the compiler's own plugin):

```js [eslint.config.js]
import runtypes from '@mionjs/devtools/eslint';

export default [runtypes.configs.recommended];
```

::note
The rules read your project's `tsconfig.json` from the directory the linter runs in, like your
build does. Point them somewhere else with `settings: {runtypes: {tsconfig: 'tsconfig.lint.json'}}`.
::

## Rules

### `@mionjs/strong-typed-routes`

Ensures that all route and middleFn handlers have explicit type annotations for parameters and return types. This is essential for mion's automatic validation and serialization to work correctly.

#### Why is this important?

mion uses TypeScript types at runtime to generate validation and serialization functions. Without explicit types, mion cannot properly validate incoming data or serialize responses.

The call context is exempt: it never crosses the wire, so it does not need an annotation. Everything after it does.

### `@mionjs/no-throw-in-handlers`

Refuses a `throw` inside a route, query, mutation, middleFn or headersFn handler. Handlers answer with errors instead, so the error stays in the function signature and the client handles it at the call site, strongly typed.

#### Why is this important?

A returned error is part of the contract. A thrown one is not: it lands in the undeclared slot, the client sees only its public message, and the handler's declared return type stops being true. Two return forms cover everything a handler needs.

```ts
return new RpcError({...});   // the client gets it typed, the rest of the chain keeps running
return new FatalError({...}); // the client gets it typed, the request stops here
```

A `throw` caught by a `try` and `catch` inside the same handler never reaches the router, so the rule leaves it alone.

::note
Throwing is still the escape hatch for something nobody declared, such as a bug or an infrastructure failure. When a `throw` is deliberate, silence the rule on that line with `eslint-disable-next-line @mionjs/no-throw-in-handlers` and say why.
::

### `@mionjs/returned-error-type`

Refuses a handler whose declared return type can be an error that is not an `RpcError`. Only `RpcError`, and classes that extend it such as `FatalError` or your own, get a typed slot in the answer.

#### Why is this important?

mion tells your errors apart by a marker it puts on `RpcError`. An error without it has nowhere typed to go, so the router fails the request and drops the error in the undeclared slot instead. The code still compiles, the declared return type just stops being true, and the client never receives the error you promised it.

`TypedError` is refused for a different reason: it is the base class, so it has no public message and no status code, and there would be nothing for the client to show.

### `@mionjs/no-unsafe-property-names`

Refuses a property named `__proto__`, `prototype` or `constructor` in any interface, type literal or class, optional or not, however deeply nested. Those names are never data: every decoder refuses them on the wire, validation refuses them under an index signature, and the build fails for any type a route compiles with one of them. This rule reports the declaration itself, so the problem shows up in the editor before a build, and for types no route reaches yet.

The one way past it is on purpose: a type that describes a real constructor (a cast reaching a class through its `prototype`, say) never crosses the wire, so disable the rule on that line with an `eslint-disable-next-line` comment and leave a note saying why.

#### ✅ Valid Examples

```ts
interface Settings {
  builder: string;
}

class Box {
  size: number;
  constructor(size: number) {
    this.size = size;
  }
}
```

#### ❌ Invalid Examples

```ts
interface Settings {
  constructor: string;
}

type Poison = {
  __proto__: {admin: boolean};
};
```

### Two rules that are gone

**Purity is checked by RunTypes, not mion.** `runtypes/pure-functions` from `@mionjs/devtools/eslint` surfaces the resolver's own diagnostics (`PFE9006` to `PFE9011`, `PFN001` to `PFN002`), the same rules the build enforces. See the [Pure Functions](/runtypes/guide/pure-functions) guide.

**Union order is handled for you.** The compiler orders union members when it builds the validator, so you can write them in any order and a more specific member is never shadowed by a looser one.

## RunTypes compiler rules (`runtypes/*`)

mion's rules above sit alongside the 25 `runtypes/*` rules shipped by `@mionjs/devtools`, which
surface the RunTypes compiler's diagnostics about your types. Both families come from the same
compiler and the same single pass over each file; they are grouped under two names so you can
level them separately.

The recommended config enables them next to mion's, so one entry covers both families:

```js [eslint.config.js]
import runtypes from '@mionjs/devtools/eslint';

export default [runtypes.configs.recommended];
```

### Markers and pure functions

| Rule | What it catches | Recommended |
|------|-----------------|-------------|
| `runtypes/broken-tsconfig` | The tsconfig the linter was pointed at is missing or does not parse, so type-aware linting cannot run | ✅ Error |
| `runtypes/invalid-marker` | A marker the build cannot turn into a function: an unfilled generic, a non-literal options argument, an unresolved import | ✅ Error |
| `runtypes/redundant-marker` | A marker that works but probably does not do what you meant (for example a call made only to read its return type) | ⚠️ Warn |
| `runtypes/pure-functions` | A registered pure function that breaks purity (`this`, `await`, `yield`, dynamic import, blocked globals, outer variables), is double-registered, or is referenced but never registered | ✅ Error |

### Validation

| Rule | What it catches | Recommended |
|------|-----------------|-------------|
| `runtypes/validate-non-serializable` | A type that can never be validated: validators only see the data-only projection | ✅ Error |
| `runtypes/validate-skipped-member` | A member the validator silently skips (function, method, static, symbol) | ⚠️ Warn |
| `runtypes/non-enumerable` | A `@nonEnumerable` property that is not optional, so the tag does nothing and the property always serializes | ⚠️ Warn |
| `runtypes/unknown-keys` | A member the unknown-keys helpers skip | ⚠️ Warn |

### Serialization

| Rule | What it catches | Recommended |
|------|-----------------|-------------|
| `runtypes/json-non-serializable` | A type that can never be encoded to or decoded from JSON | ✅ Error |
| `runtypes/json-skipped-member` | A member the JSON encoder/decoder leaves out | ⚠️ Warn |
| `runtypes/binary-non-serializable` | A type that can never be serialized to or from binary | ✅ Error |
| `runtypes/binary-skipped-member` | A member the binary encoder/decoder leaves out | ⚠️ Warn |
| `runtypes/clone-unsupported-type` | A type `cloneExactShape` cannot clone safely (union of objects, callable root) | ✅ Error |
| `runtypes/clone-shared-reference` | A member the clone cannot rebuild, so both copies point at the same value | ⚠️ Warn |
| `runtypes/unsafe-property-name` | A type a marker compiles that declares `__proto__`, `prototype` or `constructor` | ✅ Error |

### Formats and overrides

| Rule | What it catches | Recommended |
|------|-----------------|-------------|
| `runtypes/format` | A custom string format with a broken definition (a sample that fails its own pattern, invalid params, an uncompilable regex) | ✅ Error |
| `runtypes/invalid-override` | The same (type, function) pair registered twice, or a redirect to a module that does not exist | ✅ Error |
| `runtypes/override-side-effect` | A `validate` override that also changes the JSON/binary union decoders, which run validation internally | ⚠️ Warn |
| `runtypes/other` | Any other compiler diagnostic, reached when a locally built binary runs ahead of the message catalog | ✅ Error |

### Generated enrichment files (FriendlyText / MockData)

| Rule | What it catches | Recommended |
|------|-----------------|-------------|
| `runtypes/no-enrichment-todo` | An unfilled `@todo` placeholder the generator scaffolded | ⚠️ Warn |
| `runtypes/no-orphan-carcass` | A commented-out `@rtOrphan` block left behind when a type or field disappeared | ⚠️ Warn |
| `runtypes/enrichment-field` | An entry that no longer matches its type: an unknown field, or a property colliding with the reserved `rt$` prefix | ✅ Error |
| `runtypes/enrichment-message` | A message template with an undeclared error key, an unknown `$[placeholder]`, an invalid plural arm, or a plural missing its `other` arm | ⚠️ Warn |
| `runtypes/enrichment-broken-source` | A generated mirror whose source file or type is gone | ✅ Error |
| `runtypes/enrichment-misplaced-file` | A generated mirror that is no longer where the generator would write it | ⚠️ Warn |

::note
The `error` severities above are `@mionjs/devtools`' own defaults and mion keeps them as-is: every
one of them marks output that is **wrong or impossible to generate**, not a style preference, so
finding out at build time is the point. The `warn` rules describe something that still works,
whether it drops data silently or is only untidy. Worth reading, not worth blocking on.

A rule's severity here is what your editor shows, which is not always what your build does. A rule
can sit at `error` while its findings are only Warnings to the build (`enrichment-field` is exactly
that: a dead map entry deserves a squiggle without stopping a build). It never goes the other way:
a rule that can report an Error or a RuntimeError is always `error`. See
[Diagnostics](/runtypes/diagnostics/error-levels#the-three-levels).
::

::note
Every rule on this page is in the recommended config, at the severity its table shows.
::
