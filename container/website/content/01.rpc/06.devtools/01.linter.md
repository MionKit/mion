`@mionjs/devtools/eslint` is a lint plugin for OXlint and ESLint that catches mistakes in mion routes, middleware and types as you write them. It ships inside `@mionjs/devtools`.

The rules use the mion compiler that builds your validation and serialization, so they read your types. A handler is checked however you write it: inline, passed by name, typed with `Handler`, wrapped in `satisfies`, or tagged with JSDoc.

## Lint Rules

The plugin has one rule per [level](/runtypes/diagnostics/error-levels), and each message starts with its code, like `[MRT001]`. The route checks below and the [RunTypes checks](/runtypes/tooling/linting) both report through them.

| Rule | What it reports | Recommended |
|------|-----------------|-------------|
| `mion/error` | Every Error: no code was made, so the build stops | ✅ Error |
| `mion/runtime-error` | Every RuntimeError: the code throws when called, or no longer checks what you asked for, so the build stops | ✅ Error |
| `mion/warning` | Every Warning, and every error you lowered | ⚠️ Warn |
| `mion/info` | Every Info message: documented behaviour or advice | Off |
| `mion/enforce-type-imports` | A value import from backend code, so server code stays out of the frontend bundle | Off, needs a `backendSources` option |

::tip
Unlike `mion/enforce-type-imports`, the four level rules are the same in every app and cannot turn a single check on or off. To allow one error, add a `@mion-expect-error` comment above it or lower its code in your tsconfig: your editor and your build both follow it.
::

## Installing the Plugin

```bash
npm install @mionjs/devtools -D
```

## Recommended Config

The recommended config turns on the four level rules. The plugin is ESM only, so ESLint needs its flat config (`eslint.config.js`), not `.eslintrc.json`. The [RunTypes linting page](/runtypes/tooling/linting#lint-plugin-setup) shows the OXlint config.

```js [eslint.config.js]
import mion from '@mionjs/devtools/eslint';

export default [mion.configs.recommended];
```

::note
The rules find `tsconfig.json` the way tsc does, from the directory the linter runs in. Point them at another file
with `settings: {mion: {tsconfig: 'tsconfig.lint.json'}}`.
::

## Showing Info Messages

The linter hides Info messages, which mark code that works as documented: a method a validator skips,
a validator on a type you wrote as `any`. Turn on `mion/info` to show them.

```js [eslint.config.js]
import mion from '@mionjs/devtools/eslint';

export default [mion.configs.recommended, {rules: {'mion/info': 'warn'}}];
```

## Route Checks

### Typed Handlers

`MRT001` and `MRT002` report a route or middleware handler without explicit return or parameter types. mion builds validation and serialization from those types, so without them it cannot check incoming data or serialize responses. Only the call context needs no type, since it is never sent over the network.

### Returning Errors Instead of Throwing

`MRT003` reports a `throw` that escapes a route, query, mutation, middleware or headersFn handler. A returned error stays in the signature, so the client gets it typed. A thrown one goes to the undeclared slot, the client sees only its public message, and the declared return type is no longer true.

```ts
return new RpcError({...});   // the client gets it typed, the rest of the chain keeps running
return new FatalError({...}); // the client gets it typed, the request stops here
```

::note
A `throw` is still the way out for an error nobody declared, such as a bug or an infrastructure failure. Add `// @mion-expect-error MRT003` on the line above it, and a comment saying why.
::

### Returned Error Types

`MRT004` reports a handler whose declared return type can be an error that is not an `RpcError`. Only `RpcError` and its subclasses, such as `FatalError` or your own, get a typed slot in the response. Any other error fails the request and goes to the undeclared slot, so the code compiles but the client never gets the error its type promised.

### Unsafe Property Names

`MRT005` reports a property named `__proto__` in any interface, type literal or class, optional or not, at any depth. Writing that key on a plain object changes its prototype instead of storing a value, so every compiled function drops the member and its value is lost. TypeScript accepts it, so the linter reports the declaration in your editor, even for types no route uses yet.

It allows `prototype` and `constructor`.

#### ✅ Valid Examples

```ts
interface Settings {
  builder: string;
  constructor: string;
  prototype: string;
}

class Box {
  size: number;
  constructor(size: number) {
    this.size = size;
  }
}
```

#### ❌ Invalid Examples

```ts
interface Settings {
  __proto__: string;
}

type Poison = {
  __proto__: {admin: boolean};
};
```
