mion resolves your types at build time, so the transform has to run wherever your code is
compiled. In a Next.js app that is Next itself, and `withMion` wires it up in one line.

<code-import path="packages/examples/src/codegen/next-config.ts" lang="ts [next.config.ts]" />

The `await` is required. The whole-program scan has to finish before the bundler starts
handing files over, and there is no later point to wait at.

That is the whole setup. Your front end gets the same compiled validators and serializers
the rest of mion uses, from the same types.

## Turbopack and webpack

`withMion` picks the right road for you.

Turbopack has no plugin API, so mion does not use one. Your `next.config` runs before any
bundler worker exists, so mion starts a small background process there that holds the type
resolver, then registers a loader that asks it to rewrite each file. You do not configure
any of that.

Running `next --webpack` instead? mion detects it and uses the ordinary webpack plugin. Same
result, nothing to change.

Only your own TypeScript is rewritten. Files in `node_modules` are left alone.

## Hosting the API in Your Next App

Your Next app can serve the mion API itself, with no second server and no proxy. Add a catch-all
route handler that imports your routes module and re-exports the handlers
[@mionjs/platform-vercel](/rpc/platforms/vercel) builds from them:

<code-import path="packages/examples/src/codegen/next-route-handler.ts" lang="ts [app/api/[...mion]/route.ts]" />

That file is rewritten like any other TypeScript in the app, so your routes get their compiled
validators and serializers from the same build as your components. Point your client at `/api`:

```ts
const {routes} = initClient<MyApi>({baseURL: '/api'});
```

One app, one program, one deployment. It is also the deployment shape Vercel expects, so nothing
changes when you ship it.

## Sharing Batches With Your API

If your client sends [batches](/rpc/client/batch), the build has to know them, and where that
happens depends on where your API lives.

**API in this app.** Nothing to configure. The app is one program, so the same build reads your
batches and compiles them into the route handler.

**API in a separate project.** This app is the client half and it needs nothing either: the
transform gives every batch its id and every inline `inputFrom` mapper its hash. The API's own
build generates the batch table and the mapper modules from this app's program. Point its Vite
config at this app's tsconfig:

<code-import path="packages/examples/src/codegen/vite-server.config.ts" lang="ts [api vite.config.ts]" />

See [Batch Transport](/rpc/devtools/vite#batch-transport). Nothing is written from here, and
there is no build order to keep.

## Editing types while the dev server runs

Edit a type in one file and every file that reflects it recompiles, including types declared
in a `.d.ts` with no import to follow. mion tells the bundler what each rewrite depends on,
so `next dev` stays correct without a restart.

## Options

`withMion` takes the same `runTypes` block and the same `client` pointer as the Vite plugin, so
[Vite Configuration](/rpc/devtools/vite) is the reference for every knob. The `client` pointer is
only for a Next app that hosts the mion API and serves batches to a **separate** client project.

Two Vite options have no meaning here and are not accepted: the Vue single file component pass
and the `server` block. Next runs its own dev server and builds your API route with everything
else, so there is nothing for mion to mount or to emit.
