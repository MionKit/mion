The `mionVitePlugin` from `@mionjs/devtools/vite` is the single Vite plugin behind mion's build-time features: mion type compilation (validation & serialization), the batch transport, and (for fullstack setups) running your mion API **inside the Vite dev server**.

## Plugin Options

```typescript
import {mionVitePlugin} from '@mionjs/devtools/vite';

mionVitePlugin({
    // mion type compilation: rewrites route()/createValidate()/... call sites with the
    // precompiled validation & serialization functions at build time.
    // Required for mion's validation and serialization.
    runTypes?: {
        tsConfig?: string;                // Path to tsconfig.json (auto-discovered by default)
        genDir?: string;                  // Generated-output root (default: <srcDir>/.mion)
        emitMode?: 'code' | 'both';       // What generated fn entries ship (default: 'code').
                                          // MUST be 'both' on edge runtimes (Cloudflare Workers,
                                          // Vercel Edge): 'code' compiles fns with `new Function`
                                          // on first use, which those runtimes forbid.
        failOnError?: boolean;            // Halt the build on Error-severity diagnostics (default: true)
        patternSampleCount?: number;      // mockSamples generated per pattern that declares none
        patternSampleRetries?: number;    // Generation retries before failing with FMT005
        jsRuntime?: string;               // Runtime for the pattern-check sidecar (node/bun auto-detected)
        sfc?: boolean;                    // Transform typed code in Vue SFC <script> blocks (default: true)
    },

    // The mion API behind this Vite run: where the batch transport writes its generated module
    // (the API's project root), and, in dev, how the API runs. Either mounted INSIDE the Vite dev
    // server ('middleware', the default) or spawned beside it with vite-node ('childProcess').
    server?: {
        startScript: string;              // Absolute path to the server entry script (required)
        runMode?: 'middleware'            // default: API runs in this Vite process
               | 'childProcess';          //          separate process + port, awaited via serverReady

        // middleware mode
        basePath?: string;                // Mount prefix (default: the router's own basePath)
        platform?: string;                // Adapter module (default: '@mionjs/platform-node')
        exclude?: RegExp[];               // With no basePath: paths left to Vite (assets, /@vite/…)
        hotReload?: boolean;              // Re-load the API on source changes (default: true)

        // childProcess mode
        viteConfig?: string;              // Server's vite config for vite-node (auto-discovered)
        waitTimeout?: number;             // Max ms to wait for the server port (default: 30000)
        env?: Record<string, string>;     // Extra env vars for the server process
    },
});
```

::note
The legacy `serverPureFunctions` and `aotCaches` options, and `runTypes.compilerOptions` / `include` / `exclude` / `reflectionMode`, are **removed**. Passing any of them now fails the build with a message naming the replacement. Delete them: build-time compilation is always on, the batch transport is automatic (the `batches` option is gone too, see below), and scan scope comes from your tsconfig. `server.runMode: 'buildOnly'` is gone too (it was the AOT harvest mode) and passing it now throws.
::

### Batch Transport

A [batch](/rpc/client/batch) is written in **client** code, but the server must know it: the build gives every `batch([...])` call site an id from its routes and mappings, and the server runs only the ids it knows. The plugin moves that table, plus every inline `inputFrom` mapper, across the two builds with no option:

- The **client** build writes one generated module, `.mion/rpc/batches.generated.js`, into the server's project root. With client and server in one project that is the shared root. With a separate API project, the `server` block (`startScript`, or better `viteConfig`) names it.
- The **server** build imports that module from whichever module calls `initMionRouter`. You write nothing. In `vite build` the table is inlined as static data and each mapper's generated module is bundled in, so no `node:fs` ends up in the artifact and it stays edge/lambda-safe.
- The module carries a checksum of its batch ids. The server side recomputes it before importing, and a mismatch (an edited or corrupted file) fails the build. A module that exists but is imported nowhere fails the build too, since the artifact would silently lack its batches.
- In dev the server entry imports the module, so a client rewrite is an ordinary file change and the API reloads the new table. The old table is dropped in full on every load.

::note
A batch the build cannot read (a spread, a route from a function parameter, a mapper it cannot trace) fails the build, because a batch without an id can never be sent.
::

### Fullstack (Nuxt / SSR / "backend of a frontend")

The default. Your API is loaded into **this** Vite process through Vite's own SSR pipeline (`ssrLoadModule`) and mounted as dev-server middleware: one process, one port, one module graph. The frontend calls `/api/...` on the same origin it is served from: no proxy, no second server to start, and the API is transformed by the same plugin the app is.

Your server entry needs no changes. Before it runs, the plugin tells the platform adapter that the host owns the socket (`asMiddleware`), so an ordinary `initMionRouter(); startNodeServer();` entry registers its routes without opening a port. Batches need nothing either: the client half of this same run writes the batch module into this root, the entry imports it, and a batch edit reloads the API like any other change.

<code-import path="packages/examples/src/codegen/vite-middleware.config.ts" lang="ts [Client + in-process API]" />

What reaches mion is decided by the router's `basePath`, matched on a path boundary, so `/api` never swallows `/apidocs`. With no `basePath` mion serves the root and `exclude` keeps Vite's own URLs (`/@vite/...`, assets, HMR pings); extend `DEFAULT_MIDDLEWARE_EXCLUDE` rather than replacing it. Editing a route file re-loads the API on the next request (`hotReload: false` to opt out), and a failed load answers `503` with the real cause instead of a blank page.

Using a fetch-based adapter (`@mionjs/platform-bun`, or an edge handler you want to exercise in dev)? Point `server.platform` at it. Vite's middleware layer is Node `req`/`res` in every runtime, so mion bridges the two for you.

### Separate server process (e2e / client tests)

When the client tests need a real socket, a server on its own port, in its own process. `runMode: 'childProcess'` spawns it with vite-node and `serverReady` resolves once the port accepts connections, so a Vitest `globalSetup` can await it. It is not needed to compile types: route validation and serialization metadata is derived from the router types at build time.

### Vue / Nuxt (SFC support)

Typed mion code inside a `.vue` `<script>` (`createValidate*`, `batch`, `inputFrom`, any call the plugin compiles) is transformed like code in a `.ts` file. Nothing to configure: keep `@vitejs/plugin-vue` in the same config and the mion plugin handles the SFC's script for you, `<script setup>` and classic `<script>` alike (including a type declared in one block and used in the other).

The types a marker reflects must live somewhere TypeScript can resolve: a `.ts`/`.d.ts` file or a package. A type imported **from another `.vue`** cannot be resolved by the type scanner, so the build stops with `MKR007` naming that import rather than shipping a validator that silently accepts anything.

::note
`runTypes: {sfc: false}` turns the SFC pass off. The plugin still warns when an SFC ships a marker with no compiled functions. That combination fails at runtime, so it is never silent.
::

### Client Without the Plugin

A client can run without the mion plugin: it fetches validation and serialization metadata from the server at runtime, so single route calls need no build step. It cannot send a [batch](/rpc/client/batch), since batch ids only exist when the build injects them, and `batch()` throws `batch-missing-id`. Add the plugin to the client build when your client uses batches.

## ESLint Rules

mion provides an ESLint plugin with rules to catch common mistakes with type imports, route typing, and pure functions. See the [ESLint Rules](./linter) page for full documentation.

```json [.eslintrc.json]
{
  "extends": ["plugin:@mionjs/recommended"]
}
```
