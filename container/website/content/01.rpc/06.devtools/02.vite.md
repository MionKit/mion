The `mionVitePlugin` from `@mionjs/devtools/vite` is the single Vite plugin behind mion's build-time features: mion type compilation (validation & serialization), the batch transport, and (for fullstack setups) running your mion API **inside the Vite dev server**.

## Plugin Options

```typescript
import {mionVitePlugin} from '@mionjs/devtools/vite';

mionVitePlugin({
    // mion type compilation: rewrites mion.route()/createValidate()/... call sites with the
    // precompiled validation & serialization functions at build time.
    // Required for mion's validation and serialization.
    runTypes?: {
        tsConfig?: string;                // Path to tsconfig.json (auto-discovered by default)
        genDir?: string;                  // Generated-output root (default: <srcDir>/.mion)
        emitMode?: 'code' | 'both';       // What generated fn entries ship (default: 'code').
                                          // MUST be 'both' on edge runtimes (Cloudflare Workers,
                                          // Vercel Edge): 'code' compiles fns with `new Function`
                                          // on first use, which those runtimes forbid.
        downgradeErrors?: string[] | '*'; // Report these codes as warnings instead of halting (default: none)
        patternSampleCount?: number;      // mockSamples generated per pattern that declares none
        patternSampleRetries?: number;    // Generation retries before failing with FMT005
        jsRuntime?: string;               // Runtime for the pattern-check sidecar (node/bun auto-detected)
        sfc?: boolean;                    // Transform typed code in Vue SFC <script> blocks (default: true)
    },

    // A SEPARATE client project this API serves batches to. The build reads every batch() and
    // inline inputFrom mapper out of it and generates the batch transport under this project's
    // genDir. Leave it out when client and API share one project (they are one program then).
    client?: {
        tsConfig: string;                 // The client project's tsconfig (absolute, or relative to the Vite root)
    },

    // The mion API this Vite run hosts. In `vite dev` it is mounted INSIDE the Vite process,
    // and `build` adds it to `vite build` as a second bundle. One process, one program.
    // An API that is started on its own never sets this.
    server?: {
        startScript: string;              // Absolute path to the server entry script (required)

        // build: opt in to the second bundle
        build?: {
            outDir?: string;              // Where the API bundle lands (default: 'dist-server')
        },

        // dev server
        basePath?: string;                // Mount prefix (default: the router's own basePath)
        platform?: string;                // Adapter module (default: '@mionjs/platform-node')
        exclude?: RegExp[];               // With no basePath: paths left to Vite (assets, /@vite/…)
        hotReload?: boolean;              // Re-load the API on source changes (default: true)
    },
});
```

::note
The legacy `serverPureFunctions` and `aotCaches` options, and `runTypes.compilerOptions` / `include` / `exclude` / `reflectionMode`, are **removed**. Passing any of them now fails the build with a message naming the replacement. Delete them: build-time compilation is always on, the batch transport is automatic (the `batches` option is gone too, see below), and scan scope comes from your tsconfig.
::

### Batch Transport

A [batch](/rpc/client/batch) is written in **client** code, but the server must know it: the build gives every `batch([...])` call site an id from its routes and mappings, and the server runs only the ids it knows. The **server** build produces that knowledge itself, with no option:

- Its build reads every `batch([...])` call and every inline `inputFrom` mapper out of the client program (its own program, or the project `client.tsConfig` names) and writes one folder under its gen dir, `.mion/rpc/`: the batch table (`batches.generated.js`) plus one module per inline mapper, with relative imports only. Nothing is written into another project, and no path leaks into a generated file.
- The same build appends the table's import to whichever module calls `createMionRouter`. You write nothing. In `vite build` the table is inlined as static data and each mapper module is bundled in, so no `node:fs` ends up in the artifact and it stays edge and lambda safe.
- With client and API in one project, the program itself is the batch source. With a separate client project, `client.tsConfig` names it, and the API's dev server watches that whole project, so a client edit, a new client file or a deleted one regenerates the table and reloads the API. Batches written in the API's own program are then left out, and the build says so (BAT008).
- The client build needs nothing: its own transform gives each batch its id and each mapper its hash, from the same source the server reads, so the two sides agree without a build order.

The [CLI](/rpc/devtools/cli) generates the same folder with `mion compile`, since both lanes run the same compiler.

::note
A batch the build cannot read (a spread, a route from a function parameter, a mapper it cannot trace) fails the build, because a batch without an id can never be sent.
::

### Fullstack (Nuxt / SSR / "backend of a frontend")

In dev, your API is loaded into **this** Vite process through Vite's own SSR pipeline (`ssrLoadModule`) and mounted as dev-server middleware: one process, one port, one module graph. The frontend calls `/api/...` on the same origin it is served from, and the API is transformed by the same plugin the app is.

Your server entry needs no changes. Before it runs, the plugin tells the platform adapter that the host owns the socket (`asMiddleware`), so an ordinary `mion.initRoutes(routes); startNodeServer();` entry registers its routes without opening a port. Batches need nothing either: client and API are one program, so the build generates the batch table from it, the entry imports it, and a batch edit reloads the API like any other change.

<code-import path="packages/examples/src/codegen/vite-middleware.config.ts" lang="ts [Client + in-process API]" />

What reaches mion is decided by the router's `basePath`, matched on a path boundary, so `/api` never swallows `/apidocs`. With no `basePath` mion serves the root and `exclude` keeps Vite's own URLs (`/@vite/...`, assets, HMR pings); extend `DEFAULT_MIDDLEWARE_EXCLUDE` rather than replacing it. Editing a route file re-loads the API on the next request (`hotReload: false` to opt out), and a failed load answers `503` with the real cause instead of a blank page.

Using a fetch-based adapter (`@mionjs/platform-bun`, or an edge handler you want to exercise in dev)? Point `server.platform` at it. Vite's middleware layer is Node `req`/`res` in every runtime, so mion bridges the two for you.

### One Config, Two Bundles

Set `server.build` and one `vite build` emits both halves of your app: the static client files in `build.outDir` (default `dist`), and your API in `server.build.outDir` (default `dist-server`). That is the shape mion targets in production, static files on a CDN plus an ordinary API server, and it comes out of the same config the dev server uses.

<code-import path="packages/examples/src/codegen/vite-client.config.ts" lang="ts [vite.config.ts]" />

Both bundles are built from one program by one type resolver, so a type shared between your client and your API is compiled once and cannot drift between them. Leave `server.build` out and the build is untouched: only the client half is emitted.

::tip
Building a standalone API with no client of its own? Leave the `server` block out entirely and use a plain library build. See [Server](#server) above.
::

### Client Tests

Tests that need a real socket start the API themselves, in the same process, from a Vitest `globalSetup`. Nothing is spawned and no port is polled: your entry's start function resolves once the socket is listening, and `teardown` closes it again.

<code-import path="packages/examples/src/codegen/vite-vitest-global-setup.ts" lang="ts [globalSetup.ts]" />

This keeps client and API in one program, which is what lets the build read the batches your tests write and compile them into the API they run against.

### Vue / Nuxt (SFC support)

Typed mion code inside a `.vue` `<script>` (`createValidate*`, `batch`, `inputFrom`, any call the plugin compiles) is transformed like code in a `.ts` file. Nothing to configure: keep `@vitejs/plugin-vue` in the same config and the mion plugin handles the SFC's script for you, `<script setup>` and classic `<script>` alike (including a type declared in one block and used in the other).

The types a marker reflects must live somewhere TypeScript can resolve: a `.ts`/`.d.ts` file or a package. A type imported **from another `.vue`** cannot be resolved by the type scanner, so the build stops with `MKR007` naming that import rather than shipping a validator that silently accepts anything.

::note
`runTypes: {sfc: false}` turns the SFC pass off. The plugin still warns when an SFC ships a marker with no compiled functions. That combination fails at runtime, so it is never silent.
::

### Client Without the Plugin

A client can run without the mion plugin: it fetches validation and serialization metadata from the server at runtime, so single route calls need no build step. It cannot send a [batch](/rpc/client/batch), since batch ids only exist when the build injects them, and `batch()` throws `batch-missing-id`. Add the plugin to the client build when your client uses batches.

## ESLint Rules

mion provides an ESLint plugin with rules to catch common mistakes with type imports, route typing, and pure functions. See the [ESLint Rules](./linter) page for full documentation.

```json [.eslintrc.json]
{
  "extends": ["plugin:@mionjs/recommended"]
}
```
