`mionVitePlugin` from `@mionjs/devtools/vite` is the one Vite plugin for mion's build-time features: compiling validation and serialization, the batch transport, and, for fullstack apps, running your API **inside the Vite dev server**.

## Plugin Options

```typescript
import {mionVitePlugin} from '@mionjs/devtools/vite';

mionVitePlugin({
    // Build-time compilation of validation and serialization
    runTypes?: {
        tsConfig?: string;                // Path to tsconfig.json (auto-discovered by default)
        genDir?: string;                  // Generated-output root (default: <srcDir>/.mion)
        emitMode?: 'code' | 'both';       // What generated functions ship (default: 'code'). MUST be 'both' on edge
                                          // runtimes (Cloudflare Workers, Vercel Edge), which forbid the
                                          // `new Function` that 'code' runs on first use.
        downgradeErrors?: string[] | '*'; // Report these RuntimeError codes as warnings instead of halting (default: none)
        patternSampleCount?: number;      // mockSamples generated per pattern that declares none
        patternSampleRetries?: number;    // Generation retries before failing with FMT005
        derivedPayloadLimits?: boolean;   // Derive per-route size limits from the types (default: true)
        jsRuntime?: string;               // Runtime for the pattern-check sidecar (node/bun auto-detected)
        sfc?: boolean;                    // Transform typed code in Vue SFC <script> blocks (default: true)
    },

    // A SEPARATE client project this API serves batches to (see Batch Transport). Leave it out when
    // client and API share one project.
    client?: {
        tsConfig: string;                 // The client project's tsconfig (absolute, or relative to the Vite root)
    },

    // Bundle metadata and compiled functions for the routes this client calls, so they need no request
    // and no code built at runtime. 'bundled' (default) covers every route the client calls; 'mixed' still
    // fetches a route the build could not see; false fetches every route (both need useMethodsMetadata).
    bundleApi?: 'bundled' | 'mixed' | false;

    // The SEPARATE API project this client calls. With bundleApi on, route types resolve there, so the
    // client ships the server's exact functions. Leave it out when client and API share one project.
    api?: {
        tsConfig: string;                 // The API project's tsconfig (absolute, or relative to the Vite root)
    },

    // The mion API this Vite run hosts: mounted INSIDE `vite dev`, and a second `vite build` bundle
    // with `build` set. Leave it out for an API started on its own.
    server?: {
        startScript: string;              // Absolute path to the server entry script (required)

        // build: opt in to the second bundle
        build?: {
            outDir?: string;              // Where the API bundle lands (default: 'dist-server')
        },

        // dev server
        basePath?: string;                // Mount prefix (default: the router's own basePath)
        platform?: string;                // Adapter module (default: '@mionjs/platform-node')
        exclude?: RegExp[];               // With no basePath: paths left to Vite (assets, /@vite/…)
        hotReload?: boolean;              // Re-load the API on source changes (default: true)
    },
});
```

::note
Build-time compilation is always on, the batch transport is automatic, and scan scope comes from your tsconfig, so none of the three has an option here.
::

### Batch Transport

A [batch](/rpc/client/batch) is written in **client** code, but the server runs only the batch ids it knows. The build gives each `batch([...])` call an id from its routes and mappings, and the **server** build collects them itself, with no option:

- It reads every `batch([...])` call and inline `inputFrom` mapper from the client program (its own, or the project `client.tsConfig` names). It writes the batch table (`batches.generated.js`) and one module per inline mapper to `.mion/rpc/` in its own gen dir, never into another project.
- It adds the table's import to the module that calls `createMionRouter`, so you write nothing. `vite build` inlines the table and bundles each mapper, so the output has no `node:fs` and stays edge and lambda safe.
- With a separate client project, the API's dev server watches that whole project: editing, adding or deleting a client file regenerates the table and reloads the API. A batch written in the API's own program is not in that table, so the build fails with BAT008, naming each one. Move it into the client project, or drop `client.tsConfig` when client and API are one program.
- The client build needs nothing: it gives each batch its id and each mapper its hash from the same source, so the two sides agree in any build order.

`mion compile` in the [CLI](/rpc/devtools/cli) generates the same folder.

::note
A batch the build cannot read (a spread, a route from a function parameter, a mapper it cannot trace) fails the build, because a batch without an id can never be sent.
::

### Fullstack Apps

For a fullstack app (Nuxt, SSR, a frontend's own backend), `vite dev` mounts your API in **this** Vite process as dev-server middleware: one process, one port, one module graph. The frontend calls `/api/...` on the origin it is served from.

Your server entry needs no changes: the plugin sets `asMiddleware` on the platform adapter first, so `mion.initRoutes(routes); startNodeServer();` registers its routes without opening a port. Batches need nothing either: client and API are one program, and a batch edit reloads the API like any other change.

<code-import path="packages/private-examples/src/codegen/vite-middleware.config.ts" lang="ts [Client + in-process API]" />

The router's `basePath` decides what reaches mion, matched on a path boundary, so `/api` never catches `/apidocs`. With no `basePath`, mion serves the root and `exclude` leaves Vite's own URLs (`/@vite/...`, assets, HMR pings) to Vite; extend `DEFAULT_MIDDLEWARE_EXCLUDE` rather than replace it. Editing a route file reloads the API on the next request, and a failed load answers `503` with the real cause instead of a blank page.

For a fetch-based adapter (`@mionjs/platform-bun`, or an edge handler you want to test in dev), set `server.platform` to it. mion bridges it to Vite's Node `req`/`res` in every runtime.

### One Config, Two Bundles

Set `server.build` and one `vite build` emits the static client files in `build.outDir` (default `dist`) and your API in `server.build.outDir` (default `dist-server`). That is mion's production shape, static files on a CDN plus an API server, from the same config the dev server uses.

<code-import path="packages/private-examples/src/codegen/vite-client.config.ts" lang="ts [vite.config.ts]" />

Both bundles come from one program, so a type shared by client and API is compiled once and cannot drift.

::tip
For a standalone API with no client, leave out the `server` block and use a plain library build, as in [Server-Only Builds](#server-only-builds).
::

### Vue Single-File Components

Typed mion code in a `.vue` `<script>` (`createValidate*`, `batch`, `inputFrom`, any call the plugin compiles) is compiled like code in a `.ts` file. Keep `@vitejs/plugin-vue` in the same config; `<script setup>` and classic `<script>` both work, even with a type declared in one and used in the other.

The types a marker reads must live in a `.ts` or `.d.ts` file or a package. A type imported **from another `.vue`** file cannot be resolved, so the build stops with `MKR007` naming that import.

::note
`runTypes: {sfc: false}` turns this off. The plugin still warns when a `.vue` file ships a marker with no compiled functions, since that fails at runtime.
::

### Bundled Client

`bundleApi` bundles every route the client calls, and `api.tsConfig` resolves those route types in the API project. The bundled modules go under `.mion/api/`. See [Bundling the API Into the Client](/rpc/client/bundled-api) for the modes and the release check.

### Client Without the Plugin

Without the plugin, a client fetches validation and serialization metadata from the server at runtime, so single route calls need no build step once you set up `useMethodsMetadata` (see [Setting Up Metadata Fetching](/rpc/client/metadata-cache#setting-up-metadata-fetching)). It cannot send a [batch](/rpc/client/batch): batch ids come from the build, so `batch()` throws `batch-missing-id`. Add the plugin to the client build when your client uses batches.
