One package per database gives you the [Drizzle ORM](https://orm.drizzle.team) table functions for that database, with the same names, parameters, modifier chains, indexes and constraints. You write your tables exactly as you would with drizzle.

| Database | Package |
|----------|---------|
| PostgreSQL | `@mionjs/drizzle-orm-pg-core` |
| MySQL | `@mionjs/drizzle-orm-mysql-core` |
| SQLite | `@mionjs/drizzle-orm-sqlite-core` |
| Cloudflare D1, Durable Objects | `@mionjs/drizzle-orm-sqlite-core` |

Cloudflare's two databases are both SQLite, so they use the SQLite package and only change the driver: see [Cloudflare D1 and Durable Objects](/rpc/drizzle-orm/cloudflare-storage).

Package versions follow drizzle-orm, not mion: version 0.45.x works with drizzle-orm 0.45.x and declares that range as a peer dependency. Pick the version that matches your drizzle-orm. A new version ships only when the package changes, so one version can stay current across several mion releases.

Install the database package with its shared core. drizzle-orm is an optional peer: your schema, models and validators work without it.

```bash
npm install @mionjs/drizzle-orm-pg-core @mionjs/drizzle-orm @mionjs/run-types
npm install drizzle-orm   # only needed to run queries or migrations
```

Drizzle's own table types are heavy and drop most column parameters (a varchar length, whether an int is unsigned). These builders record your calls instead of running drizzle. Their types carry the matching format type from `@mionjs/run-types/formats` with the parameters you wrote, plus the not-null and default flags. Inferred models are small flat types, so editors stay fast.

## Writing a Table as a Type

Any table can also be written as a type. Each column builder has a column type of the same name, first letter uppercased. It takes the database column name, then one object with the builder's config keys and the modifiers you would chain: `Varchar<'name', {length: 100; notNull: true}>` matches `varchar('name', {length: 100}).notNull()`.

A modifier with no arguments is `true`, one with arguments is its argument list: `{primaryKey: true}` for `.primaryKey()`, `{default: [21]}` for `.default(21)`. Both forms give the same models, validators and recorded table, so you can mix them per table. `mion convert` translates a table between the two forms in either direction.

## Building the Drizzle Table

pgTable returns a recorded table, not drizzle's table type. `toDrizzle` builds the real drizzle table from it on the first call and returns the same object after that. It is the one place drizzle runs, so drizzle's heavy types stay in the files that run queries, out of your routes and your client. For a table written as a type, `toDrizzle<UsersTable>()` builds the same table from the type alone, so a query file imports nothing else from the schema file.

## Recorded Tables From a Type

Where you need the recorded table without drizzle (models, refinement, mion routes), use `tableFromType<UsersTable>()` from the package root. Its options take the two runtime inputs a type cannot hold: the tables a column References (`{tables: {parents: parents}}`, or `{tables: {parents: () => parents}}` when that table is declared further down the file) and the runtime callbacks described below.

## Refining Tables for Your API

`refineTableType` adds API rules stricter than the database column: a name that holds 100 characters can require at least 10. It returns the same table object with the extra format parameters merged into the captured ones, and the SQL does not change. Build validators, mock data and JSON serializers from the refined models, with or without mion.

A refinement that does not fit the column is a compile error, never a silent override: a number rule on a string column, an unknown parameter, or a change to whether the column accepts null (that stays with notNull on the table). Columns without a format (booleans, JSON, enums) cannot be refined.

## Refined Table Types

`RefinedTable` does the same refinement as a type, with no table value: it takes the table type and the per-column rules, so a types-only file can export the API view of a table.

```ts
import type {RefinedTable} from '@mionjs/drizzle-orm';
import type {UsersTable} from './schema.ts';

type ApiUsersTable = RefinedTable<UsersTable, {name: {minLength: 10}; age: {min: 18}}>;
```

## Runtime Column Callbacks

Drizzle's `$default`, `$defaultFn`, `$onUpdate` and `$onUpdateFn` take a function your app runs on insert or update. Builder tables chain them as usual. A type cannot hold a function, so a table type sets a prop of the same name on the column (`$defaultFn: true` for `.$defaultFn(...)`, and so on) and the callback goes in the `runtime` option of tableFromType or toDrizzle. A column with any of these props counts as having a default, so it is optional on insert, even in files that only import the type.

## Custom JSON Types

Columns with no matching format (geometry, vectors, MAC addresses, binary data, plain booleans and JSON) keep their plain data type. For a JSON column, declare your own type with `.$type<T>()` as in drizzle, or with the `$type` prop on a table type:

::code-group
```ts [Builders]
import * as DZ from '@mionjs/drizzle-orm-pg-core';

const events = DZ.pgTable('events', {
  id: DZ.uuid('id').primaryKey(),
  payload: DZ.jsonb('payload').$type<{kind: string; at: number}>().notNull(),
});
```

```ts [Types]
import * as DZ from '@mionjs/drizzle-orm-pg-core';

type EventsTable = DZ.PgTable<
  'events',
  {
    id: DZ.Uuid<'id', {primaryKey: true}>;
    payload: DZ.Jsonb<'payload', {$type: [{kind: string; at: number}]; notNull: true}>;
  }
>;
```
::

::note
Every column builder's format, per database and column mode, is listed in [Column Formats](./column-formats).
::
