A view declared with explicit columns works like a table: `toDrizzle` builds the real drizzle view from it, and its row type goes through your routes and your client without drizzle types.

## Declaring a View

Give the view its columns, then the query as plain sql. Tables you embed in the query resolve to the real drizzle tables when the view is built.

## View Row Types

A view's row type comes from `InferSelectViewModel`, not the table name. Views are read only, so there is no insert or update model. Drizzle splits the names for the same reason: asking for one is caught while you type.

The columns carry the same format types as a table's, so a validator built from the row type checks the same lengths, ranges and shapes.

## Materialized Views

`pgMaterializedView` takes the same columns and query, plus the storage options PostgreSQL accepts:

```ts
export const topTeams = pgMaterializedView('top_teams', {
  id: serial('id'),
  code: varchar('code', {length: 10}).notNull(),
})
  .using('btree')
  .with({fillfactor: 90})
  .tablespace('custom_tablespace')
  .withNoData()
  .as(sql`select id, code from teams`);
```

MySQL views take `algorithm`, `sqlSecurity` and `withCheckOption` instead. SQLite views take no options.

## Views Built From a Query

Drizzle can also declare a view whose columns come from a query builder:

```ts
// this form stays on drizzle
export const userView = pgView('user_view').as((qb) => qb.select().from(user));
```

Its columns come from drizzle's own query typing, which these packages keep out of your app. Declare those views with drizzle, over your `toDrizzle` tables, in the file that runs your queries. For a view's row type in your app, declare the columns yourself.
