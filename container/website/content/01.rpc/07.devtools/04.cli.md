`mion compile` runs the same compiler as the Vite plugin, the way `tsc` does: it rewrites your mion calls, emits `.js` files to your tsconfig `outDir`, writes the generated modules and the batch transport under the gen dir, and reports type errors. Use it when a project has no bundler, or when you want plain emitted files.

A type error makes it exit with code 1. With `noEmitOnError` in your tsconfig, it writes no file.

## Compiling a Project

Run it from the project that holds your client and server code. It finds every `batch([...])` and inline `inputFrom` mapper in the program, and imports the batch table from the emitted file that calls `createMionRouter`. Client and server get the same batch ids and mapper hashes.

```bash
mion compile --tsconfig tsconfig.json
```

## Compiling a Fetching Client

By default a client ships the compiled functions of the routes it calls. Pass `--client-routes fetch` to [fetch them from the server](/rpc/middlewares/fetch-metadata-client#disabling-routes-metadata-bundling) at runtime instead, like `client.routes` on the Vite plugin:

```bash
mion compile --tsconfig tsconfig.json --client-routes fetch
```

::note
In the tsconfig plugin entry, the option is `clientRoutes` (`'bundle'` or `'fetch'`).
::

## Checking a Client Against Its Server

`mion api-check` compares a client build with a server build, for example a mobile client already in users' hands with the server you are about to deploy. It reads two manifests under `<genDir>/api/`: `manifest.json` lists the server's routes and the ids of their compiled types, `client-manifest.json` what the client bundled.

```bash
mion api-check --server-gen-dir .mion --client-gen-dir ../released-client/.mion
```

It exits `0` when every bundled route matches the server, `1` with one line per difference (the route, the field, both values), and `2` when a manifest is missing or invalid, or a flag is wrong.

## Building a Client From Published API Types

Build your API package with `mion compile` and `declaration: true`, and its `.d.ts` carries the server's build version. A client calling `initClient<typeof api>()` on that type checks its ids against the version at build time, and fails with `MET012` if they differ (another tsconfig or library version).

```ts
export declare const api: PublicApi<{...}> & ApiBuildVersion<"k3Jd92xQaP1z">;
```

::note
Types written by plain `tsc` carry no version, so the client builds with the warning `MET013` and a mismatch only shows at runtime. They also lose the type of every `private` class field, so a route type holding such a class fails the client build with `MKR016`.
::

## Publishing a Types-Only Package

`mion api-types` builds a package your clients install instead of the whole server. It holds your API's types and none of the server's code.

```bash
mion api-types --tsconfig tsconfig.json --out api-types
cd api-types && npm publish
```

| In the package | What it is for |
| --- | --- |
| `.d.ts` files | The exported API and every type it reaches. Private and raw middlewares, server-only code and their imports are left out. |
| `mion-pure-fns/` | Your server's pure functions and overrides, when it has any, so the client computes the same ids. |
| `.mion/api/manifest.json` | Lets `mion api-check` compare a client build with this server build. |
| `mion-api.json` | The marker a client checks. |
| `package.json` | No JavaScript entry. Peer dependencies on the mion packages and on every library the types import. |

The name is your server's package name plus `-types`, and the version is your server's version. Change them with `--name` and `--version`.

::note
A client refuses a package with types and no JavaScript entry unless `mion api-types` built it (`MET015`). Build the client with the same mion version as the package (`MET016`).
::

## Types-Only Package Compared With OpenAPI

A types-only package does for TypeScript clients what an OpenAPI spec does for other stacks. A client that fetches its routes from the server at runtime (`client: {routes: 'fetch'}`) needs no package at all.

| | Types-only package | OpenAPI spec |
| --- | --- | --- |
| Who can read it | TypeScript clients built with mion | Any language or tool |
| Validation | The client compiles the same validators the server runs, from the same types | Each tool builds its own from the schema, so they can differ |
| Drift check | The build fails on a mismatch (`MET012`); the version is also checked at runtime | None built in |
| Version | A hash of the route ids, set by the build | Written by hand |

## API Check in CI

`mion api-check` needs no network, only the two build outputs, so it fits any CI job that has both:

```yaml
- run: mion compile --tsconfig tsconfig.json --gen-dir .mion
- run: mion api-check --server-gen-dir .mion --client-gen-dir released-client/.mion
```

## Output Locations

The gen dir defaults to `.mion` in the directory you run from. Set `genDir` in the tsconfig entry or pass `--gen-dir` to change it. Every import between these files is relative, so the emitted tree runs wherever you deploy it.

| Output | Location |
| --- | --- |
| Emitted `.js` (and source maps when the tsconfig asks for them) | The tsconfig `outDir` |
| Generated validation and JSON round trip functions | `<genDir>/types/` |
| Batch table and mapper modules | `<genDir>/rpc/` |
| Bundled route modules and the two manifests | `<genDir>/api/` |

::note
`mion compile --no-emit` checks a project and reports type errors and build diagnostics without writing anything, like `tsc --noEmit`.
::

## Shared Options

Every project option from the [RunTypes configuration](/runtypes/introduction/configuration) works as a kebab-case flag (`--emit-mode`, `--gen-dir`, `--hash-length`). A flag wins over the tsconfig entry, which wins over the default. Run `mion compile -h` for the full list.
