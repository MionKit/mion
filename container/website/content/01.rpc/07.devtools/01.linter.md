`@mionjs/devtools/eslint` is a lint plugin for OXlint and ESLint that catches mistakes in mion routes, middleware and types as you write them. It ships inside `@mionjs/devtools`.

The rules check your real types, the same way the build does. Every handler is checked, however you write it.

## Lint Rules

The plugin has one rule per [level](/runtypes/diagnostics/error-levels), and each message starts with its name, like `[rpc-handler-missing-return-type]`. The route checks below and the [RunTypes checks](/runtypes/tooling/linting) both report through them.

| Rule | What it reports | Recommended |
|------|-----------------|-------------|
| `mion/error` | Every Error: no code was made, so the build stops | ✅ Error |
| `mion/runtime-error` | Every RuntimeError: the code throws when called, or no longer checks what you asked for, so the build stops | ✅ Error |
| `mion/warning` | Every Warning, and every error you lowered | ⚠️ Warn |
| `mion/info` | Every Info message: documented behaviour or advice | Off |

::tip
The four rules are the same in every app and cannot turn one check on or off. To allow one error, add a `@mion-expect-error` comment above it or list its name in `downgradeErrors` in your tsconfig: your editor and your build both follow it.
::

## Installing the Plugin

```bash
npm install @mionjs/devtools -D
```

## Recommended Config

The recommended config turns on the four level rules. The plugin is ESM only, so ESLint needs its flat config (`eslint.config.js`), not `.eslintrc.json`. The [RunTypes linting page](/runtypes/tooling/linting#lint-plugin-setup) shows the OXlint config.

```js [eslint.config.js]
import mion from '@mionjs/devtools/eslint';

export default [mion.configs.recommended];
```

::note
The rules find `tsconfig.json` the way tsc does, from the directory the linter runs in. Point them at another file
with `settings: {mion: {tsconfig: 'tsconfig.lint.json'}}`.
::

## Showing Info Messages

The linter hides Info messages, which mark code that works as documented: a method a validator skips,
a validator on a type you wrote as `any`. Turn on `mion/info` to show them.

```js [eslint.config.js]
import mion from '@mionjs/devtools/eslint';

export default [mion.configs.recommended, {rules: {'mion/info': 'warn'}}];
```

### Separating Database Code

`drizzle-mixed-types` reports RuntimeError when a slim schema or model file imports heavy Drizzle types or the conversion bridge.
Keep schemas and models in one file, with `toDrizzle`, connections, relations and queries in a companion file.
In your editor, both layouts cost the same. A full type check (tsc or tsgo, as in CI) does not: a client importing one model also checks every `toDrizzle` call, relation and query in that file. A value import also bundles drizzle-orm into the client.

### Typed Handlers

`rpc-handler-missing-return-type` and `rpc-handler-missing-param-type` report a route or middleware handler without explicit return or parameter types. mion builds validation and the JSON round trip from those types, so without them it cannot check incoming data or encode responses. Only the call context needs no type, since it is never sent over the network.

### Returning Errors Instead of Throwing

`rpc-handler-throws` reports a `throw` that escapes a route, query, mutation, middleware or headersMiddleware handler. A returned error stays in the signature, so the client gets it typed. A thrown one goes to `@thrownErrors`, the client sees only its public message, and the declared return type is no longer true.

```ts
return new RpcError({...});   // the client gets it typed, the rest of the chain keeps running
return new FatalError({...}); // the client gets it typed, the request stops here
```

::note
A `throw` is still the way out for an error nobody declared, such as a bug or an infrastructure failure. Add `// @mion-expect-error rpc-handler-throws` on the line above it, and a comment saying why.
::

### Returned Error Types

`rpc-handler-returns-non-rpc-error` reports a handler whose declared return type can be an error that is not an `RpcError`. Only `RpcError` and its subclasses, such as `FatalError` or your own, get a typed slot in the response. Any other error fails the request and goes to `@thrownErrors`, so the code compiles but the client never gets the error its type promised.

### Unsafe Property Names

`rpc-handler-non-data-property` reports a property named `__proto__` in any interface, type literal or class, optional or not, at any depth. Writing that key on a plain object changes its prototype instead of storing a value, so every compiled function drops the member and its value is lost. TypeScript accepts it, so the linter reports the declaration in your editor, even for types no route uses yet.

It allows `prototype` and `constructor`.

#### ✅ Valid Examples

```ts
interface Settings {
  builder: string;
  constructor: string;
  prototype: string;
}

class Box {
  size: number;
  constructor(size: number) {
    this.size = size;
  }
}
```

#### ❌ Invalid Examples

```ts
interface Settings {
  __proto__: string;
}

type Poison = {
  __proto__: {admin: boolean};
};
```

### API Type Imports

`rpc-client-imports-server-value` reports a client file that imports the API type it passes to `initClient` without `type`. A normal import can put your server code and the mion router in your client bundle. The build reports it too, as a RuntimeError.

Only that import is checked: a test can start your server and call it in the same file.
