`mionVitePlugin` from `@mionjs/devtools/vite` is the one Vite plugin for mion's build-time features: compiling validation and the JSON round trip, the batch transport, and, for fullstack apps, running your API **inside the Vite dev server**.

The options are listed in [All Plugin Options](#all-plugin-options).

### One Tsconfig for Client and Server

mion reads your client and your server code as one program. `tsConfig` names the tsconfig that includes both, and defaults to `tsconfig.json` in the Vite root.

::note
A tsconfig with only `references` and no files (the shape Vite starters use) fails the build. Point `tsConfig` at the tsconfig that lists your source files.
::

### Fullstack Apps

For a fullstack app (Nuxt, SSR, a frontend's own backend), set `server.entry` to your server entry file. `vite dev` then mounts your API in **this** Vite process as dev-server middleware: one process, one port, one module graph. The frontend calls `/api/...` on the origin it is served from.

Your server entry needs no changes: the platform adapter it starts registers its routes without opening a port, so `mion.initRoutes(routes); startNodeServer();` works as written. Batches need nothing either: client and API are one program, and a batch edit reloads the API like any other change.

<code-import path="packages/private-examples/src/codegen/vite-middleware.config.ts" lang="ts [Client + in-process API]" />

The router's `basePath` decides what reaches mion, matched on a path boundary, so `/api` never catches `/apidocs`. With no `basePath`, mion serves the root and `exclude` leaves Vite's own URLs (`/@vite/...`, assets, HMR pings) to Vite; extend `DEFAULT_MIDDLEWARE_EXCLUDE` rather than replace it. Editing a route file reloads the API on the next request, and a failed load answers `503` with the real cause instead of a blank page.

A fetch-based adapter (`@mionjs/platform-bun`) works the same way, bridged to Vite's Node `req`/`res` in every runtime. For an adapter that starts no server (an edge handler), export its handler from the entry as `requestHandler`.

### One Config, Two Bundles

Set `server.build` and one `vite build` emits the static client files in `build.outDir` (default `dist`) and your API in `server.build.outDir` (default `dist-server`). That is mion's production shape, static files on a CDN plus an API server, from the same config the dev server uses.

<code-import path="packages/private-examples/src/codegen/vite-client.config.ts" lang="ts [vite.config.ts]" />

Both bundles come from one program, so a type shared by client and API is compiled once and cannot drift.

::tip
For a standalone API with no client, leave out the `server` block and use a plain library build, as in [Server-Only Builds](#server-only-builds).
::

### Vue Single-File Components

Typed mion code in a `.vue` `<script>` (`createValidate*`, `batch`, `inputFrom`, any call the plugin compiles) is compiled like code in a `.ts` file. Keep `@vitejs/plugin-vue` in the same config; `<script setup>` and classic `<script>` both work, even with a type declared in one and used in the other.

The types a marker reads must live in a `.ts` or `.d.ts` file or a package. A type imported **from another `.vue`** file cannot be resolved, so the build stops with `MKR007` naming that import.

::note
`runTypes: {sfc: false}` turns this off. The plugin still warns when a `.vue` file ships a marker with no compiled functions, since that fails at runtime.
::

### Bundled Client

By default the build bundles every route the client calls, under `.mion/api/`, so a call needs no request and no code built at runtime. Set `client: {routes: 'fetch'}` to get them from the server instead, see [fetchMetadata](/rpc/middlewares/fetch-metadata-client#disabling-routes-metadata-bundling).

### Generic Call Helpers

The build bundles a call only when it can see which route the call names. A helper typed with a plain `RouteSubRequest<any>` hides the route, so keep the helper generic.

### Client Without the Plugin

Without the plugin, a client fetches validation and JSON round trip metadata from the server at runtime, so single route calls need no build step once you set up [`useFetchMetadata`](/rpc/middlewares/fetch-metadata-client). It cannot send a [batch](/rpc/client/batch): batch ids come from the build, so `batch()` throws `batch-missing-id`. A client that uses batches must be built in the same program as its API.

## Batch Transport

A [batch](/rpc/client/batch) is written in **client** code, but the server runs only the batch ids it knows. The build gives each `batch([...])` call an id from its routes and mappings, and collects them for the server itself, with no option:

- It reads every `batch([...])` call and inline `inputFrom` mapper in the program. It writes the batch table (`batches.generated.js`) and one module per inline mapper to `.mion/rpc/` in its gen dir.
- It adds the table's import to the module that calls `createMionRouter`, so you write nothing. `vite build` inlines the table and bundles each mapper, so the output has no `node:fs` and stays edge and lambda safe.
- The client calls get each batch's id and each mapper's hash from the same source, so the two sides agree in any build order.

`mion compile` in the [CLI](/rpc/devtools/cli) generates the same folder.

::note
A batch the build cannot read (a spread, a route from a function parameter, a mapper it cannot trace) fails the build, because a batch without an id can never be sent.
::

## All Plugin Options

```typescript
import {mionVitePlugin} from '@mionjs/devtools/vite';

mionVitePlugin({
    // The one tsconfig that includes your client and server code (default: tsconfig.json in the Vite root)
    tsConfig?: string,

    client?: {
        // 'bundle' (default): ship each called route's metadata and compiled functions, no request needed.
        // 'fetch': get them from the server on first use (needs useFetchMetadata and mionFetchMetadata).
        routes?: 'bundle' | 'fetch',
    },

    // Fullstack app only: the mion API this Vite run hosts, mounted INSIDE `vite dev`, and a second
    // `vite build` bundle with `build` set. Leave it out for an API started on its own.
    server?: {
        entry: string;                    // The server entry file, relative to the Vite root (required)

        // build: opt in to the second bundle
        build?: {
            outDir?: string;              // Where the API bundle lands (default: 'dist-server')
        },

        // dev server
        exclude?: RegExp[];               // With no router basePath: paths left to Vite (assets, /@vite/…)
        hotReload?: boolean;              // Re-load the API on source changes (default: true)
    },

    // Build-time compilation of validation and the JSON round trip
    runTypes?: {
        genDir?: string;                  // Generated-output root (default: <srcDir>/.mion)
        emitMode?: 'code' | 'both';       // What generated functions ship (default: 'code'). MUST be 'both' on edge
                                          // runtimes (Cloudflare Workers, Vercel Edge), which forbid the
                                          // `new Function` that 'code' runs on first use.
        downgradeErrors?: string[] | '*'; // Report these RuntimeError codes as warnings instead of halting (default: none)
        levels?: 'all';                   // Also print Info messages, hidden by default
        patternSampleCount?: number;      // mockSamples generated per pattern that declares none
        patternSampleRetries?: number;    // Generation retries before failing with FMT005
        derivedPayloadLimits?: boolean;   // Derive per-route size limits from the types (default: true)
        jsRuntime?: string;               // Runtime for the pattern-check sidecar (node/bun auto-detected)
        sfc?: boolean;                    // Transform typed code in Vue SFC <script> blocks (default: true)
    },
});
```

::note
Build-time compilation is always on, the batch transport is automatic, and scan scope comes from your tsconfig, so none of the three has an option here.
::
