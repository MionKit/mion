mion uses `@mionjs/run-types` for automatic validation.
This is a powerful type system that extracts TypeScript type metadata at compile time and uses it at runtime.
No need to manage schemas or write extra code for validation.

## Automatic Validation

All routes and middleFns parameters are automatically validated before the method gets called.
If validation fails, an `RpcError` is thrown with details about the validation errors and method gets never called.

## Validation Functions

mion provides two main validation functions with different use cases:

#### isType - Fast Boolean Check

`isType` is optimized for performance and returns a simple `true` or `false` result. Use this when you only need to know if data is valid without detailed error information.

<code-import path="packages/examples/src/run-types/validation-is-type.ts" lang="ts" />

**When to use `isType`:**
- Quick validation checks in hot paths
- Guard clauses where you just need a boolean
- Performance-critical code where detailed errors aren't needed

#### getTypeErrors - Detailed Error Information

`getTypeErrors` returns comprehensive error data including the path to invalid properties and expected types. Use this when you need to provide detailed feedback to users or for debugging.

<code-import path="packages/examples/src/run-types/validation-type-errors.ts" lang="ts" />

**When to use `getTypeErrors`:**
- Form validation with user feedback
- API error responses with detailed messages
- Debugging and logging validation failures
- When you need to know exactly what went wrong

## Strict Types

By default, mion allows objects with extra properties to pass validation. When `strictTypes` is enabled, objects with unknown or extra properties are rejected.

This is useful for security-sensitive endpoints where you want to ensure no unexpected data is passed.

## Sanitize params

A RunTypes format can declare a rewrite under its `transform` key: trim the spaces around a value, lowercase an email, strip the grouping from a card number. See [Transforms](/runtypes/guide/type-formats#transforms) for the two ways to spell one.

By default a route never applies it, so the handler gets the value exactly as sent. Turn on `sanitizeParams` and the route applies every transform its params types declare, after the request is decoded and before validation. That order matters: a value that only passes once it is trimmed is accepted, and the handler always gets the clean value. Only the params are sanitized. Headers and return values are never touched, and the option works even when `validateParams` is off.

<code-import path="packages/examples/src/router/sanitize-params-example.routes.ts" lang="ts" />

The client mirrors it. The resolved flag travels with the route metadata, and the client applies the same compiled transform locally before its own validation and before the value goes on the wire, so both ends validate and send the same thing. The client option `sanitizeParams` (on by default) turns that local step off; the server still sanitizes.

<code-import path="packages/examples/src/client/client-sanitize-params.ts" lang="ts" />

::note
A value with the wrong shape (a number where a string is expected) skips the transform and reaches validation, which reports the real error. And because a sanitized route runs the transform on the client and again on the server, prefer transforms that give the same result twice: trim, the case changes, `replaceAll` and `stripSeparators` do, while `replace` (first match only) does not.
::
