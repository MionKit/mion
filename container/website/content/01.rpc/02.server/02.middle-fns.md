Middleware functions are declared with `mion.middleFn`, a helper of the router returned by `createMionRouter` (see [Creating the Router](/rpc/server/routes#creating-the-router)), and can be executed before or after a route. middleware are functions that can be chained to create the full [Execution Chain](/rpc/server/middle-fns) for a route.

MiddleFns are useful when a route might require some extra data like authorization, filters or some extra processing like body parsing, logging, etc...

The first parameter is always the [Call Context](/rpc/server/routes), the rest of parameters are remote parameters that get deserialized and validated before the middleFn gets executed.

## Raw Middleware functions

In case we need to access the raw or native underlying request and response, we must use `mion.rawMiddleFn`.

These are functions that receive the `CallContext`, `RawRequest`, `RawResponse` and `RouterOptions`, but can't receive any remote parameters or return any data. 
`Raw Middleware functions` can only modify the CallContext and return or throw errors.

Raw Middleware functions are useful to extend the router's core functionality, i.e: The router internally uses them for serialization/deserialization.

## Always Run

A thrown error, or a returned `FatalError`, ends the request: the rest of the middleFns and the route are not executed. A plain returned `RpcError` does not stop anything, see [Error Handling](/rpc/server/error-handling).

A middleFn with `alwaysRun: true` runs anyway, on every request. This is useful for a logger that needs to run after everything else and log the errors or the request data. The error that ended the request is on `ctx.response.fatalError`.

## Requests That Already Failed

Some requests are refused before any handler could run:

| Request | Answer |
| --- | --- |
| A path that names no route | 404, `route-not-found` |
| A batch id the server does not know | 404, `batch-unknown-id` |
| A body larger than the route's request limit | 413, `request-payload-too-large` |

None of them reads the body: the platform adapter never buffers it and the router never parses it.

**Only the middleFns that declare `alwaysRun` run for such a request.** That is the point: a session loader or an authorization step does no work for a request that is already going to be refused. A rate limiter or an access log that must see these requests declares `alwaysRun` too.

A middleFn declared in the routes object belongs to the routes next to it and never runs for any of them.

## Execution Chain

The Execution Chain is a list of all the middleFns and the route that are executed during a route call.
That is: all middleFns before the route, the route itself, and all middleFns after the route.
The Execution chain is generated when the the router is started so it is the same for all requests.

For every incoming request the Execution Chain is retrieved and all middleFns and the route get executed in order,
there are no paths or conditionals everything is executed unless an error occurs.

### Execution Order

::note
The order in which Routes and Middleware functions are added to the router is important.
Middleware functions and Routes are executed in the same order they are defined (Top Down order).
::

We can limit middleFns to be executed only on a subset of routes.
