Every route and middleware gets the call context as its first parameter. It holds everything about one request: the request, the response and the data your routes and middleware share.

Unlike Express, a route does not parse the request or write the response. It reads its params and returns a value, and mion sends both over HTTP.

::tip
Never keep the context in a module-level variable or a cache. It holds the whole request body, so that memory is never freed.

## Sharing Data Between Handlers

`ctx.shared` passes data from one middleware or route to the next in the same request. It is never sent to the client. The `contextDataFactory` router option is a function that creates it for each request, and its return type is the type of `ctx.shared` everywhere. Without a factory, `ctx.shared` is an empty object typed `any`.

::tip
The factory must return a new object each time, never a module-level one, or all requests share it. A factory that returns an empty object makes `initRoutes` throw.
::

## Request and Response Format

The URL path is the route id: the route's keys in your routes object, joined by `/`, after the `basePath`. The body is a JSON object whose keys are route and middleware ids, each holding an array of params. The response uses the same keys for the return values. A route or middleware with no params, or no return value, has no key.

<code-import path="packages/private-examples/src/router/call-context-wire-format.routes.ts" lang="ts" />

A call to `users.getUser` also sends the params of the `auth` middleware, and gets both return values back:

```http
POST /users/getUser
{"auth": ["my-token"], "users/getUser": [42]}

200 OK
{"auth": 3600, "users/getUser": {"id": 42, "name": "Leo"}}
```

Headers go as HTTP headers, never in the body. Errors use their own keys, see [Error Response Format](/rpc/server/error-handling#error-response-format).

::tip
The body can also be a plain JSON array of the route's params, like `[42]`. Use it for a quick `curl` call when no middleware needs params and you do not use [mionSyncRoutes](/rpc/middlewares/sync-routes).
::

## JSON Round Trip Steps

mion runs these steps for each request. A failed step ends the request with an error. To pick how params and return values are encoded, see [Parser Strategies](/rpc/server/json-round-trip#parser-strategies).

1. Parses the body as JSON, once.
2. For each middleware and route in the [execution chain](/rpc/server/middleware#execution-chain) (the order they run in), turns its params back into their types (a Date from a string, a Map from an array), validates them, then runs it.
3. Encodes every return value and sends the response.

## Queries in the URL

The client sends a route made with `mion.query()` as a GET request when the URL fits in 4096 characters. The JSON body goes base64url encoded in the `data` query parameter. The server reads `data` only when the request has no body. A `data` value that is not base64url fails with `invalid-query-body`.

```http
GET /users/getUser?data=eyJ1c2Vycy9nZXRVc2VyIjpbNDJdfQ
```

## Request Body Safety

The router checks every body before your middleware and routes run:

- The body must be valid JSON holding an object or an array. Anything else fails with `parsing-json-request-error` or `invalid-request-body`.
- Each handler's value must be an array of params, or the request fails with `serialization-error`.
- A `__proto__` key in data typed as a record or index signature fails with `serialization-error`, so a request cannot change an object's prototype. `prototype` and `constructor` are ordinary keys.
- Params nested too deep to decode or validate fail with `request-nesting-too-deep`.
