mion uses `RpcError` for every error in routes and middleware. How you raise it decides whether the client gets it typed and whether the rest of the chain runs.

| What you write | Typed on the client | The rest of the chain |
| --- | --- | --- |
| `return new RpcError(...)` | Yes, in the route or middleware's own slot | Keeps running |
| `return new FatalError(...)` | Yes, in the route or middleware's own slot | Stops |
| `throw` anything | No, only the public message in the undeclared slot | Stops |

## Return Errors

**Return application errors.** A returned error is part of the function signature, so the client knows every error type a route can answer, its `errorData` included. With several error types, the client gets a discriminated union of all of them. A returned error keeps the chain running, so one route answering `user-not-found` does not drop the other routes in the same request.

::tip
A middleware can return a typed error without blocking, such as an expired session on a route that still works for guests.
::

## Stopping the Request

Return a `FatalError` when an error must also stop the request, like a failed auth check in a middleware. It is an `RpcError`, so it stays in the signature and reaches the client typed. Nothing after it runs except the middleware with `alwaysRun`, and in a batch the routes after it are skipped.

<code-import path="packages/examples/src/router/error-handling.routes.ts" lang="ts" commentStart="// start:fatal-error" commentEnd="// end:fatal-error" />

::tip
The client sees a returned `FatalError` like any declared error: in the middleware's own slot and its `onError` listeners, never in the undeclared slot. It is not told the route was skipped: a route that returns a value simply gives `undefined`.
::

## HTTP Status Codes

A `FatalError` sets the response's HTTP status from its `statusCode`, such as 401. Without one it answers 400, a declared application error, like the auth gate above. A thrown error without a `statusCode` answers 422, something the server did not expect.

## Throwing Errors (Discouraged)

Throw only for truly unexpected situations, like bugs or infrastructure failures. A thrown error ends the request like a `FatalError`, but it is not in the function signature, so the client gets only its `publicMessage`, in the undeclared slot.

<code-import path="packages/examples/src/router/error-handling.routes.ts" lang="ts" commentStart="// start:throw-error" commentEnd="// end:throw-error" />

The router itself throws for what nobody declared: a missing route, an unreadable body, a payload over the limit. The exception is `validation-error`: it is thrown on the server but is part of every route's contract, so the client still gets it typed.

::note
The `@mionjs/no-throw-in-handlers` lint rule reports a `throw` inside a handler. To keep a throw, add `eslint-disable-next-line @mionjs/no-throw-in-handlers` above it and say why.
::

## Error Response Format

- **Returned errors** (strongly typed), a `FatalError` included, appear under the route or middleware id with their type information.
- **Thrown errors** (untyped) go in the `@thrownErrors` field.

```json
{
    "getUser": [0, {
        "type": "user-not-found",
        "publicMessage": "User not found",
        "errorData": {"userId": "123"}
    }],
    "@thrownErrors": {
        "someMiddleware": {
            "type": "unknown-error",
            "publicMessage": "Unknown error in handler \"someMiddleware\" of route ExecutionChain.",
            "statusCode": 422
        }
    }
}
```

`getUser` returns `User | RpcError`, so its value is sent as an `[index, value]` pair.

::note
The mion client handles this for you: read `error` or `errors` from the result. The internal `message` property and the fatal flag are never sent to the client.
::

## Always Run Middleware

A middleware with `alwaysRun: true` runs even after an error ended the request, see [Always Run](/rpc/server/middleware#always-run).
