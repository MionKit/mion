mion uses `RpcError` for every error in routes and middleFns. Two things about an error are decided separately:

- **Is it part of the contract?** A returned error is in the handler's signature, so the client gets it strongly typed and handles it right at the call site. A thrown error is not, so the client only gets its public message.
- **Does it end the request?** A `FatalError` and a thrown error stop the execution chain. A plain returned `RpcError` does not.

| What you write | Typed on the client | The rest of the chain |
| --- | --- | --- |
| `return new RpcError(...)` | Yes, in the route or middleFn's own slot | Keeps running |
| `return new FatalError(...)` | Yes, in the route or middleFn's own slot | Stops |
| `throw` anything | No, only the public message in the undeclared slot | Stops |

A returned error keeps the chain running. That is what a chain of routes needs: one route answering `user-not-found` must not drop the other routes in the same request. It also lets a middleFn report something typed without blocking, such as an expired session on a route that still works for guests.

## Return a FatalError to Stop the Request

Some errors must also stop the request. An auth middleFn is the usual case: the route behind it must not run at all. Return a `FatalError` for that. It is an `RpcError`, so it stays in the signature and reaches the client typed, and it ends the execution chain: nothing after it runs, except the middleFns with `alwaysRun`.

<code-import path="packages/examples/src/router/error-handling.routes.ts" lang="ts" commentStart="// start:fatal-error" commentEnd="// end:fatal-error" />

::tip
The client sees a returned `FatalError` exactly like any declared error: in the middleFn's own slot and in its `onError` listeners, never in the undeclared slot. That the route was skipped is a server detail. For a route that returns a value, the result is simply `undefined`.
::

In a batch, routes run in order on one execution chain, so a `FatalError` from one route ends the whole batch: the routes after it are skipped.

A `FatalError` sets the HTTP status of the response. Give it a `statusCode` (401 for the auth gate above). Without one the response answers 400, a declared application error. A thrown error without a `statusCode` answers 422, the code for something the server did not expect.

## Throwing Errors (Discouraged)

::warning
**Thrown errors lose type information.** Throw only for truly unexpected situations (bugs, infrastructure failures).
::

A thrown error ends the request like a `FatalError`, but it is not part of the function signature, so the client gets only the `publicMessage` in its undeclared slot:

<code-import path="packages/examples/src/router/error-handling.routes.ts" lang="ts" commentStart="// start:throw-error" commentEnd="// end:throw-error" />

::note
The `@mionjs/no-throw-in-handlers` lint rule reports a `throw` inside a handler, so the pattern is enforced as you write. When a throw is deliberate, silence it on that line with `eslint-disable-next-line @mionjs/no-throw-in-handlers` and say why.
::

The router itself throws for what nobody declared: a route that does not exist, a body it cannot read, a payload over the limit. The one exception is `validation-error`, which is thrown on the server but is part of every route's contract, so the client still gets it typed.

## Error Response Format

Returned and thrown errors are serialized differently in the response body:

- **Returned errors** (strongly typed), a `FatalError` included: appear under the route or middleFn id, preserving type information
- **Thrown errors** (untyped): collected in the `@thrownErrors` field

```json
{
    "getUser": {
        "type": "user-not-found",
        "publicMessage": "User not found",
        "errorData": {"userId": "123"}
    },
    "@thrownErrors": {
        "someMiddleFn": {
            "type": "unknown-error",
            "publicMessage": "Unexpected error"
        }
    }
}
```

::note
The mion client abstracts this away, you simply access `error` or `errors` from the result object. The internal `message` property is never sent to the client, and neither is the fatal flag.
::
