mion has an RPC style routing system so Routes are just functions that can be called remotely.

The first parameter of the remote method is always the [Call Context](/rpc/server/routes). The rest of parameters are the remote parameters that get deserialized and validated before the route gets executed.

There are no URLs or Paths when defining a route, instead the API is defined using a plain JavaScript object, where every entry of the object is a route or middleFn. This way we simplify referencing remote methods when calling them from the client.

Internally a URL is generated for each route so these can be referenced using regular HTTP requests, but all this complexity is managed transparently by the [client](/rpc/client/client-overview).

## Creating the Router

Create the router once per app with `createMionRouter` and pass every router option there (base path, serializer, context data factory, strict types and the rest). The options are written once and carried by type into every helper the router returns: `route`, `query`, `mutation`, `middleFn`, `headersFn` and `rawMiddleFn`. When a `contextDataFactory` is given, `ctx.shared` is typed from its return value in every handler, with nothing to annotate.

::tip
Create the router and call `initRoutes` in the same file, your routes file; the server entry then just imports it (see the platform pages). A second `createMionRouter` call throws. The helpers are plain functions, so destructuring them is fine: `const {route, middleFn} = createMionRouter({...})`.
::

::note
A shared field that starts out empty needs a return type on the factory, `(): {user: User | null} => ({user: null})`, otherwise `ctx.shared.user` is typed as `null` and handlers cannot assign to it.
::

## Query and Mutation Handlers

The router's `query` and `mutation` helpers declare the intent of each route. This distinction enables the client to automatically optimize how requests are sent over the wire.

- **`mion.query()`**: read-only operations. The client automatically sends small payloads via `GET` with `?data=base64url`.
- **`mion.mutation()`**: operations that modify data. The client always sends data in the body.
- **`mion.route()`**: no explicit intent, data is sent in the body. Does not participate in cache semantics.

<code-import path="packages/examples/src/router/query-mutation-definition.routes.ts" lang="ts" />

::tip
Declaring intent with `mion.query()` and `mion.mutation()` is recommended. It makes your code more readable and enables future optimizations like caching layers.
::

## Registering Routes

Once the routes object is complete, pass it to `mion.initRoutes`. It runs once per app: it initializes the router with the options given to `createMionRouter`, registers the routes and returns the API type the client uses. To split routes across files, export each routes object and compose them with spread in that single call. A sub-api can still be typed on its own with `PublicApi<typeof routes>`.

## Naming Routes

Keep it simple and use regular valid JS variable names for routes. It is not recommended to use the array notation (using quotes) to define route names.

::note
When a route lookup is done there is no URL decoding done so if you define names that include special URL encoded characters then routes won't be found.
::

## Call Context

The [`CallContext`](#callcontext) contains all the data related to the ongoing call.

Most of the data within the CallContext is marked as read-only, this is because it is not recommended to modify the context manually. It is still possible to modify it (the context is not a real Immutable JS object). 

::tip
**Quick Tip:**
To avoid memory leak issues you should never store a reference to the context or any of its properties within a Route or MiddleFn.
The context is passed to every handler so there shouldn't be any reason to do so.
::
