title: Request & Response
description: Understanding mion's request and response objects.

Every route and middleware gets a MionRequest and a MionResponse in its [call context](/rpc/server/routes#call-context), the first parameter.

mion does not use the Fetch API `Request` and `Response`. It uses its own objects to support platforms that do not use them, such as Node.js and AWS Lambda.

For example, [`@mionjs/platform-node`](/rpc/platforms/node-js) uses node's `IncomingMessage` and `ServerResponse` and [`@mionjs/platform-aws`](/rpc/platforms/aws-lambda) uses `APIGatewayEvent` and `APIGatewayProxyResult`, but routes and middleware always get a MionRequest and MionResponse.

::note
mion passes the parameters to routes and middleware for you, so you rarely need the request or response objects. Just declare the parameters and their types.
::

## How Data Is Sent and Received

The URL path is the route's id, used to find the route. The request body is a JSON object: each key is a route or middleware id, each value an array of its parameters. The response body uses the same keys, each holding that method's return value.

This lets **one HTTP request call several routes and middleware**. For example, an auth middleware can send and receive its own data next to the route, in the same request.

::code-group

```md [Example]
| Request Path | Request Body                      | Response Body                          |
| ------------ | --------------------------------- | -------------------------------------- |
| `/sayHello`  | `{"sayHello": ["John"] }`         | `{"sayHello": "Hello John."}`          |
| `/greetings` | `{"greetings": ["Adan", "Eve"] }` | `{"greetings": "Hello Adan and Eve."}` |
```

## Error Handling in Responses

Returned errors go under the route id and thrown errors in `@thrownErrors`, see [Error Response Format](/rpc/server/error-handling#error-response-format).
