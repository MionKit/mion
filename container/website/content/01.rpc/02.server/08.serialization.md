## Encoder Strategies

Every route has two wires: the params (the client encodes, the server decodes) and the return value (the server encodes, the client decodes). The `encoder` option picks a strategy for each of them. The strategies are the JSON encoder strategies of RunTypes, plus binary.

| Strategy  | What it does                                                                          | Mutates your objects | Unknown keys | Payload   |
| --------- | ------------------------------------------------------------------------------------- | -------------------- | ------------ | --------- |
| `clone`   | Builds a fresh JSON value from the type, then the platform stringifies it.            | No                   | Dropped      | Normal    |
| `mutate`  | Rewrites Dates, Maps and the like in place, then the platform stringifies the value.  | Yes                  | Kept         | Normal    |
| `direct`  | Writes the JSON string in one pass.                                                   | No                   | Dropped      | Normal    |
| `compact` | Drops the key names: an object becomes an array of its declared properties, in order. | No                   | Dropped      | Smallest JSON |
| `binary`  | Writes bytes instead of JSON, with fixed-size encodings for the numeric formats.      | No                   | Dropped      | Smallest  |

The built-in defaults are `direct` for the params and `mutate` for the return value. That is the fastest pairing for a request and response cycle, where the returned objects are discarded right after they are sent.

The option is written once on the router and applies to every route, as a string for both directions or as an object naming each one.

::tip
The build reads the `encoder` option to decide which functions each route compiles, so write it inline or as an `as const` preset, as above. An option built at run time (a function call, a variable typed `string`) is a build error and a lint error, and the router refuses to start when the value it reads differs from what was compiled.
::

## What Each Route Compiles

A route only compiles the functions its strategies need. With the defaults, a route ships a validator, an error reporter, a string writer for its params and an in-place encoder for its return. Choosing `compact` swaps in the positional pair, and choosing `binary` adds the binary pair next to the JSON one: the JSON pair still serves the first call of a route, before the client knows the strategy, and any client that sends JSON.

The response framing follows from the strategies. A `direct` return is a string the router joins into the body, a `binary` return is bytes, and every other strategy hands the platform a value to stringify. A middleware function returning data with `direct` makes the whole response a joined string.

## Compact in Practice

`compact` measures 40 to 60 percent fewer bytes than keyed JSON on real objects, because the property names never travel. Keep three things in mind:

- The wire is coupled to the type, like binary: both ends must share the same type, which mion guarantees by shipping the compiled functions to the client.
- An optional property that is absent rides a `null` placeholder and comes back `undefined`, so a property typed `T | null | undefined` cannot tell a present `null` from an absent value.
- The payload is positional, so it is not a JSON document another service can read by key. Pick `clone` or `direct` for an endpoint other tools consume.

## Binary Serialization in Detail

For applications where data transfer efficiency is critical, binary serialization provides more compact data transfer compared to JSON.

::tip
Binary serialization is especially effective for transferring data structures that contain numeric data. Using the numeric type formats from `@mionjs/run-types/formats` (like `Int32`, `UInt8`, `Float`) allows the binary serializer to use optimized fixed-size encodings, significantly reducing payload sizes compared to JSON.
::

## Why a Custom Binary Format?

You might wonder why mion uses its own binary protocol instead of established formats like Protocol Buffers, MessagePack, or CBOR. The answer lies in **full TypeScript support** and **flexibility**.

**Full TypeScript Feature Support**

Unlike Protocol Buffers which requires separate `.proto` schema files and has limited type support, mion's binary format is generated directly from your TypeScript types. This means it supports:

- **Union types** - `string | number | MyType`
- **Discriminated unions** - Tagged unions with type discriminators
- **Intersection types** - `TypeA & TypeB`
- **Tuples** - `[string, number, boolean]`
- **Optional properties** - `{ name?: string }`
- **Rest parameters** - `(...args: string[]) => void`
- **Circular/recursive types** - Types that reference themselves
- **Generics** - Full generic type support
- **Enums** - Both string and numeric enums
- **Maps and Sets** - Native JavaScript collections
- **Classes** - With custom serialization/deserialization

**End-to-End Control**

Since mion controls both the client and server serialization, we can optimize the protocol for our specific use case:

- **No schema files** - Types are the schema
- **JIT compilation** - Serializers are generated at build time for maximum performance
- **Type-aware encoding** - The encoder knows the exact type, eliminating type markers where possible
- **Compact representation** - Optional properties use bitmaps, known properties don't need names

::note
For a deep dive into how binary serialization works internally, see the [Binary Serialization Deep Dive](/rpc/articles/binary-serialization) article.
::

##### Buffer Pooling

Binary responses are written into a size-classed buffer that is reused across requests instead of
allocated per response. Where a platform can hand the buffer back safely it is enabled by default,
**node** (released on the response's `finish`/`close`) and **bun** (Bun copies the bytes into the
`Response` synchronously). The other adapters allocate per response.

mion sizes that buffer from what each route recently wrote, and falls back to measuring the exact
byte count when a route's recent sizes are too volatile for the statistics to pick the right size
class. Nothing needs configuring for this. The defaults are what the benchmarks are tuned against.
