## Serializer Strategies

Every route has two wires: the params (the client encodes, the server decodes) and the return value (the server encodes, the client decodes). The `serializer` option picks a strategy for each of them.

| Strategy  | What it does                                                                          | Mutates your objects | Unknown keys sent | Unknown keys received | Payload  |
| --------- | ------------------------------------------------------------------------------------- | -------------------- | ----------------- | --------------------- | -------- |
| `clone`   | Builds a fresh JSON value from the type, then the platform stringifies it.            | No                   | Dropped           | Dropped               | Normal   |
| `mutate`  | Rewrites Dates, Maps and the like in place, then the platform stringifies the value.  | Yes                  | Kept              | Kept on params        | Normal   |
| `compact` | Drops the key names: an object becomes an array of its declared properties, in order. | No                   | Dropped           | Dropped               | Smallest |

Unknown keys have two columns because a route has two ends. What you send is up to your strategy. What you receive depends on which end you are.

Your server reads params from any caller, which need not be a mion client, so `mutate` hands your handler exactly what arrived. Your client reads a return value your own server wrote, so it always rebuilds the declared shape: a property your return type does not declare never reaches the caller, whatever the route sent.

::note
An unknown key is dropped at serialization, not at validation. It is gone from the params, not set to `undefined`, so it cannot slip into a database insert. To reject the request instead of dropping the key, see [Strict Types](/rpc/server/validation#strict-types).
::

The default is `clone` on both directions, the safe pairing. It never touches the value it encodes, so a handler can return a cached row and a caller can pass an object it still uses, and it builds the payload from the declared type, so anything the type does not declare never reaches the wire.

The option is written once on the router and applies to every route, as a string for both directions or as an object naming each one.

::tip
`mutate` is the faster return strategy: it rewrites Dates and the like in place and allocates no copy. Two conditions make it safe. The handler must be done with the object it returns (it is modified, so never return a cached or shared one), and the object must already hold exactly what the type declares, because `mutate` sends every property it finds.
::

The build reads the `serializer` option to decide which functions each route compiles, so write it inline or as an `as const` preset, as above. An option built at run time (a function call, a variable typed `string`) is a build error and a lint error, and the router refuses to start when the value it reads differs from what was compiled.
::

## What Each Route Compiles

A route only compiles the functions its strategies need. With the default it ships a validator, an error reporter and one `clone` pair per direction. Choosing `compact` swaps in the positional pair instead.

Every strategy hands the platform a value to stringify, so the response framing is the same whichever one you pick.

## Compact in Practice

`compact` measures 40 to 60 percent fewer bytes than keyed JSON on real objects, because the property names never travel. Keep three things in mind:

- The wire is coupled to the type: both ends must share the same type, which mion guarantees by shipping the compiled functions to the client.
- An optional property that is absent rides a `null` placeholder and comes back `undefined`, so a property typed `T | null | undefined` cannot tell a present `null` from an absent value.
- The payload is positional, so it is not a JSON document another service can read by key. Pick `clone` for an endpoint other tools consume.
