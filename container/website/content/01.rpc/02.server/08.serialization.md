## Serializer Strategies

Every route has two wires: the params (the client encodes, the server decodes) and the return value (the server encodes, the client decodes). The `serializer` option picks a strategy for each one, written on the router as a string for both directions or as an object naming each one.

<code-import path="packages/examples/src/router/serializer-strategies.ts" lang="ts" />

| Strategy  | What it does                                                                          | Mutates your objects | Unknown keys sent | Unknown keys received | Payload  |
| --------- | ------------------------------------------------------------------------------------- | -------------------- | ----------------- | --------------------- | -------- |
| `clone`   | Builds a fresh JSON value from the type, then the platform stringifies it.            | No                   | Dropped           | Dropped               | Normal   |
| `mutate`  | Rewrites Dates, Maps and the like in place, then the platform stringifies the value.  | Yes                  | Kept              | Kept on params        | Normal   |
| `compact` | Drops the key names: an object becomes an array of its declared properties, in order. | No                   | Dropped           | Dropped               | Smallest |

Unknown keys have two columns because a route has two ends. On params only `mutate` keeps them, because your server can be called by something that is not a mion client. A return value always arrives in the shape your return type declares.

::note
An unknown key is dropped at serialization, not at validation. It is gone from the params, not set to `undefined`, so it cannot slip into a database insert. To reject the request instead of dropping the key, see [Strict Types](/rpc/server/validation#strict-types).
::

::tip
`mutate` is the faster return strategy: it rewrites Dates and the like in place and allocates no copy. It is safe when the handler is done with the object it returns, and the object holds exactly what the type declares.

Any route or middleware function overrides the router with its own `serializer`, for one direction or both. A middleware function that takes params or returns data uses the same wires as its route, so give it the same strategy when the route uses `compact`.

::tip
Write the `serializer` option inline or as an `as const` preset, as above, because the build reads it. A value built at run time (a function call, a variable typed `string`) is a build error and a lint error, and the router refuses to start when the value it reads differs from what was compiled.
::

## What Each Route Compiles

A route only compiles the functions its strategies need. With the default it ships a validator, an error reporter and one `clone` pair per direction, and `compact` swaps in the positional pair instead. Every strategy hands the platform a value to stringify, so the response framing is the same whichever one you pick.

## Compact in Practice

`compact` measures 40 to 60 percent fewer bytes than keyed JSON on real objects, because the property names never travel. Three things to keep in mind:

- Both ends must share the same type, which mion guarantees by sending the compiled functions to the client.
- An absent optional property travels as `null` and comes back `undefined`, so a property typed `T | null | undefined` cannot tell a present `null` from an absent value.
- The payload is positional, not a JSON document another service can read by key. Pick `clone` for an endpoint other tools consume.
