## Writing a Mapper

Write the mapper inline, in the call. The build copies it into the server, so there is nothing to register or keep in sync.

It must follow the RunTypes [pure function](/runtypes/guide/pure-functions) rules: no closures, no outside variables, no side effects. The server runs it without your client-side scope.

```ts
// ✅ Pure: only uses its input
inputFrom(order, (o) => o!.userId)

// ✅ Pure: inline computation is fine
inputFrom(order, (o) => o!.totalUSD * 100)

// ❌ Not pure: references an outside variable
const multiplier = 2;
inputFrom(order, (o) => o!.totalUSD * multiplier)
```

## How a Batch Reaches the Server

A batch is defined once, in your client code, and the build does the rest:

1. The build gives every `batch([...])` call site an id, from its routes in order and its mappings. The same batch gets the same id anywhere, and the id changes only when its routes or mappings change, so a different mapper makes another batch.
2. The build compiles a table of id to definition (routes plus mappings) into the server.
3. The client sends only the id, `POST /mion-batch?id=<batchId>`, with the route inputs in the body.
4. The server looks the id up, runs the routes and the mappings, and answers in one round trip.

::note
The batch definition never travels on the wire. The server runs only the batches and the mappers its own build compiled in.
::

## Writing a Batch the Build Can Read

Write each element as a route call, inline in the array or bound to a `const` / `let` in the same file. Anything else is a build error, and a batch the build cannot read has no id, so it can never be sent.

```ts
// ✅ Inline route calls
batch([routes.users.getById('U1'), routes.orders.list()]).call();

// ✅ Route calls bound to a const in the same file
const user = routes.users.getById('U1');
const orders = routes.orders.list();
batch([user, orders]).call();

// ❌ The build cannot read a spread or a parameter
function run(extra: RouteSubRequest[]) {
  return batch([routes.users.getById('U1'), ...extra]).call();
}
```

| The build reports | Example |
| --- | --- |
| An element that is not a readable route call | A spread (`...routes`), a value from a function parameter, a route built in a loop, a `let` that is reassigned after its initializer |
| A mapping whose source route is outside the batch | `inputFrom(other, ...)` where `other` is not in the array, or comes after its target |
| A mapper the build cannot read | A function reference instead of an inline arrow, a computed name, a mapping placed after a spread argument |
| The same route twice in one batch | `batch([routes.users.getById(1), routes.users.getById(2)])`: the server keys a batch by route id, so list a route once |
| A mapping at a parameter the route does not have | `routes.users.getById(id, inputFrom(...))` on a one-parameter route |

## Unknown or Missing Batch Ids

An id the server does not know is refused with `batch-unknown-id` (404) before the body is read. Only middleware that declares `alwaysRun` runs for it.

Without the mion build plugin, `batch()` throws `batch-missing-id` and nothing is sent. Single route calls still work. When asked for every method, the metadata route also lists the registered batch ids, so a hand-written client can call a batch by id. It skips both when the API has more methods than the `getAllRemoteMethodsMaxNumber` router option (100 by default).

## Build Configuration

Nothing to configure. The **server** build writes the batch table and every inline `inputFrom` mapper into one folder under its own gen dir, and imports the table from the file that calls `createMionRouter`:

```
<server genDir>/rpc/batches.generated.js
<server genDir>/rpc/pf/…                   one module per inline mapper
```

| Rule | What it means for you |
| --- | --- |
| Generated by the server | The server owns every file it loads. Nothing is written into the client project, and no path leaks into a generated file. |
| Relative imports only | The table imports each mapper as `./pf/…`, so the folder is self-contained and portable. |
| Whole table replaced on load | Every load registers exactly the batches in the file and nothing from before. |
| No build order | The client's own build gives each batch its id and each mapper its hash from the same source, so both sides agree whichever is built first. |
| Follows client edits | In dev the server watches the client project's batch files, regenerates the table on a change, and reloads the API. |

See [Vite](/rpc/devtools/vite#batch-transport) for the plugin reference, and [CLI](/rpc/devtools/cli) for the same output from `mion compile`.

::note
An alias, a namespace import, a local barrel or your own wrapper around `createMionRouter` all work. A wrapper shipped by another package (behind a declaration file) does not: a production build fails with BAT009, and the dev server only reports it. Add the import yourself in the module that creates the router:

```typescript
import './.mion/rpc/batches.generated.js';
```
::

## Batches From a Separate Client Project

When client and server share one project (a fullstack app, or one package with two entries), nothing points anywhere. When the client is a separate project, name its tsconfig in the server's Vite config. The client config needs nothing:

<code-import path="packages/examples/src/codegen/vite-server.config.ts" lang="ts [server vite.config.ts]" />

::note
That client project is then the only batch source. A `batch()` in the server's own program (a test or a script, for instance) never reaches the table, so the build fails with BAT008, naming each one. The dev server only reports it. Move it into the client project, or drop the pointer when client and server are one program.
::

::note
Next.js works the same way. A Next app is the client; your API's own build points at the app's tsconfig. See [Next.js](/rpc/devtools/nextjs#sharing-batches-with-your-api).
::

## Batch vs Single Route

`call()` and `batch([...]).call()` differ in the response shape:

::code-split
<code-import path="packages/examples/src/client/batch-vs-single.ts" lang="ts [client.ts]" />
<code-import path="packages/examples/src/client/batch-orders.routes.ts" lang="ts [server.routes.ts]" />
::

| Aspect | `route.call()` | `batch([routes...]).call()` |
|--------|----------------|-------------------------|
| **HTTP Requests** | One per route | One for all routes |
| **Result** | Single value | Array of values |
| **Error** | Single error | Array of errors |
| **Position** | Direct access | Index-based access |

::tip
**When to use a batch:**
- Fetching data for a page that needs multiple API calls
- Independent routes, or routes chained with `inputFrom`
- Reducing network latency in high-latency environments
::

## Error Handling in a Batch

The error array holds each error at the same index as its route:

```ts
const [[user, order], [userError, orderError]] = await batch([
    routes.users.getById('USER-123'),    // index 0
    routes.orders.getById('ORDER-404'),  // index 1, fails
]).call();

// user = {id: 'USER-123', name: 'John'}
// userError = undefined
// order = undefined
// orderError = RpcError<'order-not-found'>
```

::warning
A failing route does NOT stop the other routes. Each route in the batch is processed independently.
::

## Errors in Mapped Routes

A route that reads a mapped input depends on its source route:

| What happened | What you get |
| --- | --- |
| The source route returned a declared error | The source keeps its own error. The target does not run and its slot holds `batch-mapping-source-failed`, naming both routes. |
| The mapper function threw | The whole batch stops with one undeclared error, `batch-mapper-failed`, naming the two routes. |
| The source route threw an undeclared error | The batch stops with one undeclared error, as with any thrown error. |

## Serialization in a Batch

A batch serializes `Date`, `Map` and `Set` exactly like a single route call:

```ts
const testDate = new Date('2024-06-15T12:30:00.000Z');
const testMap = new Map([['a', 1], ['b', 2]]);

const [[date, map], [dateError, mapError]] = await batch([
    routes.getSameDate(testDate),
    routes.getSameMap(testMap),
]).call();

// date is a Date instance
// map is a Map instance
```

## Constraints

- [Same client instance:]{.text-highlighted} All routes in a batch must use the same client
- [At least one route:]{.text-highlighted} A batch requires at least one route

```ts
// ❌ This will throw an error
const {routes: routes1} = initClient<MyApi>({baseURL: 'http://server1.com'});
const {routes: routes2} = initClient<MyApi>({baseURL: 'http://server2.com'});

await batch([routes1.users.getById('USER-123'), routes2.orders.getById('ORDER-1')]).call();

// ✅ Use routes from the same client
const {routes} = initClient<MyApi>({baseURL: 'http://localhost:3000'});
await batch([routes.users.getById('USER-123'), routes.orders.getById('ORDER-1')]).call();
```
