## Feeding One Route Into Another

Use `inputFrom()` to feed the output of one route into the input of another. The mapping runs on the **server**, inside the same HTTP request, so a relationship costs no extra round trip. `.asArg()` gives you a typed placeholder for the value the server maps in.

::code-split
<code-import path="packages/examples/src/client/batch-input-from.ts" lang="ts [client.ts]" />
<code-import path="packages/examples/src/client/batch-orders.routes.ts" lang="ts [server.routes.ts]" />
::

The mapper can be written inline, or named after a function the server registers itself.

| Call shape | Where the mapper lives | What the server needs |
| --- | --- | --- |
| `inputFrom(order, (o) => o!.userId)` | Inline in your client code. The build copies it into the server | Nothing, the build does it |
| `inputFrom(order, 'toUserId')` | Registered on the server under the name | A `registerPureFn('mionjs::toUserId', fn)` plus an `allowInputMapper(inputMapperKey('toUserId'))` call |

<code-import path="packages/examples/src/introduction/pure-functions-examples.ts" lang="ts [server.ts]" commentStart="// start:register-named-mapper" commentEnd="// end:register-named-mapper" />

An inline mapper must be a **pure function**: no closures, no outside variables, no side effects. The build extracts its body and compiles it into the server, which runs it with no access to your client-side scope.

```ts
// ✅ Pure: only uses its input
inputFrom(order, (o) => o!.userId)

// ✅ Pure: inline computation is fine
inputFrom(order, (o) => o!.totalUSD * 100)

// ❌ Not pure: references an outside variable
const multiplier = 2;
inputFrom(order, (o) => o!.totalUSD * multiplier)
```

The rules every mapper must follow are the RunTypes [pure function](/runtypes/guide/pure-functions) rules.

## How a Batch Reaches the Server

A batch is defined once, in your client code, and the build does the rest:

1. The build reads every `batch([...])` call site and gives it an id, hashed from its ordered route ids and its mappings. The same batch anywhere gives the same id, and the id changes only when its routes or mappings change, so the same routes with a different mapper are simply another batch.
2. The build compiles a table of id to definition (routes plus mappings) into the server.
3. The client sends only the id, `POST /mion-batch?id=<batchId>`, with the route inputs in the body.
4. The server looks the id up, runs the routes and the mappings, and answers in one round trip.

::note
The batch definition never travels on the wire. The server runs only the batches and the mappers its own build compiled in.
::

## Writing a Batch the Build Can Read

The build has to see the routes of every batch. Write each element as a route call, either inline in the array or bound to a `const` / `let` in the same file. Anything else is a build error, since a batch the build cannot read has no id and can never be sent.

| The build reports | Example |
| --- | --- |
| An element that is not a readable route call | A spread (`...routes`), a value from a function parameter, a route built in a loop |
| A mapping whose source route is outside the batch | `inputFrom(other, ...)` where `other` is not in the array, or comes after its target |

```ts
// ✅ Inline route calls
batch([routes.users.getById('U1'), routes.orders.list()]).call();

// ✅ Route calls bound to a const in the same file
const user = routes.users.getById('U1');
const orders = routes.orders.list();
batch([user, orders]).call();

// ❌ The build cannot read a spread or a parameter
function run(extra: RouteSubRequest[]) {
  return batch([routes.users.getById('U1'), ...extra]).call();
}
```

## What the Server Refuses

The server keeps its own table of batch ids and looks the id up before reading the body. An id it does not know is refused with `batch-unknown-id` (404), so an unknown request costs no work.

A client built without the mion build plugin has no batch ids, so `batch()` throws `batch-missing-id` and nothing is sent. Single route calls work as before. The metadata route lists the registered batch ids, so a hand-written client can still call a batch by id.

## Build Configuration

The Vite plugin moves batches from the client build to the server build through a manifest, with the `batches` option:

- On the **client** build, set `batches.emit` to a manifest path. The plugin writes every batch it read, and every inline mapper, to `.mion/batches.json`.
- On the **server** build, set `batches.consume` to that same path. The plugin compiles the table into `.mion/batches.generated.js` and imports it for you from whichever module calls `initMionRouter`. Nothing to import by hand.

## Batch vs Single Route

The difference between `call()` and `batch([...]).call()` is in the response structure:

| Aspect | `route.call()` | `batch([routes...]).call()` |
|--------|----------------|-------------------------|
| **HTTP Requests** | One per route | One for all routes |
| **Result** | Single value | Array of values |
| **Error** | Single error | Array of errors |
| **Position** | Direct access | Index-based access |

::code-split
<code-import path="packages/examples/src/client/batch-vs-single.ts" lang="ts [client.ts]" />
<code-import path="packages/examples/src/client/batch-orders.routes.ts" lang="ts [server.routes.ts]" />
::

```ts
// Single route call: direct result/error
const [result, error, fatal, middleFnResults, middleFnErrors] = await route.call();

// Batch: arrays of results/errors; `fatal` is request-scoped (ONE slot for the whole batch)
const [[result1, result2], [error1, error2], fatal, middleFnResults, middleFnErrors] = await batch([route1, route2]).call();
```

::tip
**When to use a batch:**
- Fetching data for a page that needs multiple API calls
- Operations that do not depend on each other
- Reducing network latency in high-latency environments
::

## Error Handling in a Batch

Each route in a batch can succeed or fail on its own. The error array holds each error at the same index as its route:

```ts
const [[user, order], [userError, orderError]] = await batch([
    routes.users.getById('USER-123'),    // index 0
    routes.orders.getById('ORDER-404'),  // index 1 - this will fail
]).call();

// Results:
// user = {id: 'USER-123', name: 'John'}  - success
// userError = undefined

// order = undefined                      - failed
// orderError = RpcError<'order-not-found'>
```

::warning
A failing route does NOT stop the other routes. Each route in the batch is processed independently.
::

## Serialization in a Batch

Complex types like `Date`, `Map`, and `Set` are serialized and deserialized in a batch exactly like in single route calls:

```ts
const testDate = new Date('2024-06-15T12:30:00.000Z');
const testMap = new Map([['a', 1], ['b', 2]]);

const [[date, map], [dateError, mapError]] = await batch([
    routes.getSameDate(testDate),
    routes.getSameMap(testMap),
]).call();

// date is a Date instance
// map is a Map instance
```

## Constraints

::stylish-list
---
type: x
---
- [Same client instance:]{.text-highlighted} All routes in a batch must use the same client
- [At least one route:]{.text-highlighted} A batch requires at least one route
- [Readable by the build:]{.text-highlighted} Every route must be written inline or bound to a const in the same file
::

```ts
// ❌ This will throw an error
const {routes: routes1} = initClient<MyApi>({baseURL: 'http://server1.com'});
const {routes: routes2} = initClient<MyApi>({baseURL: 'http://server2.com'});

await batch([routes1.users.getById('USER-123'), routes2.orders.getById('ORDER-1')]).call(); // Error!

// ✅ Use routes from the same client
const {routes} = initClient<MyApi>({baseURL: 'http://localhost:3000'});
await batch([routes.users.getById('USER-123'), routes.orders.getById('ORDER-1')]).call(); // Works!
```
