## The Result Pattern

`call()` returns a tuple with 5 slots. Most of the time you read the first two, what the route returned and the error it declared. The last three are for the occasional case.

::code-split
<code-import path="packages/examples/src/client/result-short.ts" lang="ts [the two slots you need]" />
<code-import path="packages/examples/src/client/result-full.ts" lang="ts [all five slots]" />
::

Every error lands in exactly one slot:

| Slot | Name | What it holds |
| --- | --- | --- |
| 0 | result | What the route returned, if it ran and succeeded. |
| 1 | error | The route's declared errors plus `ValidationError`. A closed, strongly typed union. |
| 2 | fatal | Anything nobody declared: a transport failure (timeout, abort, network), a platform error, a framework error, or an undeclared throw. An open `RpcError<string>`. |
| 3 | middleFnResults | Middleware function results, by name. |
| 4 | middleFnErrors | Each middleware function's declared errors plus `ValidationError`, by name, one slot per function so nothing is lost when several fail. |

::note
The result tuple is built by the client. Your handlers stay plain functions that return a value or an `RpcError`, the server never deals with this shape.
::

::tip
Only what a handler declared is strongly typed: the route's errors in slot 1, and each middleware function's errors in slot 4 (see [Prefilling Middleware Functions](#prefilling-middleware-functions)). Everything undeclared goes to `fatal`, untyped.
::

::

## Prefill vs Call with Middleware Functions

| Aspect | `.prefill()` | `.call({middleFns: ...})` |
|--------|--------------|-------------------|
| **Persistence** | Data stored for ALL future requests | Data sent with this request only |
| **Error handlers** | Persistent via `.prefill().onError()` | Same `.onError()` API, registered directly on the middleware function (no prefill needed) |
| **Use case** | Auth tokens, session data | Metadata related to the request |
