A cancelled request comes back with `type === 'request-aborted'` in the **fatal** slot. Transport failures are never part of the route's typed error union.

::tip
A cancel started by the user is not a failure. Ignore `request-aborted` in your UI instead of showing an error.
::

## Aborting Mutations

Aborting stops the **client** from waiting. It does not undo work on the server. By the time the signal fires, the server may not have received the request, may be halfway through it, or may already have committed it.

::warning
Treat an aborted mutation as **unknown**, not as **failed**. There is no client-side way to tell the difference.
::

`client.abort()`, the per-request `signal` and `timeout` are best effort: they end the client-side wait cleanly, and the server sees the same thing it would see if the connection had dropped.

::tip
Two things make this safe. Send an idempotency key with each logical action, so the server can return the stored result when you retry. And after an abort, refetch the affected resource and show "syncing" rather than "failed".
::

Cancelling a `query()` is always safe, the worst case is wasted work on the server. See [Queries and Mutations](/rpc/client/client-overview#queries-and-mutations).
