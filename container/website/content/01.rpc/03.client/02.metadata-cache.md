---
title: What the Client Remembers
description: The client keeps what it learns about your routes, so a later visit starts faster.
toc: false
---

The first time your app calls a route, the client asks the server how that route works: how to check its
params, how to put them on the wire, how to read the answer back. It keeps that, so the next visit does
not have to ask again.

## Where It Is Kept

In the browser's own database (IndexedDB), one entry per server, under your site's own storage. Nothing
is shared with any other site, and nothing is sent anywhere.

On a server (during server side rendering), in a Web Worker, or in a browser where storage is turned off,
the client keeps the same data in memory for the life of the process instead. Everything works the same,
it just starts fresh each time.

## What It Holds

| Kept | Why |
| --- | --- |
| Each route's description | Its params, its result, and how both travel |
| The compiled check and convert functions | So params are checked in the browser before anything is sent |

Nothing about your users, and nothing you passed to a route. Only the shape of your API.

## Why It Makes Things Faster

Without it, the first call of every page has to guess how the route works and be told it was wrong, which
costs a second trip to the server. With it, a returning visitor's first call goes out already knowing.

## What A Browser May Clear

This cache is a cache, so a browser is free to drop it. Two cases worth knowing:

- **Running low on space.** The browser clears site storage to make room. Your app just asks the server
  again on the next call.
- **Safari, after seven days.** Safari clears everything a site's scripts have stored once someone has
  used the browser for seven days without visiting your site. That covers every kind of storage, so no
  choice of store avoids it. Visiting the site resets the clock, and a site added to the home screen has
  its own separate counter.

Nothing breaks when it is cleared. The client notices what is missing and asks the server for it.

## Asking The Browser To Keep It

Browsers can mark your site's storage as worth keeping, so it survives a clean up. Some browsers ask the
person for permission first, and mion never triggers a permission popup on its own. It only marks the
storage when the browser has already decided to allow it, which needs nothing from you.

If you want to ask directly, do it yourself, ideally right after something the person did (a sign in, for
example) so the request makes sense to them:

```ts
import {requestPersistentStorage} from '@mionjs/client';

const kept = await requestPersistentStorage();
```

## When Something Cannot Be Stored

If the browser refuses to store the cache and there is no more room to free, your call still works: the
cache is only ever a shortcut. The failure comes back on your next call, in the third slot of the result,
so you can log it or tell the person if you want to:

```ts
const [result, error, undeclared] = await routes.sayHello(user).call();

if (undeclared?.type === 'metadata-cache-error') {
  console.warn('running without the local cache');
}
```
