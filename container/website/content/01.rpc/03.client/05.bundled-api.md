By default the client asks the server how a route works on first use (see
[What the Client Remembers](/rpc/client/metadata-cache)). With `bundleApi` on, the build compiles the
same validators and serializers the server holds, for every route your code calls, and ships them as real
functions. Your client code does not change.

## Choosing a Mode

Pick `bundled` when dynamic code is not allowed (a strict Content Security Policy, an edge runtime) or
when the first call has to be as fast as any other. Pick `mixed` when some calls go through code the build
cannot follow.

| `bundleApi` | First call of a route | Browser cache | Works under a strict CSP |
| --- | --- | --- | --- |
| off (default) | Asks the server for the route's metadata | Kept in the browser | No, the functions are built at runtime |
| `bundled` | Nothing to ask, unless the build missed the route | Only for a route the build missed | Only while every call is bundled |
| `mixed` | Bundled routes need nothing; a route the build could not see is fetched as usual | Only for fetched routes | Only while every call is bundled |

## What a Bundled Build Downloads

The code that asks the server how a route works ships as a file of its own. A `bundled` client downloads
it only when it needs it: a route the build never saw, or a server that changed since the build.

::tip
Under `bundled`, a call to a route the build never saw still works: the client fetches that route and
builds its functions at runtime, which a strict Content Security Policy blocks. The build warns about such
a call ([MET003](/runtypes/diagnostics/all-diagnostics)).
::

## What Counts as a Call

The build bundles a route when the program calls it: `.call()` or `.typeErrors()` on a route, and every
route inside a `batch([...]).call()`. Each route also brings the
middleware of its chain, such as an auth headers middleware it runs behind.

## Typing Call Helpers

The route's name travels in the type of the sub request. A generic helper, as in the example above, keeps
it. A helper typed with the wide `RouteSubRequest<any>` erases it, and the build reports where:
[MET003](/runtypes/diagnostics/all-diagnostics) under `bundled`, where that call is fetched and a strict
Content Security Policy blocks it, and [MET004](/runtypes/diagnostics/all-diagnostics) under `mixed`, where
it is fetched instead.

## Resolving Types in the API Project

Client and API can live in two projects, and different `lib` or strictness settings compile the same type
into a different function. Set `api.tsConfig` to the project that declares the API, and the build resolves
every route's params and return there, so the client ships exactly what the server compiled. Leave it out
when client and API share one project.

::note
The API project has to initialize its routes once (`mion.initRoutes(routes)`). The build reads the routes
from that call, and reports a program that declares the same routes in several calls
([MET005](/runtypes/diagnostics/all-diagnostics)).
::

## Checking a Release

Both builds write `api/manifest.json` under the gen dir, listing the routes they compiled. The
`mion api-check` command compares the two and fails when a bundled route no longer matches the server, for
example after a route's type changed and the client was not rebuilt.

```bash
mion api-check --server-gen-dir ../api/.mion --client-gen-dir .mion
```

It needs no network, so it runs in any CI job that has both build outputs. See
[Checking a Client Against Its Server](/rpc/devtools/cli#checking-a-client-against-its-server).

## Checking the Version at Runtime

The server sends `x-build-version` on every response, the version of the API it was built from. Your
client build gets the same value from the same route types. When they differ, the client checks each route
inside its first call. A bundled route whose types or wire format changed is reported: reload the app or
rebuild. A route fetched from the server is fetched again and saved.

```ts
const [result, error, undeclared] = await routes.sayHello(user).call();
// the call still answers; the third slot holds mion's own errors, not your route's
// undeclared?.type === 'api-version-mismatch', reported once per client
```

::note
A matching version costs nothing: no extra request, no extra bytes, no storage. A route you never call is
never checked. The client skips the check when it cannot read the header, as on a browser from another
origin. Turn the header off with `apiVersionCheck: false` in `createMionRouter`, and the client stops
checking too.
::

::tip
With `syncRoutes` on, a bundled route whose types or wire format changed is stopped before it runs, see
[Keeping Client and Server in Sync](/rpc/client/route-sync).
::
