By default the client asks the server how a route works on first use (see
[What the Client Remembers](/rpc/client/metadata-cache)). With `bundleApi` on, the build does that work
instead: for every route your code calls, it compiles the same validators and serializers the server
holds and ships them as real functions.

## Choosing a Mode

Pick `bundled` when dynamic code is not allowed (a strict Content Security Policy, an edge runtime) or
when the first call has to be as fast as any other. Pick `mixed` when some calls go through code the build
cannot follow.

| `bundleApi` | First call of a route | Browser cache | Works under a strict CSP |
| --- | --- | --- | --- |
| off (default) | Asks the server for the route's metadata | Kept in the browser | No, the functions are built at runtime |
| `bundled` | Nothing to ask: everything came with the build | Never touched | Yes, the bundle carries ready functions |
| `mixed` | Bundled routes need nothing; a route the build could not see is fetched as usual | Only for fetched routes | Only while every call is bundled |

## What a Bundled Build Leaves Out

A `bundled` client never asks the server how a route works, so the metadata request and the browser cache
stay out of your bundle. A `mixed` client keeps that code, because a route the build could not see is
still fetched.

::tip
Under `bundled`, a call to a route the build never saw fails with `route-metadata-not-found`, naming the
option. Under `mixed` the same call is fetched from the server.
::

## What Counts as a Call

The build bundles a route when the program calls it: `.call()` on a route, `.prefill()` on a middleFn,
`.typeErrors()` on either, and every route inside a `batch([...]).call()`. Each route also brings the
middleFns of its chain, such as an auth headers middleFn it runs behind.

The route's name travels in the type of the sub request. A helper that keeps that type generic, as in the
example above, keeps the name. A helper typed with the wide `RouteSubRequest<any>` erases it, and the
build reports where: [MET003](/runtypes/diagnostics/all-diagnostics) under `bundled`, where that call fails
at runtime, and [MET004](/runtypes/diagnostics/all-diagnostics) under `mixed`, where it is fetched
instead.

## Resolving Types in the API Project

Client and API can live in two projects, and different `lib` or strictness settings compile the same type
into a different function. Set `api.tsConfig` to the project that declares the API, and the build resolves
every route's params and return there, so the client ships exactly what the server compiled. Leave it out
when client and API share one project.

::note
The API project has to initialize its routes once (`mion.initRoutes(routes)`). The build reads the routes
from that call, and reports a program that declares the same routes in several calls
([MET005](/runtypes/diagnostics/all-diagnostics)).
::

## Checking a Release

Both builds write `api/manifest.json` under the gen dir, describing the routes they compiled: the
server's from its routes, the client's from what it bundled. The `mion api-check` command compares the
two and fails when a bundled route no longer matches the server, for example after a route's type changed
and the client was not rebuilt.

```bash
mion api-check --server-gen-dir ../api/.mion --client-gen-dir .mion
```

It reads two files and needs no network, so it runs in any CI job that has both build outputs. See
[Checking a Client Against Its Server](/rpc/devtools/cli#checking-a-client-against-its-server).
