By default the client learns how a route works on first use: it asks the server, keeps the answer in the
browser, and rebuilds the compiled functions from it (see [What the Client Remembers](/rpc/client/metadata-cache)).
With `bundleApi` on, the build does that work instead. For every route your code calls, it compiles the
same validators and serializers the server holds and ships them with the call, as real functions.

Your client code does not change. Each route call already names its route in its type, so the build
knows what to bundle from the calls you write.

## Choosing a Mode

| `bundleApi` | First call of a route | Browser cache | Works under a strict CSP |
| --- | --- | --- | --- |
| off (default) | Asks the server for the route's metadata | Kept in the browser | No, the functions are built at runtime |
| `bundled` | Nothing to ask: everything came with the build | Never touched | Yes, the bundle carries ready functions |
| `mixed` | Bundled routes need nothing; a route the build could not see is fetched as usual | Only for fetched routes | Only while every call is bundled |

Pick `bundled` when the app runs where dynamic code is not allowed (a strict Content Security Policy, an
edge runtime) or when the first call has to be as fast as any other. Pick `mixed` when some calls go
through code the build cannot follow and you want them to keep working.

::tip
Under `bundled`, a call to a route the build never saw fails with `route-metadata-not-found`, naming the
option. Under `mixed` the same call is fetched from the server.
::

## What Counts as a Call

The build bundles a route when the program calls it: `.call()` on a route, `.prefill()` on a middleFn,
`.typeErrors()` on either, and every route inside a `batch([...]).call()`. Along with each route come the
middleFns of its execution chain, so an auth headers middleFn the route runs behind is bundled with it.

The route's name travels in the type of the sub request. A helper that keeps that type generic, as in the
example above, keeps the name. A helper typed with the wide `RouteSubRequest<any>` erases it, and the
build tells you where: [MET003](/runtypes/diagnostics/all-diagnostics) under `bundled`, where that call
will fail at runtime, and [MET004](/runtypes/diagnostics/all-diagnostics) under `mixed`, where it is
fetched instead.

## Resolving Types in the API Project

Client and API can live in two projects with two tsconfigs. Different `lib` or strictness settings can
compile the same type into a different function. `api.tsConfig` names the project that declares the API.
With it set, the build resolves every route's params and return in that program, so the client ships
exactly what the server compiled.

Leave it out when client and API share one project. Then there is one program, and nothing can differ.

::note
The API project has to initialize its routes once (`mion.initRoutes(routes)`). That call is where the
build reads the routes from, and a program that declares the same routes in several calls is reported
([MET005](/runtypes/diagnostics/all-diagnostics)).
::

## Checking a Release

Both builds write a small file describing the routes they compiled, `api/manifest.json` under the gen
dir: the server's from its routes, the client's from what it bundled. The `mion api-check` command
compares the two and fails when a bundled route no longer matches the server, which is what happens
when a route's type changed on the server and the client was not rebuilt.

```bash
mion api-check --server-gen-dir ../api/.mion --client-gen-dir .mion
```

It reads two files and needs no network, so it fits any CI job that has both build outputs. See
[Checking a Client Against Its Server](/rpc/devtools/cli#checking-a-client-against-its-server).
