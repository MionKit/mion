## Result Mapping with `serverMapFrom`

Use `serverMapFrom()` to feed the output of one route into the input of another. The mapping is resolved **server-side**, inside the same HTTP request, so a relationship costs no extra round trip.

::code-split
<code-import path="packages/examples/src/client/workflow-mapFrom.ts" lang="ts [client.ts]" />
<code-import path="packages/examples/src/client/flow-orders.routes.ts" lang="ts [server.routes.ts]" />
::

### How it works

1. `serverMapFrom(sourceRoute, mapperFn)` creates a reference to the source route's output
2. `.asArg()` provides a type-safe placeholder so TypeScript can infer the result types
3. At **build time**, the mion plugin harvests the mapper function from your client source and bundles it into the **server**
4. At **runtime**, the server executes the first route, runs the mapper function, and passes the mapped value as input to the second route

::note
The request carries only the mapper's registry key, never its body, so the server runs only functions its own build baked in.
::

### Pure functions requirement

The mapper function passed to `serverMapFrom` must be a **pure function**: no closures, no external variables, no side effects. Its body is extracted at build time and bundled into the server, which runs it in its own context with no access to your client-side scope.

```ts
// ✅ Pure function — only uses the input parameter
serverMapFrom(order, (o) => o!.userId)

// ✅ Pure function — inline computation is fine
serverMapFrom(order, (o) => o!.totalUSD * 100)

// ❌ NOT pure — references external variable
const multiplier = 2;
serverMapFrom(order, (o) => o!.totalUSD * multiplier)
```

The rules every mapper must follow are the RunTypes [pure function](/runtypes/guide/pure-functions) rules.

### Vite plugin configuration

`serverMapFrom` mappers are written in **client** code but must run on the **server**, so the mion Vite plugin moves them between the two builds through a manifest:

- On the **client** build, set `serverMappers.emit` to a manifest path, the plugin harvests every inline `serverMapFrom` mapper and writes it there.
- On the **server** build, set `serverMappers.consume` to that same path, the plugin compiles those mappers into `.mion/server-mappers.generated.js` and imports it for you from whichever module calls `initMionRouter`. Nothing to import by hand.

::code-split
<code-import path="packages/examples/src/client/server-mappers-client.vite.config.ts" lang="ts [client vite.config.ts]" />
<code-import path="packages/examples/src/client/server-mappers-server.vite.config.ts" lang="ts [server vite.config.ts]" />

::note

## RoutesFlow vs Single Route Call

The key difference between `call()` and `routesFlow()` is in the response structure:

| Aspect | `route.call()` | `routesFlow([routes...]).call()` |
|--------|----------------|-------------------------|
| **HTTP Requests** | One per route | One for all routes |
| **Result** | Single value | Array of values |
| **Error** | Single error | Array of errors |
| **Position** | Direct access | Index-based access |

::code-split
<code-import path="packages/examples/src/client/workflow-vs-single.ts" lang="ts [client.ts]" />
<code-import path="packages/examples/src/client/flow-orders.routes.ts" lang="ts [server.routes.ts]" />
::

### Response Pattern Comparison

```ts
// Single route call - direct result/error
const [result, error, fatal, middleFnResults, middleFnErrors] = await route.call();

// RoutesFlow - arrays of results/errors; `fatal` is request-scoped (ONE slot for the whole flow)
const [[result1, result2], [error1, error2], fatal, middleFnResults, middleFnErrors] = await routesFlow([route1, route2]).call();
```

::tip
**When to use routesFlow:**
- Fetching data for a page that needs multiple API calls
- Batch operations that don't depend on each other
- Reducing network latency in high-latency environments
::

## Error Handling in RoutesFlows

In a routes flow, each route can succeed or fail independently. The error array contains errors at the same index as their corresponding routes:

```ts
const [[user, order], [userError, orderError]] = await routesFlow([
    routes.users.getById('USER-123'),    // index 0
    routes.orders.getById('ORDER-404'),  // index 1 - this will fail
]).call();

// Results:
// user = {id: 'USER-123', name: 'John'}  - success
// userError = undefined

// order = undefined                      - failed
// orderError = RpcError<'order-not-found'>
```

::warning
A failing route does NOT stop other routes from executing. Each route in the routes flow is processed independently.
::

## Serialization in RoutesFlows

Complex types like `Date`, `Map`, and `Set` are automatically serialized and deserialized in routes flows, just like single route calls:

```ts
const testDate = new Date('2024-06-15T12:30:00.000Z');
const testMap = new Map([['a', 1], ['b', 2]]);

const [[date, map], [dateError, mapError]] = await routesFlow([
    routes.getSameDate(testDate),
    routes.getSameMap(testMap),
]).call();

// date is a Date instance
// map is a Map instance
```

## Constraints

::stylish-list
---
type: x
---
- [Same client instance:]{.text-highlighted} All routes in a routes flow must use the same client
- [At least one route:]{.text-highlighted} A routes flow requires at least one route subrequest
::

```ts
// ❌ This will throw an error
const {routes: routes1} = initClient<MyApi>({baseURL: 'http://server1.com'});
const {routes: routes2} = initClient<MyApi>({baseURL: 'http://server2.com'});

await routesFlow([routes1.users.getById('USER-123'), routes2.orders.getById('ORDER-1')]).call(); // Error!

// ✅ Use routes from the same client
const {routes} = initClient<MyApi>({baseURL: 'http://localhost:3000'});
await routesFlow([routes.users.getById('USER-123'), routes.orders.getById('ORDER-1')]).call(); // Works!
```
