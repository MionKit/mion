## A clean type when you need one

`FromJsonSchema` recovers the exact type the pipeline enforces, and constraint keywords ride along inside it as internal metadata. For a hover, a generated document or a plain annotation over data that arrives from elsewhere, `JsonSchemaType` gives the same shape with that metadata stripped: formats collapse to their base and the machinery disappears. Any value the schema validates is assignable to it. When a schema position accepts any JSON value at all (a bare pattern or minimum constrains only one type, and other values pass by definition), the clean type names that domain `JsonValue` instead of spelling out the whole union.

The clean type is for annotations only. Passing it to a factory would build functions with every constraint deleted, because the stripped metadata is exactly what the generated functions are built from. Hand the factories the schema itself, as every example on this page does.

## Which keywords map to what

Draft 2020-12, and these tables are total: every keyword the dialect defines appears exactly once below, with the two spellings it maps to. Every constraint accepted is a constraint enforced, at build time when a type can carry it and inside the generated validator when it cannot.

A shape can therefore migrate from a JSON Schema to a TypeScript type (or back) without changing what gets enforced, and matching spellings land on one generated function. `TF` comes from `@ts-runtypes/core/formats` and `RT` from `@ts-runtypes/core/builders`.

### Types

| Keyword | In a schema | As a type | As a builder |
| --- | --- | --- | --- |
| `type` | `{type: 'string'}` | `string`, `number`, `boolean`, `null` | `TF.string()`, `TF.number()`, `RT.boolean()`, `RT.literal(null)` |
| `type` (integer) | `{type: 'integer'}` | `TF.Integer` | `TF.integer()` |
| `type` (array form) | `{type: ['string', 'null']}` | `string \| null` | `RT.union([TF.string(), RT.literal(null)])` |
| `const` | `{const: 'pending'}` | `'pending'` | `RT.literal('pending')` |
| `enum` | `{enum: ['red', 'blue']}` | `'red' \| 'blue'` | `RT.union([RT.literal('red'), RT.literal('blue')])` |

A bare `true` or `{}` as a subschema recovers `unknown` (`RT.unknown()`), and `false` recovers `never` (`RT.never()`).

### Objects

| Keyword | In a schema | As a type | As a builder |
| --- | --- | --- | --- |
| `properties` | `{properties: {id: {...}}}` | an object type with those members | `RT.object({id: ...})` |
| `required` | `{required: ['id']}` | a member left out gets `?` | `RT.optional(...)` on the members left out |
| `additionalProperties` (schema) | `{additionalProperties: {type: 'number'}}` | an intersection with `Record<string, V>` | `RT.intersection([shape, RT.record(v)])` |
| `additionalProperties: false` | `{additionalProperties: false}` | the shape really closes | `RT.object(config)` stays exact |
| `minProperties` / `maxProperties` | `{minProperties: 1}` | `TF.FormattedObject<Base, {minProperties: 1}>` | `RT.object(config, {minProperties: 1})` |
| `patternProperties` | `{patternProperties: {'^col_': {...}}}` | `TF.FormattedObject<Base, {patternProperties: {'^col_': number}}>` | `RT.record(inner, {patternProperties: {'^col_': TF.number()}})` |
| `propertyNames` | `{propertyNames: {pattern: '^[a-z]+$'}}` | `TF.FormattedObject<Base, {propertyNames: Key}>` | `RT.record(inner, {propertyNames: keys})` |
| `dependentRequired` | `{dependentRequired: {card: ['cvv']}}` | a union of the allowed combinations | `RT.dependentRequired({card: ['cvv']})` |
| `dependentSchemas` | `{dependentSchemas: {card: {...}}}` | a union of the allowed combinations | `RT.dependentSchemas({card: RT.object({...})})` |

### Arrays and tuples

| Keyword | In a schema | As a type | As a builder |
| --- | --- | --- | --- |
| `items` | `{items: {type: 'string'}}` | `Item[]` | `RT.array(item)` |
| `prefixItems` | `{prefixItems: [a, b], items: r}` | `[A, B, ...Rest[]]` | `RT.tuple([a, b], rest)` |
| `prefixItems` (boolean slots) | `{prefixItems: [true, false]}` | `true` leaves a position unconstrained, `false` forbids it | the matching tuple slots |
| `minItems` | `{minItems: 2}` | `TF.FormattedArray<T[], {minItems: 2}>`, or required tuple slots beside `prefixItems` | `RT.array(item, {minItems: 2})` |
| `maxItems` | `{maxItems: 5}` | `TF.FormattedArray<T[], {maxItems: 5}>` | `RT.array(item, {maxItems: 5})` |
| `uniqueItems` | `{uniqueItems: true}` | `TF.FormattedArray<T[], {uniqueItems: true}>` | `RT.array(item, {uniqueItems: true})` |
| `contains` | `{contains: {format: 'uuid'}}` | `TF.FormattedArray<Base, {contains: Item}>` | `RT.array(item, {contains: TF.uuid()})` |
| `minContains` / `maxContains` | `{contains: c, minContains: 2}` | `TF.FormattedArray<Base, {contains: Item; minContains: 2}>` | `RT.array(item, {contains: c, minContains: 2})` |

Trailing optional slots come from `prefixItems` entries past `minItems`: two prefix entries with `minItems: 1` recover `[A, B?]`, written `RT.tuple([a], [b])`.

### Strings

| Keyword | In a schema | As a type | As a builder |
| --- | --- | --- | --- |
| `format` | `{format: 'email'}` | `TF.EmailAddress`, `TF.IdnEmail`, `TF.UUID`, `TF.StringDate`, `TF.StringTime`, `TF.StringDateTime`, `TF.StringDuration`, `TF.Hostname`, `TF.IdnHostname`, `TF.IPv4`, `TF.IPv6`, `TF.Uri`, `TF.UriReference`, `TF.UriTemplate`, `TF.Iri`, `TF.IriReference`, `TF.RegexString`, `TF.JsonPointer`, `TF.RelativeJsonPointer` | `TF.emailAddress()`, `TF.uuid()`, `TF.stringDate()` and the rest |
| `minLength` / `maxLength` | `{minLength: 2, maxLength: 60}` | `TF.String<{minLength: 2; maxLength: 60}>` | `TF.string({minLength: 2, maxLength: 60})` |
| `pattern` | `{pattern: '^[a-z]+$'}` | `TF.String<{pattern: {source: '^[a-z]+$'}}>` | `TF.string({pattern: {source: '^[a-z]+$'}})` |
| `contentEncoding` | `{contentEncoding: 'base64'}` | `TF.Base64`, `TF.Base32`, `TF.Base16` | `TF.base64()`, `TF.base32()`, `TF.base16()` |
| `contentMediaType` | `{contentMediaType: 'application/json'}` | `TF.JsonContent`, or `TF.JsonContentBase64` behind an encoding | `TF.jsonContent()`, `TF.jsonContentBase64()` |

Length is counted in characters, not in the units a JavaScript string happens to store. An emoji counts as one, so `'💩💩'` fits `maxLength: 2`.

A `pattern` is a regular expression read in unicode mode, which is what lets `\p{Letter}` and the other property escapes mean what they say.

### Numbers

| Keyword | In a schema | As a type | As a builder |
| --- | --- | --- | --- |
| `minimum` / `maximum` | `{minimum: 0, maximum: 120}` | `TF.Number<{min: 0; max: 120}>` | `TF.number({min: 0, max: 120})` |
| `exclusiveMinimum` / `exclusiveMaximum` | `{exclusiveMinimum: 0}` | `TF.Number<{gt: 0; lt: 1}>` | `TF.number({gt: 0, lt: 1})` |
| `multipleOf` | `{multipleOf: 5}` | `TF.Number<{multipleOf: 5}>` | `TF.number({multipleOf: 5})` |

The JSON spellings are accepted on the type side too, so `TF.Number<{minimum: 0}>` and `TF.Number<{min: 0}>` are the same type.

`multipleOf` takes any positive number, whole or not, so `{multipleOf: 0.01}` on a price works. A value counts as a multiple when dividing it by the step gives a whole number, which is the rule the spec states.

### Combinators and negation

| Keyword | In a schema | As a type | As a builder |
| --- | --- | --- | --- |
| `anyOf` | `{anyOf: [a, b]}` | a plain union `A \| B`, or `RT.AnyOf<[A, B]>` | `RT.union([a, b])` or `RT.anyOf([a, b])` |
| `oneOf` | `{oneOf: [a, b]}` | `RT.OneOf<[A, B]>`, exactly one branch, enforced | `RT.oneOf([a, b])` |
| `allOf` | `{allOf: [a, b]}` | an intersection `A & B` | `RT.intersection([a, b])` |
| `not` | `{not: {format: 'email'}}` | `TF.Not<TF.Email>` | `RT.not(TF.email())` |

A `not` over a value list rather than a format recovers a string with disallowed values, written `TF.string({disallowedValues: {...}})`.

### Conditionals

| Keyword | In a schema | As a type | As a builder |
| --- | --- | --- | --- |
| `if` / `then` / `else` | `{if: c, then: t, else: e}` | a union of the two outcomes | `RT.conditional({if: c, then: t, else: e})` (format conditions) |

### References

| Keyword | In a schema | As a type | As a builder |
| --- | --- | --- | --- |
| `$defs` | `{$defs: {Node: {...}}}` | named types referring to each other | run-types held in variables |
| `$ref` | `{$ref: '#/$defs/Node'}` | the referenced type | the variable holding that run-type |
| `$ref` to the root | `{$ref: '#'}` | a recursive type | `RT.circular(...)` with `RT.self()` |
| `$anchor` / `$dynamicAnchor` | `{$anchor: 'node'}` | a name a `$ref` can target | the same variable, named |
| `$dynamicRef` | `{$dynamicRef: '#node'}` | the anchored type, resolved statically | the variable it resolves to |

### Unevaluated

| Keyword | In a schema | As a type | As a builder |
| --- | --- | --- | --- |
| `unevaluatedProperties` | `{unevaluatedProperties: false}` | the object type is unchanged, the check is enforced | `RT.object(config)` |
| `unevaluatedItems` | `{unevaluatedItems: false}` | the array type is unchanged, the check is enforced | `RT.array(item)` |

These two are the clearest case of a rule that is enforced without being spelled in the type. Both ask what the rest of the schema already covered, and often that answer depends on the value in front of you: a branch of `anyOf` only counts the keys it declares when that branch actually passed, and an `else` only counts its positions when the `if` failed. So the recovered type stays the plain object or array, and the generated validator carries the counting. You get exactly the checking the spec describes, and a type that reads the way you would have written it by hand:

```ts
const schema = {
  properties: {foo: {type: 'string'}},
  anyOf: [{properties: {bar: {const: 'bar'}}, required: ['bar']}],
  unevaluatedProperties: false,
} as const;
// {foo: 'a', bar: 'bar'}        accepted, the branch that declares bar passed
// {foo: 'a', bar: 'bar', baz: 1} rejected, nothing evaluated baz
```

### Annotations

These describe the schema rather than the data, so they are read and ignored at every position. The type does not change and nothing extra is enforced.

| Keyword | In a schema | As a type | As a builder |
| --- | --- | --- | --- |
| `title`, `description`, `examples`, `default`, `$comment`, `deprecated`, `readOnly`, `writeOnly` | `{title: 'User'}` | nothing, the type is unchanged | nothing |
| `$schema`, `$id`, `$vocabulary` (at the root) | `{$schema: '...2020-12/schema'}` | nothing, the type is unchanged | nothing |

An ignored keyword can still read like an instruction, so the lint plugin warns when one carries intent nothing will enforce: a `readOnly` or `writeOnly` set to true, a `then` or `else` without `if`, a `minContains` or `maxContains` without `contains` (the `runtypes/json-schema-dropped-intent` rule on the [Linting](/guide/linting) page). The schema still builds; the warning tells you what was dropped. If you want the readonly modifier on a member, spell it in TypeScript or with `RT.propMod({readonly: true}, field)`.

Every string format the dialect defines is accepted and enforced: `email`, `idn-email`, `uuid` (any version, as the spec intends), `date`, `time`, `date-time`, `duration`, `hostname`, `idn-hostname`, `ipv4`, `ipv6`, `uri`, `uri-reference`, `uri-template`, `iri`, `iri-reference`, `regex`, `json-pointer` and `relative-json-pointer`. A `format` value nobody defines is treated as the annotation the spec defaults it to: the type stays a plain string and nothing is silently half-checked.

Each keyword lowers to the format of the same name, and those formats read the keyword the way the spec does. `ipv4` accepts a dotted quad and turns down the word `localhost`, because the spec calls it an address. Where a format offers a wider reading, it is an option you turn on yourself rather than something the keyword assumes.

Three keywords lower to a format whose name differs, because the closest existing one means something narrower. `hostname` becomes `TF.Hostname`, which accepts a single label like `localhost` (`TF.Domain` wants a dotted name with a top level domain). `uri` becomes `TF.Uri`, which accepts any scheme including `mailto:` and `urn:` (`TF.Url` is the web address form, http and friends only). `email` becomes `TF.EmailAddress`, which accepts the whole addressing grammar, including a quoted local part like `"joe bloggs"@example.com` and an address literal like `joe@[127.0.0.1]` (`TF.Email` is the everyday shape most fields actually want). All three narrower formats are still there when a narrower check is what you want.

`hostname` and `idn-hostname` are checked properly rather than by shape alone. A label written as punycode (the `xn--` form) is decoded, and what it decodes to has to be a real name in its own right, spelled the one way punycode would spell it. An internationalized name also answers to the rules its scripts bring with them, so a character that is only allowed next to particular neighbours is checked against them, and a name carrying a right to left letter follows the ordering rules for those.

Keywords that assert something no TypeScript type can express, like `uniqueItems` or a `contains` count, still validate exactly: the generated function carries the check even though the recovered type stays the closest expressible shape.

::note
Anything the dialect does not define is rejected where you wrote it, not silently dropped. A misspelled `minLen` is a type error on that key, so a constraint can never go missing without you hearing about it.
::

A few corners are turned away loudly instead of guessed at. `contentSchema` would validate decoded content against a second schema in one pass, which has no honest single-pass story. `oneOf` beside `not`, `if`, `dependentRequired`, `dependentSchemas` or a reference is the other one: the exclusivity would have to be dropped to combine them, so the schema resolves to an impossible type instead, and the fix is to move the shared constraint into each branch by hand.

## Things worth knowing

Both combinators mean exactly what the spec says. `anyOf` accepts a value that matches at least one branch, which is what a plain union already does. `oneOf` requires exactly one branch: a value matching two branches is rejected, just as a strict JSON Schema validator would reject it. Exclusivity counts branches as you wrote them, so in `oneOf: [A, {anyOf: [B, C]}]` a value matching both B and C still matched only one branch and passes. A `type` gate or a plain constraint written next to `oneOf` applies to every branch, exactly as the spec reads it, so `{type: 'string', oneOf: [{minLength: 2}, {maxLength: 4}]}` accepts a string matching exactly one of the two lengths and nothing else. One nesting corner is deliberate: when a branch reaches through a `$ref` to a definition that is itself a `oneOf`, the outer count reads that branch as its plain union (at least one, not exactly one, inside it). Spell the nested exclusivity inline in the branch when it matters.

Constraints spread across `allOf` branches really combine. A branch that is itself a `oneOf` combines too: the other branches apply to every alternative, and the exactly-one count is unchanged, so `allOf: [{type: 'object'}, {oneOf: [a, b]}]` means an object matching exactly one of the two. When two branches each describe tuple positions with `prefixItems`, the positions merge one by one into a single tuple, and the generated validator enforces the merged shape. Bounds combine the same way, keeping whichever is tighter, so `allOf: [{maximum: 30}, {minimum: 20}]` accepts 25 and rejects 35. Several `multipleOf` constraints fold into the one number they all agree on. That holds when the two constraints land on the same array position from different places, too: a `prefixItems` inside a branch meeting an `items` outside it gives that position both rules, so `{allOf: [{prefixItems: [{minimum: 3}]}], items: {minimum: 5}}` accepts `[5, 5]` and rejects `[3, 5]`. A combination that no value could satisfy is rejected outright instead of being half-checked.

Only draft 2020-12 is accepted, and a `$schema` naming another dialect is a type error.

Some things simply have no JSON Schema spelling: `bigint`, `Date` and the other native class types, `Map`, `Set`, and template literal types. Those still work, you just describe them with a TypeScript type or an `RT.*` builder instead. You can mix all three forms in one file.

## Two deliberate limits

Both of these come up often enough to answer here, because in each case the behaviour is a decision rather than a gap.

### Formats are always checked

In the 2020-12 dialect, `format` is a label by default. A validator is allowed to read `format: 'email'` and check nothing at all, and most only check it once you turn on something extra (AJV, for instance, needs its separate `ajv-formats` package). RunTypes always checks it, so a string that is not an email is rejected.

That follows from what the schema turns into. `format: 'email'` becomes the `EmailAddress` type in your code, and that type has to mean the value was checked. Otherwise every function further down that accepts an `EmailAddress` is quietly accepting anything. Reading the keyword as a label would mean recovering a plain `string` and dropping the constraint, which is the one outcome this translation never allows.

There is no switch for it, and the reason is that nothing in the schema tells us which behaviour you meant. The dialect does define a way to say so (a custom meta schema that declares the format assertion vocabulary, pointed at from `$schema`), but that lives in a second document which would have to be fetched, and it is almost never used. In practice the choice gets made in the consuming code, invisible to the file. So a default has to be picked, and checking is the safer one: reading a schema in, we may reject a value a laxer validator would have accepted, but we never accept one a stricter validator would have rejected.

A `format` value the dialect does not define stays a label, because there is nothing to check it against.

### References stay inside the document you passed

`$ref` and `$dynamicRef` resolve within the schema you hand over, including `$anchor` and `$dynamicAnchor` targets and the root itself. A reference to another document is turned down at the key rather than guessed at, and an embedded `$id` is turned down for the same reason, since it re-scopes references to a document boundary that would then have to be resolved.

The schema is read while your project builds, before anything runs. Following a reference out of the document would mean fetching it mid build, which puts the network in the middle of your type checking, lets the same source produce different types on different machines, and leaves no honest answer for the moment a fetch fails.

The reuse you wanted is still there, two ways. Pull the pieces into one document under `$defs` and point at them with `$ref`, or keep them as separate schemas in separate variables and compose them in TypeScript, which is the same thing with none of the above.
