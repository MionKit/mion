RunTypes reads its settings from the `plugins` list in your `tsconfig.json`. Configure a project once, and every build tool (Vite, Rollup, webpack, Rspack, esbuild) picks it up.

## Option Reference

Every option is optional. Leave one out and the compiler uses its default. Set them in your tsconfig plugin entry, shown under [Setting Options](#setting-options).

| Option | Default | What it does |
| --- | --- | --- |
| `genDir` | inferred from tsconfig | The RunTypes generated-output folder in your project. Build output goes under `types/` (ignored by git); the [enrichment CLI](/runtypes/guide/validation) writes its committed files under `enriched/` (`friendly/`, `mock/`, `i18n/<locale>/`). Each folder has a README saying what it is. When omitted, it is created next to your source as `.mion`, a dot-folder that tsconfig `include` globs skip, so the generated cache never enters your program by accident. The CLI flag is `--gen-dir`. |
| `emitMode` | `code` | How each generated function ships. `code` ships the function body as a string and builds it on first use (smallest output). `functions` ships ready functions. `both` ships both, for runtimes that block dynamic code (a strict CSP, Cloudflare Workers). A mion client built with `bundleApi` always ships ready functions for the routes it calls, whatever this is set to. |
| `moduleMode` | `default` | How the generated functions group into modules. `default` gives your bundler the best code splitting. `allSingle` groups each feature into one module (fewest files). `allModules` gives every entry its own module (rarely useful). |
| `hashLength` | `7` | Length of the short ids in generated names. Every id is exactly this long. If two types ever get the same id, the build stops and prints both types, the id they share, and the length to try next (see [MKR014](/runtypes/diagnostics/all-diagnostics)). That is the only reason to raise it, and one more character gives sixty-two times the room. |
| `downgradeErrors` | unset | A RuntimeError (a type that can never be encoded, a contradictory format rule) stops your build: your bundler produces no bundle, and the `mion` command line exits with a failure code. See [Error Levels](/runtypes/diagnostics/error-levels) for the three levels. List the codes you want reported as warnings instead, for example `['VL002']`, and every other code keeps stopping the build. A downgraded error is still printed, marked `(downgraded)`. Use `'*'` to downgrade all of them, which suits a project adopting mion that cannot list codes it has not seen yet. An Error cannot be downgraded, `'*'` included, because the build produced no code for that piece, so naming one here is refused with the reason. For a bad call site in your own source prefer a `@mion-expect-error` comment on the line above it: it is precise, and an unused one is reported as a warning. |
| `pureFnReport` | off | A report of every pure function this build generated, for tooling that moves pure function bodies between two builds of one codebase (a framework that declares a mapper in client code but runs it on the server). On the bundler plugin it has three states: `'file'` writes the report to `<genDir>/types/pure-fns-report.json` on every build (gitignored like the rest of the generated output); `'callback'` delivers it only in process to the `onPureFnReport` handler, writing no file; leave it off (the default) for neither. The file location is fixed. Each record carries the call site, the pure function's id, which function and package declared the registrar, and the function body itself. The report shape is the same for every `moduleMode`. In tsconfig, set `pureFnReport: true` to write the file (the in process handler is a plugin only API); the CLI flags are `--pure-fn-report-file` (writes the JSON) and `--pure-fn-report-wire` (report on the wire only). |
| `jsonMaxBytes` | `true` | For every reflected type whose size is fully bounded (strings with a maximum length, lists with a maximum number of items, and so on), emit the largest JSON a valid value can be. mion turns that number into per route request size limits. Set it to `false` to emit nothing, for a project that keeps its own limits. The CLI flag is `--json-max-bytes=false`. |
| `binarySizing` | unset | Tuning for the first buffer a binary encoder allocates, detailed in the table below. Leave the key out and the defaults apply. |
| `i18n` | unset | Translation settings for the friendly maps, detailed in the table below. Leave the key out and translations are off. |
| `markers` | unset | Which packages may declare the RunTypes marker types, detailed in the table below. Leave the key out and only `@mionjs/run-types` is trusted, which is what almost every project wants. It exists for a library that exposes RunTypes powered functions without asking its own users to install RunTypes for the type declarations alone. |
| `tsconfig` | found like tsc | Path to your tsconfig, relative to the project root. It is the one option that cannot live inside the tsconfig itself: set it on the bundler plugin, on the lint settings, or with the CLI `--tsconfig` flag. When not set, the config is found exactly the way tsc finds it, searching upward from the working directory. A config you name explicitly must load, or the tool stops with an error. |

::note
mion adds three keys of its own to the same plugin entry. `clientTsconfig` (CLI flag `--client-tsconfig`) names a separate client project a mion API serves batches to, documented with the [mion Vite plugin](/rpc/devtools/vite#batch-transport). `bundleApi` and `apiTsconfig` (CLI flags `--bundle-api` and `--api-tsconfig`) ship a client's routes with it, documented in [Bundling the API Into the Client](/rpc/client/bundled-api).
::

::note
For in-process tooling, the bundler plugin also accepts an `onPureFnReport(sites, phase)` callback. It fires once with the whole report after the build scan (phase `'build'`), and again under Vite with just the changed file when you edit a pure function body (phase `'update'`). It carries the same records as the JSON file. Setting the callback without `pureFnReport` implies `'callback'`, so the report is on and no file is written.
::

### Binary Buffer Sizing

The `binarySizing` object tunes how the first buffer of a binary encoder is sized:

| Key | Default | What it does |
| --- | --- | --- |
| `bias` | `0.8` | How generous that first buffer is, from 0 (tight, may need to grow) to 1 (generous). |
| `items` | `100` | How many elements to assume for an array, Map or Set with no declared limit. |
| `stringBytes` | `32` | How long to assume a string with no declared limit is. |
| `maxBytes` | `65536` | A cap on the estimate, so a very large declared limit never creates a huge buffer. |

### Marker Packages

The `markers` object says where the marker types (`InjectRunTypeId`, `InjectTypeFnArgs`, `CompTimeArgs`, `PureFunction`) are allowed to come from:

| Key | Default | What it does |
| --- | --- | --- |
| `packages` | none | Extra package names allowed to declare the marker types. This adds to the built in package, it never replaces it, so markers imported from `@mionjs/run-types` keep working alongside your own. |
| `checkPackage` | `true` | When `false`, a type counts as a marker on its name alone, whatever package declared it. An escape hatch: a type you happen to name `InjectRunTypeId` in your own code then drives rewrites too. Prefer naming your package in `packages`. |

Most projects never touch this. It matters when a library declares the marker types itself rather than re-exporting them from RunTypes: the compiler only trusts a marker from a package it knows, so an unknown package leaves your type as `unknown`. The build reports this as MKR012 and names the package to add:

```json [tsconfig.json]
{
  "compilerOptions": {
    "plugins": [
      {
        "name": "mion",
        "markers": {"packages": ["@my-org/runtypes-markers"]}
      }
    ]
  }
}
```

Re-exporting the marker types (`export type {InjectRunTypeId} from '@mionjs/run-types'`) needs no configuration, because the declaration still belongs to RunTypes. You need this key only when your package writes its own declarations.

### Translations

The `i18n` object configures [translations](/runtypes/ai-integration/i18n) for your [FriendlyText](/runtypes/ai-integration/friendly-type) maps:

| Key | Default | What it does |
| --- | --- | --- |
| `sourceLocale` | `en` | The language your friendly maps are written in. It decides which plural forms `enrich` scaffolds in them. |
| `locales` | none | The locales you translate into; `enrich --i18n all` and its `--no-emit` check walk this list. Don't list the source locale. |
| `strict` | `false` | When `true`, an incomplete or out-of-date translation fails the i18n check by default, the same as passing `--require-complete` to a single run. Rendering at runtime stays lenient either way. |

## Setting Options

Your `tsconfig.json` is the home for every option: add an entry named `mion` under `compilerOptions.plugins` and every build tool picks it up. Every project option also works directly on the `@mionjs/devtools` bundler plugin, as a per build override. Two kinds of option are the exception: the options that describe the build itself (such as `tsconfig`) are plugin only, and the `i18n` object, which belongs to the enrich command, is tsconfig only.

::code-group
```json [tsconfig.json]
{
  "compilerOptions": {
    "plugins": [
      {
        "name": "mion",
        "emitMode": "code",
        "moduleMode": "default",
        "i18n": {"sourceLocale": "en", "locales": ["es", "pl"]}
      }
    ]
  }
}
```

```ts [vite.config.ts]
import {defineConfig} from 'vite';
import runtypes from '@mionjs/devtools/runtypes/vite';

export default defineConfig({
  plugins: [runtypes({emitMode: 'functions'})],
});
```
::

::note
Order `@mionjs/devtools` first among your `enforce: 'pre'` plugins, so it sees your source before other plugins rewrite it.
::

Settings layer the way `tsc` does:

```
build-tool option / CLI flag   (highest)
tsconfig plugin entry
built-in default               (lowest)
```

::tip
Set your options once in tsconfig. Use a build-tool option or a CLI flag only when a single build needs to differ.
::

## Syncing Enrichment Files During Dev

The [enrichment CLI](/runtypes/ai-integration/workflow-and-commands) writes your committed `FriendlyText` and `MockData` maps. Instead of running it by hand, you can let the `@mionjs/devtools` bundler plugin scaffold and sync those files while your dev server runs. Turn it on with an `enrich` object on the plugin; these keys never go in your tsconfig plugin entry.

| Key | Default | What it does |
| --- | --- | --- |
| `friendly` | `false` | Scaffold and sync the `enriched/friendly/` maps as your types change. |
| `mock` | `false` | Scaffold and sync the `enriched/mock/` maps as your types change. |
| `i18n` | unset | Sync the per-locale `enriched/i18n/<locale>/` mirrors. Takes `sourceLocale`, `locales` and `strict`, the same shape as the tsconfig i18n object; its presence turns the locale sync on. |
| `suppressHmr` | `false` | Skip HMR for writes under `<genDir>/enriched`, so the dev server does not reload when the plugin (or you) touch a mirror file. |

The sync updates the file structure but never fills in translated strings or any other value you wrote, exactly like `enrich --update`. It runs only in dev and watch. On a production build the plugin never writes; it runs a read-only check instead (the build equivalent of `enrich --require-complete`), and fails the build if any file is out of date, missing, still carries an unfilled blank, or holds a stale `@rtOrphan` entry.

```ts [vite.config.ts]
import {defineConfig} from 'vite';
import runtypes from '@mionjs/devtools/runtypes/vite';

export default defineConfig({
  plugins: [
    runtypes({
      enrich: {
        friendly: true,
        mock: true,
        i18n: {sourceLocale: 'en', locales: ['es', 'pl']},
        suppressHmr: true,
      },
    }),
  ],
});
```

## The Build Cache

RunTypes keeps an on-disk cache so a rebuild can skip types that did not change. It lives under `node_modules/.cache/mion` and follows TypeScript's own switch: the cache is on when your tsconfig sets `incremental` (or `composite`), and off when it does not. There is no separate option to set.

```json [tsconfig.json]
{
  "compilerOptions": {
    "incremental": true
  }
}
```

::note
The cache is safe across versions: the compiler version and your build options are part of every entry, so a new release or a changed setting never reads a stale file. Anything that wipes `node_modules/.cache` clears it.
::
