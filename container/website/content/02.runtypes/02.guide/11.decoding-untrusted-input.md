## Decoders Trust Their Input

A decoder rebuilds a value from a wire and hands it back. It does not check that the value matches your type. `createJsonDecoderFn` and `createBinaryDecoderFn` are the fast path for data you produced yourself, or data that was validated before it reached you.

For JSON from anyone else, use `createParseFn`. It decodes and validates in one walk, and it is the one function that can never throw anything but `RTParseError`, however malformed the input. For bytes from anyone else, decode with `createBinaryDecoderFn` and run the result through `createValidateFn` before you use it.

## What a Decoder Checks and What It Leaves Alone

Every value is rebuilt only from the form the encoder writes. A well-formed value is converted, anything else is left in place for validate to refuse, and a few things are refused by the decoder itself because validate could never see them.

| Input | JSON decoders | Binary decoder |
| --- | --- | --- |
| A value of the wrong shape (a `null` where a Date string goes, `true` where a bigint goes) | Left as it is, validate refuses it | Not possible, the layout is fixed by the type |
| A bigint string that is not a whole number (`"12x"`, `"1e3"`, `""`) | Left as a string, validate refuses it | Left as a string, validate refuses it |
| An invalid date string | Comes back as an Invalid Date, validate refuses it | Comes back as an Invalid Date, validate refuses it |
| A Temporal string with bad content | The engine error is thrown, `parse` reports it as a serialization error | The engine error is thrown |
| A union envelope that is not a two-slot array (a bare value, a `null`) | The decoder throws a `[mion]` error | Not possible, the layout is fixed by the type |
| A union index or discriminator that matches no member | The decoder throws a `[mion]` error | The decoder throws a `[mion]` error |
| A property key named `__proto__` | The decoder throws a `[mion]` error | The decoder throws `BinaryDecodeError` |
| A cut-off buffer, a count or length past the bytes left, invalid UTF-8 | Not applicable | The decoder throws `BinaryDecodeError` |
| An `any`, `unknown` or `object` slot | Passed through unchecked | Parsed from JSON text, unchecked |

## The Decoder Checks the Shape Before It Converts

Validation runs on the restored value, after the decoder has done its work. That makes the decoder the one check standing between untrusted JSON and a constructor: `new Date(true)` is a real date (epoch 1), `BigInt('')` is `0n`, `new Set(null)` is an empty set. So every decoder converts only the exact form the encoder writes, and leaves any other value untouched for validate to refuse.

| Type | Converted only from |
| --- | --- |
| Date, Temporal types | a string |
| bigint | a whole-number string, or a whole number |
| Map, Set | an array |
| a union with a wire envelope | a two-slot array (anything else is refused with a typed error, since a bare value could pass validation as the wrong member) |
| a symbol literal | its `Symbol:` string form |

This is a contract, not a habit: the resolver keeps the list of types that convert, and a build-time test plus a generated-code check fail when a decoder converts a value without checking its shape first.

A value nested deeper than the engine's call stack on a recursive type makes validate throw `RangeError`. `parse` reports that as a serialization error. Bound the nesting depth of a JSON body before parsing it when the sender is untrusted.

The `strip` strategy blanks every undeclared property at every level, inside Map values and Set members included, before the declared shape is restored.

::note
RegExp values do not travel. A property typed `RegExp` is dropped from the wire like a function is, with the same build Warning, and a `RegExp` at a root, array or union position is a RuntimeError: the function is written as one that throws, and the build fails. The only regex that reaches a validator is a `pattern` format, which is fixed at build time.
::

## The One Property Name That Is Never Data

`__proto__` is the only name mion treats differently, and for one reason: writing that key on a plain object swaps the object's prototype instead of storing a value.

As a key in a record it is refused as a wire key on both roads, refused by validate, and skipped by every encoder and clone that rebuilds an object from its keys.

```ts
const decode = createJsonDecoderFn<Record<string, string>>();
decode('{"__proto__":{"admin":true}}'); // throws [mion] Unsafe property name: __proto__
```

As a declared property it is dropped, the same way a property that cannot cross the wire is dropped, and the rest of the type keeps working.

TypeScript accepts the declaration, which is why mion warns about it. The type promises a value and there is no such key at runtime:

```ts
interface Settings {ok: number; __proto__: string}
const value: Settings = {ok: 1, __proto__: 'x'}; // compiles
Object.keys(value); // ['ok']
```

`prototype` and `constructor` are ordinary property names. A record can carry them as keys, and a type can declare them:

```ts
const decode = createJsonDecoderFn<Record<string, string>>();
decode('{"constructor":"builder","prototype":"draft"}'); // both keys, as written
```

## Build-Time Trust

The generated functions are materialized from text at startup. That text comes from the compiler and from its disk cache under `node_modules/.cache/mion`. The cache is keyed by the type's content and the build options, and it is as trusted as `node_modules` itself: whoever can write there can change what your build runs, cache or no cache. Keep it out of any location an untrusted process can write.
