Every `createX<T>()` factory turns a type into a purpose-built function the build writes out for you, with no schema object and no runtime reflection. They all share one calling convention and one contract, so once you've seen one you've seen them all.

This page covers **validation**: the type guards, the error reports, and unknown-key handling. ([JSON](/runtypes/guide/json-serialization) and [binary](/runtypes/guide/binary-serialization) serialization, [mocking](/runtypes/guide/mocking) and [reflection](/runtypes/guide/reflection) get their own pages.)

::note
**Validators check serializable data.** `createValidateFn`, `createGetValidationErrorsFn`, and the JSON and binary codecs all work on the data-only projection of your type, `DataOnly<T>`: the JSON-shaped data your value carries. Non-serializable members (functions, methods, getters and symbols) are skipped, along with built-in values that have no JSON form, such as `URL` or a typed array. None of them survive a round trip through JSON or the wire anyway, and you get a build warning naming each one that is dropped. A value that is not serializable at a root position has nothing to validate, so the build reports it. This is why a validator can flag a type as non-serializable, and why a decoder returns `DataOnly<T>` rather than the full type.
::

## Three Ways to Call a Factory

Every factory takes your type three different ways. They all resolve to the same generated function, so use whichever fits the call site.

<code-import path="packages/examples/src/guide/validation-call-forms.ts" lang="ts" commentStart="// start-forms" commentEnd="// end-forms" />

- **Type-first**: you supply `<T>`, no value needed.
- **Value-first**: `T` is inferred from a value you already have.
- **Run-type**: pass the run-type a builder returned; `T` comes from it.

The rest of these guide pages use whichever form reads best for the example, but every one of them accepts all three.

### Format Error Types

Some formats can fail in more than one way, and you usually want to say
something different about each. Those set an `errorType` on the `format` detail
naming the mode, so you can switch on it:

```ts
const errors = getErrors(card);
switch (errors[0]?.format?.errorType) {
  case 'format': // not shaped like a card number at all
  case 'checksum': // right shape, the digits do not add up (a typo)
  case 'network': // a good card, just not one this field takes
}
```

The modes are stable strings, and each format exports them as a union type
(`CreditCardErrorType`, `EmailErrorType`, `DomainErrorType`, `IpErrorType`
from the formats subpath):

| Format | Modes | When |
| --- | --- | --- |
| `CreditCard` | `format`, `checksum`, `network` | `network` only when the field pins `networks` |
| `EmailAddress`, `IdnEmail` | `format`, `localPart`, `domain`, `addressLiteral`, `length` | which part of the address is wrong (`format` means no `@` at all) |
| `EmailStrict` | `format`, `localPart` | the domain half reports under the `domain` format with its own modes |
| `Hostname`, `IdnHostname` | `label`, `punycode`, `bidi`, `length` | which rule the name broke |
| `DomainStrict` | `label`, `tld` | which label failed |
| `IPv4WithPort`, `IPv6WithPort`, `IPWithPort` | `address`, `port` | only the port-accepting presets |

A format with a single failure mode leaves `errorType` unset, so its absence means
there was only one thing that could have gone wrong. That covers every format
not in the table (`Url`, `UUIDv4`, the plain `Email` and `Domain` presets, the
number and date formats): each of their constraints reports its own error, and
the `formatPath` on it already says which one. The same goes for a bound on the
whole value, like a domain's `maxParts`.

The field is typed from your type. The errors a validator returns list the
formats the type actually contains, so switching on the format name narrows
`errorType` to that format's modes and the compiler catches a typo:

## Validate Options

Both validators take an options object as a **literal at the call site**. The build reads the literal and routes you to a specialized variant, so nothing is parsed at runtime.

<code-import path="packages/examples/src/guide/validation-options.ts" lang="ts" commentStart="// start-options" commentEnd="// end-options" />

| Option | What it does |
| --- | --- |
| `noLiterals` | Literal checks degrade to their base type, so `literal 'a'` accepts any string and `literal 2` accepts any finite number. |
| `noIsArrayCheck` | Skips the leading `Array.isArray()` guard on array validators, for when you've already proven the value is an array upstream. |
| `numberMode` | Chooses how a `number` is checked. `isFinite` (the default) rejects `NaN` and `Infinity`; `typeof` accepts them (matching ajv, typia, and JSON Schema); `notNaN` rejects `NaN` but keeps `Infinity`. |

::warning
Pass the options as an **object literal** at the call site. It's read at build time, so a variable won't work because the build can't see its value.
::

### A Project-Wide Number Mode

`numberMode` is handy when migrating onto RunTypes from a library that accepts `NaN` and `Infinity`, so you usually want the same behaviour everywhere rather than per call. Set it once under a `validate` object in the plugin (or the tsconfig `mion` plugin entry) and every validator picks it up:

```ts
runtypes({validate: {numberMode: 'typeof'}})
```

A per-call `numberMode` still wins over the project default for that one validator, and setting `numberMode: 'isFinite'` at a call opts it back out.

## Unknown Keys

Properties that aren't in your declared type. These check for *extra* keys. To check that the *declared* keys hold the *right types*, that's validation above.

The usual case is wanting both at once: the value matches the type, and it carries nothing extra. Pass `checkUnknowns` and you get one function that does both in a single pass:

<code-import path="packages/examples/src/guide/unknown-keys-check-unknowns.ts" lang="ts" />

It works on `createValidateFn` and `createGetValidationErrorsFn`, and it reaches every level of the type, not just the top object. On the error form, each undeclared key adds a `{path, expected: 'never'}` entry next to the usual type errors (note the entries come out in the order the value is walked, so a nested object's errors arrive together rather than being grouped by kind).

The separate tools below are still there for when you want only one half, or want to remove the extras rather than reject them.

Working from a JSON payload rather than a value you already hold? [createParseFn](/runtypes/guide/json-serialization#parsing) does the decoding and the checking together, and takes the same strategy choice.

| Factory | What it does |
| --- | --- |
| `createHasUnknownKeysFn` | Predicate that returns `true` if the value carries any undeclared key. Takes a compile-time `{runsAfterValidation: true}` option for a much faster variant when the value already passed `validate`. |
| `createCloneExactShapeFn` | A proper deep clone of the declared shape: undeclared keys are dropped by construction, the input is never mutated, and `clone(x) !== x` for every object-typed value (a class keeps its prototype; only primitives and opaque handles pass through). |
| `createUnknownKeyErrorsFn` | One `{path, expected: 'never'}` per undeclared key, the same shape as `createGetValidationErrorsFn`. |

All three look at keys, never at shape. When the value is not an object of the declared type (null, a primitive, an array, or the wrong thing nested inside), there are no undeclared keys to report, so `createUnknownKeyErrorsFn` returns an empty list and `createHasUnknownKeysFn` returns false. Shape is what `createGetValidationErrorsFn` reports, so joining the two lists gives you one strict report with the shape named exactly once.

## Standard Schema

`createStandardSchema<T>()` wraps the validators above into a [Standard Schema](https://github.com/standard-schema/standard-schema) object: the shared `~standard` contract that tRPC, TanStack Form and Router, Hono, React Hook Form and many more accept directly. One call and your type works anywhere the spec is understood, with no per-library adapter to write.

<code-import path="packages/examples/src/guide/standard-schema.ts" lang="ts" commentStart="// start-standard" commentEnd="// end-standard" />

The object exposes a single `validate(value)`. It returns `{value}` when the value is valid, or `{issues}` when it is not, where each issue carries a `message` and a `path` locating the field that failed. Under the hood it runs the fast type guard first and only builds the issue list on a failure, so the valid path stays cheap.

It takes the same three call forms as every other factory (type-first, value-first, run-type) and the same `ValidateOptions`.

::note
`validate` is synchronous and never throws on invalid input. Instead it reports through `issues`. The result is typed as `DataOnly<T>` (the serializable projection covered above), so what a consumer reads back matches what the validator actually checks.
::
