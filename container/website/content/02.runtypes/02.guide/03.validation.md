Every `createX<T>()` factory turns a type into a function the build writes for you, with no schema object and no runtime reflection. They all share one calling convention and one contract.

This page covers **validation**: the type guards, the error reports, and unknown-key handling. ([JSON](/runtypes/guide/json-serialization) and [binary](/runtypes/guide/binary-serialization) serialization, [mocking](/runtypes/guide/mocking) and [reflection](/runtypes/guide/reflection) get their own pages.)

::note
**Validators check serializable data.** `createValidateFn`, `createGetValidationErrorsFn`, and the JSON and binary codecs work on `DataOnly<T>`, the JSON-shaped data your value carries. Functions, methods, getters, symbols, `RegExp` values and built-ins with no JSON form, such as `URL` or a typed array, are skipped, with a build warning naming each one dropped. A value that is not serializable at a root position has nothing to validate, so the generated function throws and the build reports a RuntimeError. That is also why a decoder returns `DataOnly<T>` rather than the full type.
::

### Format Error Types

Some formats fail in more than one way. Those set an `errorType` on the
`format` detail naming the mode, so you can switch on it:

```ts
const errors = getErrors(card);
switch (errors[0]?.format?.errorType) {
  case 'format': // not shaped like a card number at all
  case 'checksum': // right shape, the digits do not add up (a typo)
  case 'network': // a good card, just not one this field takes
}
```

The modes are stable strings, and each format exports them as a union type
(`CreditCardErrorType`, `EmailErrorType`, `DomainErrorType`, `IpErrorType`
from the formats subpath):

| Format | Modes | When |
| --- | --- | --- |
| `CreditCard` | `format`, `checksum`, `network` | `network` only when the field pins `networks` |
| `EmailAddress`, `IdnEmail` | `format`, `localPart`, `domain`, `addressLiteral`, `length` | which part of the address is wrong (`format` means no `@` at all) |
| `EmailStrict` | `format`, `localPart` | the domain half reports under the `domain` format with its own modes |
| `Hostname`, `IdnHostname` | `label`, `punycode`, `bidi`, `length` | which rule the name broke |
| `DomainStrict` | `label`, `tld` | which label failed |
| `IPv4WithPort`, `IPv6WithPort`, `IPWithPort` | `address`, `port` | only the port-accepting presets |

A format with a single failure mode leaves `errorType` unset: that is every
format not in the table (`Url`, `UUIDv4`, the plain `Email` and `Domain`
presets, the number and date formats). Each of their constraints reports its own
error, and the `formatPath` on it says which one. A bound on the whole value,
like a domain's `maxParts`, works the same way.

The field is typed from your type: the errors a validator returns list only the
formats the type contains.

## Validation Options

Both validators take an options object as a second argument.

<code-import path="packages/examples/src/guide/validation-options.ts" lang="ts" commentStart="// start-options" commentEnd="// end-options" />

| Option | What it does |
| --- | --- |
| `noLiterals` | Literal checks degrade to their base type, so `literal 'a'` accepts any string and `literal 2` accepts any finite number. |
| `noIsArrayCheck` | Skips the leading `Array.isArray()` guard on array validators, for a value you already know is an array. |
| `numberMode` | Chooses how a `number` is checked. `isFinite` (the default) rejects `NaN` and `Infinity`; `typeof` accepts them (matching ajv, typia, and JSON Schema); `notNaN` rejects `NaN` but keeps `Infinity`. |

::warning
Pass the options as an **object literal** at the call site. It is read at build time, so a variable does not work.
::

### A Project-Wide Number Mode

Set `numberMode` once under a `validate` object in the plugin (or the tsconfig `mion` plugin entry) and every validator picks it up:

```ts
runtypes({validate: {numberMode: 'typeof'}})
```

A per-call `numberMode` still wins over the project default for that one validator, and setting `numberMode: 'isFinite'` at a call opts it back out.

Errors come out in the order the value is walked, so a nested object's errors arrive together rather than grouped by kind.

For a JSON payload, [createParseFn](/runtypes/guide/json-serialization#parsing-and-validating-in-one-step) decodes and checks in one step, and takes the same strategy choice.

## Unknown Key Factories

Use these when you want only one half of the check, or want to remove the extras rather than reject them.

| Factory | What it does |
| --- | --- |
| `createHasUnknownKeysFn` | Predicate that returns `true` if the value carries any undeclared key. Takes a compile-time `{runsAfterValidation: true}` option for a much faster variant when the value already passed `validate`. |
| `createCloneExactShapeFn` | A proper deep clone of the declared shape: undeclared keys are dropped by construction, the input is never mutated, and `clone(x) !== x` for every object-typed value (a class keeps its prototype; only primitives and opaque handles pass through). |
| `createUnknownKeyErrorsFn` | One `{path, expected: 'never'}` per undeclared key, the same shape as `createGetValidationErrorsFn`. |

All three look at keys, never at shape. When the value is not an object of the declared type (null, a primitive, an array, or the wrong thing nested inside), there are no undeclared keys to report, so `createUnknownKeyErrorsFn` returns an empty list and `createHasUnknownKeysFn` returns false.

## Standard Schema Support

`createStandardSchema<T>()` wraps the validators above into a [Standard Schema](https://github.com/standard-schema/standard-schema) object, the `~standard` contract that tRPC, TanStack Form and Router, Hono, React Hook Form and many more read directly. No per-library adapter to write.

<code-import path="packages/examples/src/guide/standard-schema.ts" lang="ts" commentStart="// start-standard" commentEnd="// end-standard" />

Each issue carries a `message` and a `path` locating the field that failed. The schema takes the same three call forms as every other factory and the same `ValidateOptions`.

::note
`validate` is synchronous and never throws on invalid input, it reports through `issues`. The result is typed as `DataOnly<T>`, the serializable projection covered above.
::
