## JSON Encoder Strategies

`createJsonEncoderFn` takes a `strategy` (a call-site literal) that decides how it walks your value and what it does with undeclared keys.

<code-import path="packages/examples/src/guide/json-strategies.ts" lang="ts" commentStart="// start-strategies" commentEnd="// end-strategies" />

Each one compiles to a different function. The first three write the same keyed JSON, `compact` writes a smaller positional form:

| Strategy | How it works | Mutates input? | Undeclared keys |
| --- | --- | --- | --- |
| `clone` _(default)_ | Builds a fresh, JSON-safe value from the declared shape, then encodes that. Never touches your input, but cloning every object costs a little more memory. | No | Dropped (for free) |
| `mutate` | Rewrites non-serializable leaves (`Date`, `BigInt`, …) in place, then encodes. Faster, with no allocation, at the cost of mutating the object you pass in. | **Yes** | Kept on the wire |
| `direct` | One pass that writes valid JSON straight out. No clone, so it is lighter on memory than `clone`. | No | Dropped |
| `compact` | Like `clone`, but every object is written as an array of its declared properties, in order, with no key names on the wire. 40 to 60 percent fewer bytes on real objects. An absent optional property is written as `null`. | No | Dropped |

The decoder has a `strategy` too. `strip` and `preserve` read the keyed JSON and differ only in what happens to undeclared keys (see [Parsing and Validating in One Step](#parsing-and-validating-in-one-step)). `compact` reads the positional form, so pair it with the `compact` encoder; the keyed decoders cannot read it.

::tip
`clone` is the safe default. Use `mutate` only in a hot path where the allocation shows up in a profile and you are fine mutating the object you pass in. Use `compact` when both ends share the type and the bytes matter, the way a mion route does.
::

## Custom Class Serializers

Plain objects and the built-in classes (`Date`, `Map`, `Set`) round trip for free. A `RegExp` does not: a pattern is code, not data, so a `RegExp` property is dropped from the wire like a function is. Your own class sends only its data, so register it with `registerClassSerializer` to get a real instance back: you hand it the class itself and (when needed) how to rebuild an instance.

<code-import path="packages/examples/src/guide/custom-class-serializer.ts" lang="ts" />

Both halves are optional:

- `serialize` defaults to the structural encode, exactly what an interface of the same shape would produce. Provide it only when you want a different wire shape (keep it to the declared properties on the JSON path).
- `deserialize` defaults to `new YourClass()` plus setting the declared properties from the decoded data, so a class with a zero-argument constructor needs nothing but the class. Provide `deserialize` when the constructor takes arguments; the type checker requires it there.

Register before anything serializes the class.

Generic classes need nothing extra: one registration covers every instantiation, so `RpcError` registered once rebuilds both `RpcError<'a'>` and `RpcError<'b', Data>`. Registering the same class again updates its handlers; it never drops an instantiation that worked before.

A subclass is a class of its own. To send one, declare it in the signature next to its base (`AuthError | RpcError`) and register it like any class: the union picks the member by the exact class, so an `AuthError` keeps every field it declares and comes back as an `AuthError`, whatever order the members are listed in. Left unregistered, it still takes its own member by shape and comes back as a plain object. Passing a subclass to an encoder built for the base alone is a type error.

Classes also rebuild inside a union. A field typed as `Circle | Square` comes back as the right instance, even when the two classes have identical fields, because each member is picked by the actual instance. A plain object next to a class in the same union (`Money | {amount: number}`) stays a plain object.

Classes extending Error always serialize `name` and `message`, so the error is still useful on the receiving side. The optional `stack` and `cause` are sent only when the value holds them as enumerable own properties (the same test `JSON.stringify` applies), so a stack trace never leaks by default. To send one, define it as an enumerable property: `Object.defineProperty(err, 'stack', {value: err.stack, enumerable: true})`.

Add the same guard to one of your own properties with a `@nonEnumerable` JSDoc tag. It takes effect only on an optional property. On a required one the property still serializes, and a lint rule tells you.

::note
One registration covers JSON and [binary](/runtypes/guide/binary-serialization) alike. `createValidateFn` always checks a class by its structural shape and never routes through the serializer. Without a registered serializer the data still round trips, you just get a plain object back instead of an instance. If the automatic `new YourClass()` fails because the constructor needs arguments, decode throws a `CLS002` error telling you to register a `deserialize`.
::

## Detecting Circular References

The generated encoders are fast because they do not track which objects they have already seen, so a value that points back at itself (`a.next = a`) recurses until the stack overflows. Set the per-call `rejectCircularRefs` option on `createJsonEncoderFn` and that encoder throws a `CircularReferenceError` with the path to the cycle instead.

<code-import path="packages/examples/src/guide/serialization-circular.ts" lang="ts" commentStart="// start-dag" commentEnd="// end-dag" />

::note
`rejectCircularRefs` also works on the [binary encoder](/runtypes/guide/binary-serialization#detecting-circular-references), on `createValidateFn` and on `createGetValidationErrorsFn`. In validation, `validate` returns `false` and `getValidationErrors` records a `{expected: 'circular'}` entry instead of throwing. Decoders need no guard: a serialized payload cannot contain a runtime cycle. It is off by default, so set it only where you process values that might cycle.
::

## Parsing and Validating in One Step

A decoder trusts its input. When the JSON came from somewhere you do not control, `createParseFn<T>()` restores the value, checks it and collects the errors in one call:

<code-import path="packages/examples/src/guide/parse-basics.ts" lang="ts" />

It takes the output of `JSON.parse`, not the string, so it fits wherever the body was already read. A value that matches comes back typed, with dates and bigints turned back into real values.

One that does not throws `RTParseError`. Use `isSerializationError` to tell a failed check from a value that could not be decoded at all.

The value is walked once rather than twice, and no input can make it throw anything other than `RTParseError`, however malformed.

What a decoder checks on its own, what it leaves for the check, and what it throws is on the [Decoding Untrusted Input](/runtypes/guide/decoding-untrusted-input) page.

Every value is rebuilt only from the form the encoder writes: a `Date` or a `bigint` from its string, a `Map` or a `Set` from its array. Anything else at that position is left as it is for the check to refuse, so a `null` never turns into an epoch date and a `true` never turns into `1n`. The plain decoders follow the same rule.

Undeclared properties are kept by default. Set `strategy` to change that:

| Strategy | What happens to properties your type doesn't declare |
| --- | --- |
| `preserve` (default) | Kept. The cheapest option: no extra pass, no key check. |
| `strip` | Set to `undefined`, at every level. The safer choice for a payload you are about to store or forward. |
| `fail` | Rejected, the same rule `checkUnknowns` applies to validators. |

Set `parse: {strategy: 'strip'}` in the plugin options to change the default for every parser. A per-call `strategy` still wins for that one parser.

Use `createJsonDecoderFn<T>()` instead when the data is already trusted and you just want it decoded, and `createValidateFn<T>()` when you have a value in hand rather than a wire payload.

## Decoders Return Data Only

Both `createJsonDecoderFn<T>()` and `createBinaryDecoderFn<T>()` return `DataOnly<T>`, not bare `T`. A value rebuilt from JSON or bytes holds only serializable data, so the return type leaves out anything that cannot be sent, methods for one, and stops you from reaching for it.

<code-import path="packages/examples/src/guide/json-dataonly.ts" lang="ts" commentStart="// start-dataonly" commentEnd="// end-dataonly" />

This costs nothing at runtime. Only the type changes.

A property whose serialization is guarded by enumerability (anything optional inherited from Error, or one you tag with `@nonEnumerable`) is always optional in `DataOnly<T>`, so the type never promises a value the wire might omit.

## Why Only Serializable Data

Validation and both codecs use the **serializable projection** of your type, not every last TypeScript member. Functions, methods and symbols are silently dropped, so a `{name: string; onClick: () => void}` produces a validator that only checks `name`.

The build reports a `VL010`-family **Warning** when this happens, and a warning never stops anything. At a position that would throw at runtime, like a union member or array element, it becomes a **RuntimeError**: the function is still written, it just throws when you call it, and the build fails (see [Diagnostics](/runtypes/diagnostics/error-levels)). The reasoning is in [Built on typescript-go](/runtypes/introduction/built-on-typescript-go#extending-typescript-go-without-modifying-it).

## Encoding Values Without the JSON String

`createJsonEncoderFn` and `createJsonDecoderFn` give you a string. When you already own the JSON envelope (a framework that parses one request body and stringifies one response), you want the transform at the value level instead, with no extra stringify and parse.

`createPrepareForJsonFn` turns a typed value into a JSON-safe value, and `createRestoreFromJsonFn` turns it back. Both take the same `strategy`, so pair `clone` with `clone`.

<code-import path="packages/examples/src/guide/json-value-level.ts" lang="ts" commentStart="// start-value-codec" commentEnd="// end-value-codec" />

Your code owns the `JSON.stringify` and the `JSON.parse`, so many values can share one envelope with a single stringify and a single parse.

A root `undefined` or `void` is safe: `prepare` passes the value through and `restore` returns `undefined`, so neither throws. Wrap the value in your own array or object to keep a bare `undefined` from breaking `JSON.stringify`.
