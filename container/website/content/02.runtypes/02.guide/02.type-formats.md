## Available Formats

Formats come in five families. As a type the name is capitalized (`TF.Email`, `TF.Int32`, `TF.StringDate`), and as a builder it is a call (`TF.email()`, `TF.int32()`, `TF.stringDate()`).

| Family | A few of the named formats |
| --- | --- |
| **String** | `email`, `emailAddress`, `uuidv4`, `uuidv7`, `url`, `uri`, `ipv4`, `ipv6`, `domain`, `hostname`, `idnHostname`, `creditCard`, `regexString`, `alpha`, `numeric`, `lowercase` |
| **Number** | `int8`, `int16`, `int32`, `uint8`, `uint16`, `uint32`, `integer`, `float`, `positive`, `negative`, `currency` |
| **BigInt** | `bigInt64`, `bigUInt64`, `bigPositive`, `bigNegative`, `bigPositiveInt`, `bigNegativeInt` |
| **Date / time** | three representations, all sharing the same bounds (see below): string-encoded (`stringDate`, `stringTime`, `stringDateTime`), native `date`, and the TC39 `temporal.*` types |
| **Array / object / Set / Map** | not named presets but options on a collection: `minItems`, `maxItems`, `uniqueItems`, `contains`, `minProperties`, `maxProperties`, `patternProperties`, `propertyNames` (see [below](#array-object-map-and-set-constraints)) |

These formats match a JSON Schema keyword and work anywhere else too: `TF.StringDuration` for a length of time (`P4DT12H30M5S`), `TF.JsonPointer` and `TF.RelativeJsonPointer` for the path syntax, `TF.UriReference` and `TF.UriTemplate` for the URI variants, and `TF.Iri` / `TF.IriReference` for the same shapes with non-ASCII characters allowed.

`TF.Hostname` accepts a single label like `localhost`, where `TF.Domain` needs a dotted name. `TF.IdnHostname` also accepts a name written in its own script, such as `실례.테스트`. Both hostname formats decode and check a punycode label (the `xn--` form), so a label that only looks like one fails.

`TF.EmailAddress` and `TF.IdnEmail` take the full address grammar: a quoted local part may hold spaces or an at sign, and the domain may be an address literal in brackets. `TF.Email` is the everyday shape a form field wants. All three need a dotted domain, so `joe@tld` fails even though a strict reading of the RFC allows it.

Only `TF.EmailStrict` takes `localPart` and `domain` options, to limit each half of an address. On another email format they are a type error.

`TF.RegexString` is a string that must compile as a regular expression. With the `pattern` option the value must match a regex; here the value is one.

The IP formats accept only an address: `TF.IPv4` passes `127.0.0.1` and rejects `localhost`. To accept `localhost` too, use `TF.IPv4<{allowLocalHost: true}>` (builder `TF.ipv4({allowLocalHost: true})`). Loopback addresses like `::1` are ordinary addresses and never need it.

`TF.Currency` (builder `TF.currency()`) is a number marked as money: it sets the `isCurrency` param on the plain number format. It validates and serializes like `TF.Number`, and [friendly error messages](/runtypes/ai-integration/i18n#money-in-messages) use the mark to show a broken limit with the right currency symbol and decimals for the reader's language.

## Transforms

A format checks a value; a transform rewrites it, such as trimming a name or lowercasing an email. Put it under the `transform` key, in the format's params or in the Transform wrapper around any string type.

<code-import path="packages/examples/src/guide/type-formats-transforms.ts" lang="ts" />

Every string format takes `trim`, `lowercase`, `uppercase`, `capitalize`, `replace` (first match) and `replaceAll`, and `TF.CreditCard` adds `stripSeparators`. The presets `TF.Lowercase`, `TF.Uppercase` and `TF.Capitalize` are plain strings with one transform each.

`TF.Email`, `TF.Domain`, `TF.IP` and `TF.Url` never lowercase on their own, because an email's local part and a URL path are case-sensitive. To lowercase one, write `TF.Email<{transform: {lowercase: true}}>`.

::tip
Transforms run in a fixed order: the replacements and the separator strip first, then trim, then the case change.
::

## Applying a Transform

A transform is never part of validation, parsing, encoding or decoding. Only two things apply one:

- `createFormatTransformFn` gives you the rewrite as a function, for a value you hold yourself.
- A mion route with `sanitizeParams` applies it to the request params after decoding and before validation, on the server and in the client. See [Sanitizing Params](/rpc/server/validation#sanitizing-params) on the mion site.

A route is sanitized on both ends, so a transform must give the same answer when applied twice. Trim, the case changes, `replaceAll` and `stripSeparators` do. `replace` only rewrites the first match, so a value with several matches changes again on the second pass. Prefer `replaceAll`, and keep one case change per field: lowercase followed by capitalize is not stable for a letter whose uppercase is two letters, such as the German sharp s.

## Date, Time and Temporal Formats

A date comes in three shapes, each with its own format family. All three take the **same** `min` / `max` / `gt` / `lt` bounds, written in the type's own ISO form: a `PlainDate` takes `'2020-01-01'`, an `Instant` takes `'2020-01-01T00:00:00Z'`.

- **String-encoded**: `TF.StringDate`, `TF.StringTime`, `TF.StringDateTime` check an ISO string in a fixed layout (`'2020-01-01'`, `'08:30'`).
- **Native `Date`**: `TF.Date` checks a real JS `Date`; `TF.DateFuture` / `TF.DatePast` are ready-made (a `Date` that's `>= now` / `<= now`).
- **TC39 Temporal**: `TFT.PlainDate`, `TFT.ZonedDateTime`, `TFT.Instant`, `TFT.PlainTime`, `TFT.PlainDateTime`, `TFT.PlainYearMonth` check an actual `Temporal.*` instance. Import them from `@mionjs/run-types/formats/temporal` (as `TFT`), so apps that don't use Temporal never pull in its lib.

```ts
import type * as TF from '@mionjs/run-types/formats';
import type * as TFT from '@mionjs/run-types/formats/temporal';

// The same "2020 or later" bound, two representations:
type DateString = TF.StringDate<{min: '2020-01-01'}>; // an ISO string
type PlainDate = TFT.PlainDate<{min: '2020-01-01'}>;  // a Temporal.PlainDate
```

::note
Temporal values are validated by **identity** (`instanceof`), not by structural shape. `Temporal.PlainMonthDay` and `Temporal.Duration` have no min/max ordering, so they take no bounds. `DataOnly<Temporal.PlainDate>` stays a `Temporal.PlainDate`.
::

## Date Format Builders

With builders, use `TF.date(...)` and the `TFT.*` temporal namespace.

```ts
import * as TF from '@mionjs/run-types/formats';
import * as TFT from '@mionjs/run-types/formats/temporal';

TF.date({max: 'now'});               // a Date in the past
TFT.plainDate({min: '2020-01-01'});  // a Temporal.PlainDate, 2020 on
TFT.instant({min: 'now-PT1H'});      // an Instant within the last hour
```

## Relative Date Bounds

Write a bound as `now`, or `now` plus or minus an **ISO-8601 duration** such as `P1Y2M10D` (1 year, 2 months, 10 days), `P1W` (1 week) or `PT12H30M` (12 hours, 30 minutes). The build checks that the units fit the field.

<code-import path="packages/examples/src/guide/type-formats-relative.ts" lang="ts" />

| Family | Relative units |
| --- | --- |
| Date-only (`TF.stringDate`, `TFT.plainDate`, `TFT.plainYearMonth`) | date: `Y` `M` `W` `D` |
| Time-only (`TF.stringTime`, `TFT.plainTime`, `TFT.instant`) | time: `H` `M` `S` |
| Date + time (`TF.stringDateTime`, native `TF.date`, `TFT.plainDateTime`, `TFT.zonedDateTime`) | both |

::tip
`min` / `max` are inclusive, `gt` / `lt` exclusive. Use one or the other per edge: the build rejects a type with both, such as `{min: 0, gt: 0}`.
::

## Array, Object, Map and Set Constraints

Arrays, objects, Maps and Sets keep the shape you wrote in TypeScript. Limits on the collection itself go in one options bag, with one wrapper per collection kind.

<code-import path="packages/examples/src/guide/structural-formats.ts" lang="ts" commentStart="// start-array" commentEnd="// end-array" />

| | Type-first | Type Builder |
| --- | --- | --- |
| Arrays and tuples | `TF.FormattedArray<T[], {...}>` | `RT.array(item, {...})` |
| Objects and records | `TF.FormattedObject<Shape, {...}>` | `RT.object(config, {...})`, `RT.record(inner, {...})` |
| Sets | `TF.FormattedSet<Set<T>, {...}>` | `RT.set(item, {...})` |
| Maps | `TF.FormattedMap<Map<K, V>, {...}>` | `RT.map(key, value, {...})` |

::tip
No TypeScript type says "an array whose entries differ", so `uniqueItems` keeps the closest shape (`string[]`) and the generated function does the check.
::

## Collection Options

An entry is one item of an array, one member of a Set, or one `[key, value]` pair of a Map. On a Map, put `unknown` in the half of `contains` you do not care about.

<code-import path="packages/examples/src/guide/structural-formats.ts" lang="ts" commentStart="// start-contains" commentEnd="// end-contains" />

| Option | On | What it asks |
| --- | --- | --- |
| `minItems` / `maxItems` | every collection | how many entries there may be |
| `uniqueItems` | every collection | no two entries are equal, compared by value |
| `contains` | every collection | at least one entry matches a second type |
| `minContains` / `maxContains` | every collection | how many entries must match `contains` |
| `minProperties` / `maxProperties` | objects | how many keys the value may carry |
| `patternProperties` | objects | keys matching a pattern carry a given type |
| `propertyNames` | objects | every key satisfies a string format |

::note
These are the same options a JSON Schema uses, under the same names. A [generated JSON Schema document](/runtypes/guide/json-schema-generation) writes `uniqueItems` or `patternProperties` as the standard keywords, so it enforces exactly what the type does. A bounded Set or Map declares them on the array it travels as.
::

## Regex Patterns

Write a `pattern` as `{source: '...'}`; a bare regex value like `/x/` is not accepted. To reuse one across types, register it with [`registerFormatPattern`](/runtypes/guide/pure-functions), then reference it by `typeof` in a type or pass the value straight to a builder. A registered pattern can also carry a `message`, which appears as the reported value when validation fails.

## Mock Values for Patterns

A `pattern` does not need `mockSamples`: declare none and the build generates valid values from the regex, fresh on every build (a literal seed on `createMockDataFn` keeps them fixed, see [Mocking](/runtypes/guide/mocking)). Declare your own samples for curated values, or when the build reports it cannot generate for a construct like lookbehind.

::tip
Declared samples always win and must fit any length bounds the type declares. They are checked at build time with the regular expression engine your app runs on, so a bad sample or a pattern with a syntax error fails the build.
::

## Unsafe Regex Patterns

By default, the build rejects a `pattern` that can match the same text more than one way, and quotes the part responsible. On an input that almost matches, JavaScript tries every combination: with `^(\w+\s?)*$`, a few dozen characters freeze the validator.

The check reads the pattern rather than timing it, so it gives the same answer on every machine and JavaScript runtime. It reports a pattern only when it can point at the two routes through the loop, so a dense pattern that happens to nest quantifiers is fine.

::tip
If a pattern really is safe and the check rejects it, add `unsafePattern: true` next to its `source`.
::

## Smaller Binary Payloads

The binary codec uses a format constraint to size the payload. A fixed width like `int8`, or a `min` and `max` bound, packs the value into the narrowest field that fits, instead of the 8 bytes an unconstrained `number` or `bigint` needs. The [serialization formats benchmark](/benchmarks/runtypes/serialization-formats) measures the saving per type.
