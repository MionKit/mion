## Available Formats

Formats come in five families.

| Family | A few of the named formats |
| --- | --- |
| **String** | `email`, `emailAddress`, `uuidv4`, `uuidv7`, `url`, `uri`, `ipv4`, `ipv6`, `domain`, `hostname`, `idnHostname`, `creditCard`, `regexString`, `alpha`, `numeric`, `lowercase` |
| **Number** | `int8`, `int16`, `int32`, `uint8`, `uint16`, `uint32`, `integer`, `float`, `positive`, `negative`, `currency` |
| **BigInt** | `bigInt64`, `bigUInt64`, `bigPositive`, `bigNegative`, `bigPositiveInt`, `bigNegativeInt` |
| **Date / time** | three representations, all sharing the same bounds (see below): string-encoded (`stringDate`, `stringTime`, `stringDateTime`), native `date`, and the TC39 `temporal.*` types |
| **Array / object / Set / Map** | not named presets but options on a collection: `minItems`, `maxItems`, `uniqueItems`, `contains`, `minProperties`, `maxProperties`, `patternProperties`, `propertyNames` (see [below](#array-object-map-and-set-constraints)) |

Type-first, the name is capitalized on the `TF` namespace: `TF.Email`, `TF.Int32`, `TF.BigInt64`, `TF.StringDate` (from `import * as TF from '@mionjs/run-types/formats'`). The matching builders are `TF.email()`, `TF.int32()`, `TF.bigInt64()`, `TF.stringDate()`.

::note
The fixed-width number/bigint formats (`int32`, `bigUInt64`, …) also tell the [binary codec](/runtypes/guide/binary-serialization) how many bytes to pack. A `TF.UInt8` field takes a single byte on the wire.
::

Some formats exist mainly so a JSON Schema keyword has something exact to mean: `TF.StringDuration` for a length of time (`P4DT12H30M5S`), `TF.JsonPointer` and `TF.RelativeJsonPointer` for the path syntax, `TF.UriReference` and `TF.UriTemplate` for the URI variants, and `TF.Iri` / `TF.IriReference` for the same shapes with non-ASCII characters allowed. They work the same way anywhere else.

`TF.Hostname` accepts a single label like `localhost`, where `TF.Domain` wants a dotted name. `TF.IdnHostname` also accepts a name written in its own script, such as `실례.테스트`. Both decode a punycode label (the `xn--` form) and check it, so a label that only looks like one fails.

`TF.EmailAddress` and `TF.IdnEmail` take the full addressing grammar: a quoted local part may hold spaces or an at sign, and the domain may be an address literal in brackets. `TF.Email` is the everyday shape a form field wants. All three expect a dotted domain, so `joe@tld` is rejected even though the strictest reading of the RFC would allow it.

`TF.RegexString` is a string that has to compile as a regular expression. That is a different question from the `pattern` option: there the value must match a regex, here the value is one.

The IP formats accept an address and nothing else: `TF.IPv4` passes `192.168.0.1` and `127.0.0.1`, and rejects the word `localhost`. When a setting takes either, opt in with `TF.IPv4<{allowLocalHost: true}>` (builder `TF.ipv4({allowLocalHost: true})`). The option covers that one hostname spelling; loopback addresses like `::1` are ordinary addresses and never need it.

`TF.CreditCard` (builder `TF.creditCard()`) checks a payment card number with the Luhn checksum. Pass `networks` to narrow it to the issuers a field accepts, or `separators` to change which characters are allowed between digits. Leaving `networks` out keeps the card-network table out of your bundle entirely.

Mock data builds a fresh valid number each draw, with a real prefix for its network. Set the `testCreditCards` mock option when the data reaches a payment sandbox, which only accepts the published test numbers.

<code-import path="packages/examples/src/guide/type-formats-credit-card.ts" lang="ts" />

`TF.Currency` (builder `TF.currency()`) is a number marked as a monetary amount, a preset that sets the `isCurrency` param on the plain number format. It validates and serializes exactly like `TF.Number`, and [friendly error messages](/runtypes/ai-integration/i18n#money-in-messages) use the mark to show a violated limit with the right currency symbol and decimals for the reader's language.

## Transforms

A format checks a value. A transform rewrites it: trim the spaces around a name, lowercase an email, strip the grouping from a card number.

A transform goes under the `transform` key, either inside the format's params or in the Transform wrapper around any string type.

<code-import path="packages/examples/src/guide/type-formats-transforms.ts" lang="ts" />

Every string format takes the same set: `trim`, `lowercase`, `uppercase`, `capitalize`, `replace` (first match) and `replaceAll`. `TF.CreditCard` adds `stripSeparators`. They run in a fixed order: the replacements and the separator strip first, then trim, then the case change. The presets `TF.Lowercase`, `TF.Uppercase` and `TF.Capitalize` are plain strings with one transform each.

A transform is never part of validation, parsing, encoding or decoding. Only two things apply one:

- `createFormatTransformFn` gives you the rewrite as a function, for a value you hold yourself.
- A mion route with `sanitizeParams` applies it to the request params after decoding and before validation, on the server and in the client. See [Sanitize params](/rpc/server/validation#sanitize-params) on the mion site.

A route is sanitized on both ends, so a transform must give the same answer when applied twice. Trim, the case changes, `replaceAll` and `stripSeparators` do. `replace` only rewrites the first match, so a value with several matches changes again on the second pass. Prefer `replaceAll`, and keep one case change per field: lowercase followed by capitalize is not stable for a letter whose uppercase is two letters, such as the German sharp s.

`TF.Email`, `TF.Domain`, `TF.IP` and `TF.Url` never lowercase on their own. A URL path is case-sensitive, and so is the local part of an email, so the field decides: `TF.Email<{transform: {lowercase: true}}>`.

::note
Earlier versions took `trim`, `lowercase` and friends as top-level params, and `stripSeparators` at the top of `TF.CreditCard`. Those keys moved under `transform`.
::

## Date, Time and Temporal Formats

A date value comes in three shapes, with a format family for each. All three take the **same** `min` / `max` / `gt` / `lt` bounds, so a constraint means the same thing whichever one you pick:

- **String-encoded**: `TF.StringDate`, `TF.StringTime`, `TF.StringDateTime` check an ISO string in a fixed layout (`'2020-01-01'`, `'08:30'`).
- **Native `Date`**: `TF.Date` checks a real JS `Date`; `TF.DateFuture` / `TF.DatePast` are ready-made (a `Date` that's `>= now` / `<= now`).
- **TC39 Temporal**: `TFT.PlainDate`, `TFT.ZonedDateTime`, `TFT.Instant`, `TFT.PlainTime`, `TFT.PlainDateTime`, `TFT.PlainYearMonth` check an actual `Temporal.*` instance. Import them from `@mionjs/run-types/formats/temporal` (as `TFT`), so apps that don't use Temporal never pull in its lib.

```ts
import type * as TF from '@mionjs/run-types/formats';
import type * as TFT from '@mionjs/run-types/formats/temporal';

// The same "2020 or later" bound, two representations:
type DateString = TF.StringDate<{min: '2020-01-01'}>; // an ISO string
type PlainDate = TFT.PlainDate<{min: '2020-01-01'}>;  // a Temporal.PlainDate
```

The bound literal is written in the type's own ISO form. A `PlainDate` takes `'2020-01-01'`, an `Instant` takes `'2020-01-01T00:00:00Z'`. (`Temporal.PlainMonthDay` and `Temporal.Duration` have no min/max ordering, so they're validated by identity only, with no bounds.)

With builders, the same calls are `TF.date(...)` and the `TFT.*` temporal namespace:

```ts
import * as TF from '@mionjs/run-types/formats';
import * as TFT from '@mionjs/run-types/formats/temporal';

TF.date({max: 'now'});               // a Date in the past
TFT.plainDate({min: '2020-01-01'});  // a Temporal.PlainDate, 2020 on
TFT.instant({min: 'now-PT1H'});      // an Instant within the last hour
```

::note
Temporal values are validated by **identity** (`instanceof`), not by structural shape. They also survive `DataOnly` whole, so `DataOnly<Temporal.PlainDate>` stays a `Temporal.PlainDate`.
::

## Relative Date Bounds

Write a bound as `now`, or `now` plus or minus an **ISO-8601 duration** (`now+P…` / `now-P…`):

<code-import path="packages/examples/src/guide/type-formats-relative.ts" lang="ts" />

The `P…` tail is a full ISO-8601 duration, such as `P1Y2M10D` (1 year, 2 months, 10 days), `P1W` (1 week), or `PT12H30M` (12 hours, 30 minutes). The build checks that the units fit the field.

| Family | Relative units |
| --- | --- |
| Date-only (`TF.stringDate`, `TFT.plainDate`, `TFT.plainYearMonth`) | date: `Y` `M` `W` `D` |
| Time-only (`TF.stringTime`, `TFT.plainTime`, `TFT.instant`) | time: `H` `M` `S` |
| Date + time (`TF.stringDateTime`, native `TF.date`, `TFT.plainDateTime`, `TFT.zonedDateTime`) | both |

`min` / `max` are inclusive, `gt` / `lt` exclusive. Give each edge as one or the other, never both. The build rejects a type that declares both, such as `{min: 0, gt: 0}`.

## Array, Object, Map and Set Constraints

Arrays, objects, Maps and Sets keep the shape you already wrote in TypeScript. What is left to say is about the collection itself, and it goes in one options bag, with one wrapper per collection kind.

| | Type-first | Type Builder |
| --- | --- | --- |
| Arrays and tuples | `TF.FormattedArray<T[], {...}>` | `RT.array(item, {...})` |
| Objects and records | `TF.FormattedObject<Shape, {...}>` | `RT.object(config, {...})`, `RT.record(inner, {...})` |
| Sets | `TF.FormattedSet<Set<T>, {...}>` | `RT.set(item, {...})` |
| Maps | `TF.FormattedMap<Map<K, V>, {...}>` | `RT.map(key, value, {...})` |

| Option | On | What it asks |
| --- | --- | --- |
| `minItems` / `maxItems` | every collection | how many entries there may be |
| `uniqueItems` | every collection | no two entries are equal, compared by value |
| `contains` | every collection | at least one entry matches a second type |
| `minContains` / `maxContains` | every collection | how many entries must match `contains` |
| `minProperties` / `maxProperties` | objects | how many keys the value may carry |
| `patternProperties` | objects | keys matching a pattern carry a given type |
| `propertyNames` | objects | every key satisfies a string format |

An entry is one item of an array, one member of a Set, or one `[key, value]` pair of a Map. On a Map, put `unknown` in the half of `contains` you do not care about.

## Branded Types

By default a format is still structurally a `string` or `number`, so a raw string fits where a `UserId` belongs. Add a **brand name** (the second type argument) and the format becomes *nominal*: nothing else is assignable to it without an explicit `as` cast.

::tip
The `as` cast marks the exact line where a raw value becomes a `UserId`, usually right after you validate it. Everywhere else, the type system keeps your ids, cents and timestamps from getting mixed up.
::

With builders, use the `brand()` tag: `TF.string({minLength: 1}, TF.brand('UserId'))`.

## Custom Formats

`TF.String`, `TF.Number` and `TF.BigInt` take your own params when no named format fits.

<code-import path="packages/examples/src/guide/type-formats-custom.ts" lang="ts" />

The common params:

| Format | Params |
| --- | --- |
| `TF.String` | `minLength`, `maxLength`, `length`, `pattern`, `allowedChars`, `allowedValues`, … |
| `TF.Number` | `min`, `max`, `gt`, `lt`, `integer`, `float`, `multipleOf`, `isCurrency` |
| `TF.BigInt` | `min`, `max`, `gt`, `lt`, `multipleOf` (all `bigint` literals, e.g. `0n`) |

::note
A `pattern` does not need `mockSamples`: declare none and the build generates valid values from the regex, fresh on every build (a literal seed on `createMockDataFn` pins them, see [Mocking](/runtypes/guide/mocking)). Declare your own samples for curated values, or when the build reports it cannot generate for a construct like lookbehind. Declared samples always win, must fit any length bounds the type declares, and are checked at build time with the same regular expression engine your app runs on, so a bad sample or a pattern with a syntax error fails the build. Write the pattern as `{source: '...'}`; a bare regex value like `/x/` is not accepted. To reuse one across types, register it with [`registerFormatPattern`](/runtypes/guide/pure-functions), then reference it by `typeof` in a type or pass the value straight to a builder; a registered pattern can also carry a `message`, which appears as the reported value when validation fails.
::

::tip
**Every `pattern` is checked for runaway backtracking, and the check is on by default.** Some regular expressions can match the same text more than one way, and on an input that almost matches, JavaScript tries every combination in turn. `^(\w+\s?)*$` is one of those: a few dozen characters freeze the validator. The build rejects such a pattern and quotes the part responsible.
::

The check reads the pattern itself rather than timing it, so it gives the same answer on every machine and under every JavaScript runtime. It reports a pattern only when it can point at the two routes through the loop, so a dense pattern that happens to nest quantifiers is fine.

If a pattern really is safe and the check reads it wrongly, add `unsafePattern: true` next to its `source` and the build accepts it.

## Smaller Binary Payloads

The binary codec uses a format constraint to size the payload. A fixed width like `int8`, or a `min` and `max` bound, packs the value into the narrowest field that fits, instead of the 8 bytes an unconstrained `number` or `bigint` needs. The [serialization formats benchmark](/benchmarks/runtypes/serialization-formats) measures the saving per type.
