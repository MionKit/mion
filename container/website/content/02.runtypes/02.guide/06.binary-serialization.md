## Binary Round Trip

`createBinaryEncoderFn` and `createBinaryDecoderFn` are the [JSON pair](/runtypes/guide/json-serialization) with a different output: compact bytes instead of text. The codec is generated from your type, so a `Date` comes back as a `Date`, and a `Map` as a `Map`.

The encoder returns a zero-copy `Uint8Array` whose `byteLength` is the exact size on the wire; call `slice()` for an owned copy. The decoder takes those bytes, or any buffer or view.

Use binary when you move lots of records and both ends are yours (WebSockets, game state, IoT). Use JSON when a human or a third party reads the payload, or you need it `curl`-able.

A buffer that does not fit the type throws a `BinaryDecodeError` instead of returning garbage. The decoder rebuilds values without validating them, so check the result with `createValidateFn` when the bytes come from outside.

## Buffer Sizing Strategies

The `sizeStrategy` option picks how the encoder sizes its buffer, and with it the shape of the function you get back.

| Strategy | Function | What it does |
| --- | --- | --- |
| `dynamic` (default) | `(val) => Uint8Array` | Predicts the size from earlier encodes and grows the buffer when a value runs larger. Nothing to configure. |
| `precalculate` | `(val) => Uint8Array` | Measures the value once, then allocates exactly that. Roughly a quarter slower, and the buffer is never too large. |
| `initialSize` | `(val, size) => Uint8Array` | You pass the buffer size each call. It never grows, so a value that does not fit throws a `RangeError`. |
| `intoBuffer` | `(val, into) => Uint8Array` | You pass the `ArrayBuffer` to write into each call. It writes a zero-copy view into your buffer and throws if the value does not fit. |

To pick a safe size for `initialSize` or `intoBuffer`, ask `createBinarySizerFn` for the exact byte count. It allocates no buffer.

## Smaller Payloads with Format Constraints

The codec reserves a worst case width whenever it cannot tell a value's range, so an unconstrained `number` takes a fixed 8 bytes and an unconstrained `bigint` is written as a decimal string. Once the type narrows an integer to a known range (a fixed width like `int8` or `uint16`, or an `integer` flag with a `min` and `max` bound), the encoder packs it into far fewer bytes: a `uint8` into 1 byte, a `{integer: true, min: 0, max: 1000}` number into 2. The [serialization formats benchmark](/benchmarks/runtypes/serialization-formats) pairs each unconstrained value against its constrained twin.

## Detecting Circular References

A value that points back at itself makes the encoder recurse until the stack overflows. The binary encoder takes the same per-call `rejectCircularRefs` option as the [JSON one](/runtypes/guide/json-serialization#detecting-circular-references), and only the encoders that set it carry the check.

## Behaviour Shared with JSON Serialization

These work the same as on the [JSON serialization](/runtypes/guide/json-serialization) page:

- [Custom Class Serializers](/runtypes/guide/json-serialization#custom-class-serializers): one `registerClassSerializer` call covers both codecs.
- [Decoders Return Data Only](/runtypes/guide/json-serialization#decoders-return-data-only): bytes can only carry data, so methods are left out of the type that comes back.
- [Serializable Data Only](/runtypes/guide/json-serialization#why-only-serializable-data): functions, methods and symbol keys are dropped, with a build-time Warning.
- [Decoding Untrusted Input](/runtypes/guide/decoding-untrusted-input): what the decoder refuses on its own (a cut-off buffer, a bad count, invalid UTF-8, a prototype-named key) and what it leaves for validate.
