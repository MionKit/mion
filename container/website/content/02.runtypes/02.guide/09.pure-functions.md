**Pure functions** are small, self-contained helpers that the compiler inlines into the generated code. A helper that reaches outside itself fails the build.
::

## Pure Function Rules

A helper must be self-contained: no outer-scope captures, no `this`, no `await` or `yield`, and no dynamic `import`. Anything it needs goes inside the function. Break a rule and the build reports an error.

Standard built-ins are allowed: `Math`, `JSON`, `ArrayBuffer`, `DataView`, typed arrays like `Uint8Array`, `TextEncoder`, `TextDecoder`, `btoa` and `atob`. I/O and async are not, because the helper is inlined into synchronous code: no `fetch` or network, no timers, no `process` or `globalThis`, nothing awaited. So `crypto.subtle.digest` does not fit (hash over typed arrays instead), while a synchronous call like `crypto.randomUUID` is fine.

Write the helper inline, right where you register it: a name anything else could reach is rejected.

```ts
// Rejected: a name something else could reach
import {validate} from './validators';        // imported
export const validate = (v) => /* … */ true;  // exported
const validate = (v) => /* … */ true;         // a named local binding
registerValidator(validate);

// Fine: inline at the call site
registerValidator((v: unknown) => typeof v === 'string');
```

## Publishing Pure Functions in a Package

A pure function registered in one package can be used from another, like any export. Build the package with a mion bundler plugin or with `mion compile`, and the build adds one directory next to the bundle, published with the rest of dist. With `mion compile`, put the gen dir inside the output dir, for example `--gen-dir dist/.mion`.

```
dist/
  index.js
  index.d.ts
  mion-pure-fns/
    index.json                     # maps every exported name to its id
    @acme/text/9Zt1bRm4cVaPqL.js   # one compiled file per pure function
    @acme/text/Q2xVn7eK0sLmYb.js
```

::tip
The directory is build-time input only, so it adds nothing to any bundle. Its files are the same compiled modules your own build uses.
::

## Using Pure Functions From a Package

A consuming build compiles only the functions it uses from that directory into its own output, and registers each one before anything calls it. A package built without mion has no such directory, so importing one of its ids fails the build with `PFE9016`, which names the id and the package. Build that package with mion, or publish its TypeScript sources with its output, and the build reads those instead.

## Looking Up a Pure Function at Runtime

`usePureFn` and the other tracked lookups need an id the build can read. When the id only exists at runtime, such as one from a request, use `getPureFnByKey` and `hasPureFnByKey`: they take a plain string, and the build does not check them. Keep `usePureFn` for ids known at build time.

```ts
import {getRTUtils} from '@mionjs/run-types';

// wireId came in over the network
if (getRTUtils().hasPureFnByKey(wireId)) {
  const fn = getRTUtils().getPureFnByKey(wireId);
  // dispatch on it
}
```

## Sharing Compiled Functions Across Bundles

A validator or encoder the build generates in one bundle can run in another that never runs the compiler, such as a browser client; mion's router works this way. Send the entry's `CompiledFnData`, whose `code` field holds the function body as text. On the other side, restore it with `buildFactoryFromCode` and write it into the runtime cache with `addToRTCache`.

```ts
import {getRTUtils, buildFactoryFromCode, type CompiledFnData, type CompiledTypeFn} from '@mionjs/run-types';

// `wire` arrived over the network as plain data.
function ingest(wire: CompiledFnData) {
  const restored: CompiledTypeFn = {...wire, createRTFn: buildFactoryFromCode(wire.code!)};
  getRTUtils().addToRTCache(restored);
}

// later, on the client, look it up by its hash
const isUser = getRTUtils().getRTFn(rtFnHash);
```

Pure functions work the same way, with `buildPureFnFactoryFromCode` and `addPureFn`. Your framework decides which entries a payload needs and how to version the envelope.

## Overriding Generated Functions

The `overrideX` helpers register your own pure function for one type, and every matching `createX` call returns it instead of the generated body. Use one for a hand-tuned encoder, a wire format that is not the plain shape of your type, or a one-off bug workaround.

```ts
import {overrideJsonEncoder, createJsonEncoderFn} from '@mionjs/run-types';

// declared once, near the type; the function must be pure
overrideJsonEncoder<User>((user) => `{"id":${user.id}}`);

// the call site does not change
const encode = createJsonEncoderFn<User>();
```

Every factory has an override twin (`overrideValidate`, `overrideJsonEncoder`, `overrideBinaryEncoder`, and so on). Your function takes the same arguments as the generated one: a validation-errors override receives the value, the path, and the errors list.

You can register one override per type and function; a second one, with any body, is a build error. Decoders use validation to tell union branches apart, so a looser validator loosens those decoders too, and the build warns you.

## Limiting an Override to One Type

An override is matched by the **shape** of the type, not its name, so `overrideValidate<string>` applies to every string in the build, including string fields inside other objects. Give the type a brand when you mean one specific type.

```ts
type UserId = string & {readonly __brand: 'UserId'};

// Only UserId, not every string.
overrideValidate<UserId>((v) => typeof v === 'string' && (v as string).startsWith('u_'));
```
