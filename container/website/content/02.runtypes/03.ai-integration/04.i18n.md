[Experimental]{.rt-badge-experimental} The enrichment workflow works today; the generated file shape and the commands may still change between minor versions.

Your [`FriendlyText<T>`](/runtypes/ai-integration/friendly-type) map is the source language: it already holds every label and error message for a type. There is no separate message catalog to maintain.

A translation is one optional file per locale, with the same shape. Every string in it is optional too: a blank one falls back to the source text. A half-translated app renders the rest in the source language.

## Translation Workflow

List your locales in the same tsconfig plugin entry that holds the rest of your [configuration](/runtypes/introduction/configuration):

```json
{
  "compilerOptions": {
    "plugins": [
      {
        "name": "mion",
        "i18n": {
          "sourceLocale": "en",
          "locales": ["es", "pl", "pt-BR"]
        }
      }
    ]
  }
}
```

Then run the same loop as the rest of the [enrichment workflow](/runtypes/ai-integration/workflow-and-commands): scaffold a locale, fill the blanks, keep it in sync.

```bash
# scaffold the Polish translation files; existing files are left alone
mion enrich --i18n pl

# re-sync after a change, keeping everything you wrote
mion enrich --i18n pl --update

# every configured locale in one go
mion enrich --i18n all --update

# CI gate: fail if any translation is missing, untranslated, or out of date
mion enrich --i18n all --require-complete

# clear the comments parked by removed fields
mion enrich --i18n pl --prune
```

`enrich --i18n --no-emit` reports a missing translation file, unfilled blanks, an out of date translation, and parked leftovers awaiting a prune. These are warnings by default and the command still succeeds. Add `--require-complete` to fail that one run, or set `i18n.strict: true` to fail every run. Rendering at runtime stays lenient either way.

## Translation Files

Translations live under `<genDir>/enriched/i18n/<locale>/`, mirroring your source tree like the friendly files do. The locale is a folder name, so a regional tag like pt-BR works as-is:

```
src/.mion/enriched/
  friendly/models/user.ts      friendlyUser (the source language)
  mock/models/user.ts          mockUser (mock data is never translated)
  i18n/pl/models/user.ts       pl_friendlyUser (Polish)
  i18n/pt-BR/models/user.ts    pt_BR_friendlyUser (Brazilian Portuguese)
```

Each file exports one const per type, prefixed with the locale and typed `FriendlyText<T>`: a locale file is a friendly map written in another language. A scaffold arrives with every string blank and marked `@todo`, never a copy of your source text:

Fill what you can, leave the rest blank:

<code-import path="packages/examples/src/enrich/i18n-pl.ts" lang="ts" />

[Placeholder tokens](/runtypes/ai-integration/friendly-type#message-placeholders) work as they do in the source map, and a field using the [`rt$default` mode](/runtypes/ai-integration/friendly-type#one-message-per-field) has one string to translate.

The friendly map and every locale file are generated straight from your type, never from each other. Run `enrich --i18n pl --update` after a change: a new message arrives as a fresh blank, a removed one is parked as a comment (cleared by `--prune`), and nothing you wrote is lost. Renaming a type in your code renames its consts across every locale too.

## Plural Forms per Locale

Every count-carrying rule (`minLength`, `maxLength`, `min`, `max`, `lt`, `gt`) is scaffolded as a small object with exactly the plural forms that file's language uses. An English map gets `one` and `other`; the Polish translation of the same rule gets `one`, `few`, `many` and `other`. Every other rule (`type`, `pattern`, and the rest) stays a single string:

```ts
// in the English source map
minLength: {
  one: '$[label] needs at least $[val] character',
  other: '$[label] needs at least $[val] characters',
},
```

The right form is picked per locale with the browser's own plural rules (`Intl.PluralRules`). `other` is the only required form and covers any form you leave out, so you can delete the unused ones. A plain string also works on a count-carrying rule when one wording covers every count.

::warning
**The count is the rule's limit, not what the user typed.** For a field with minLength 3, the plural form and `$[val]` follow the 3, never the length of the received text. Write each form for the limit it will display.
::

A plural is translated as a whole: a half-filled one falls back to its own `other` form, and only a fully blank one falls back to the source.

## Locale Matching

The active locale does not need an exact match. The renderer tries the exact tag first, then trims it toward the base language, and falls back to the source map when nothing matches: ask for pt-BR with only a pt translation on hand and the pt file is used. The same logic is exported as `resolveLocale(locale, translations)` if you want to reuse it. A missing translation never throws.

## Money in Messages

A limit shown in a message is sometimes money. You never mark that in the template: the type already says what the value is, and `$[val]` renders it correctly for the active locale. Declare the field with the Currency format instead of a plain number:

Then tell the renderer which currency your app uses. Any ISO code works (EUR, USD, PLN), and like the locale it can be a `{value}` ref you switch at runtime:

<code-import path="packages/examples/src/enrich/i18n-currency-render.ts" lang="ts" />

Which currency a value is in is data your app owns, so it lives in this one renderer option, never in the type and never in the template. Without it, the limit renders as a plain localized number and a symbol is never guessed. An app with a single fixed currency can write the symbol into its templates and keep a plain number type.

## Dates in Messages

Date limits need no setup. A field typed with any of the date formats (a date string, a native Date bound, a Temporal type) renders its `$[val]` as a real date in the active locale. A relative limit like now-P1D stays as written, since it is not a fixed point in time.
