[Experimental]{.rt-badge-experimental} The enrichment workflow works today. The generated file shape and the commands may still change between minor versions.

`FriendlyText<T>` gives every field of a type a **label** and **error messages**. You [commit](/runtypes/ai-integration/workflow-and-commands) the map next to your type, and the compiler checks it against that type on every build. Use it to turn validation errors into messages people can read.

## FriendlyText Shape

The map mirrors your type. Every node is `{ rt$label, rt$errors, ...fields }`: the `rt$` keys hold the label and error messages for that field, every other key is a child field. Every field of the type appears, and every node carries both `rt$` keys.

The compiler scaffolds the map from your type with each blank marked `@todo`, then the agent fills those blanks. TypeScript and the compiler both check the map against the type, so a stale key or a wrong shape is an error before anything runs.

Container meta keys follow the type's shape: arrays use `rt$items`, tuples use `rt$slots`, a Map uses `rt$keys` and `rt$values`, a Set uses `rt$values`. Objects nest as the same node.

::tip
A blank string means "no custom text here", so a blank is always safe to leave. Never delete a key; the next sync scaffolds it back.
::

## Keeping FriendlyText in Sync

The map is committed next to your type. As the type changes, `enrich --update` re-syncs it and keeps every label and message you wrote. Where an edit would throw text away, the map keeps it as a comment instead of deleting it:

```ts
export const friendlyUser: FriendlyText<User> = {
  rt$label: 'User account',
  rt$errors: { type: '' },
  name: { rt$label: 'Full name', rt$errors: { type: '' } },
  /* @rtOrphanChild isActive: { rt$label: 'Active?', rt$errors: { type: '' } }, */   // you removed isActive
};
```

| The edit | What happens to your text |
| --- | --- |
| Rename a field or a whole type | it follows the field, untouched |
| Remove a field | its node is kept as a comment marked `@rtOrphanChild` |
| Change a field's type | the label always survives, and only the messages the new type no longer declares are kept as comments |
| Change a field to a different shape (a number becomes an array of objects) | the whole old node is kept as a comment and a fresh blank takes its place |
| Delete a whole type | its entire map is kept as a comment marked `@rtOrphan` |

## Pruning Comments Left by Removed Fields

The comments a removed field or type leaves behind stay until you clear them, one for each edit. `mion enrich --prune` clears them all in one pass.

```bash
mion enrich --prune
```

::tip
Prune removes only the `@rtOrphan` and `@rtOrphanChild` comments, never a live field and never a `@todo` blank. A field or type you removed and then bring back gets its text restored on the next `enrich --update`.
::

::note
The same applies to `MockData<T>`: a removed field's sample pool is kept as a comment, and `enrich --prune` clears it. Your authored data is never dropped, only kept as a comment or restored.
::

## Error Message Keys

Each `rt$errors` key names the rule the value broke: `minLength`, `pattern`, `min`, and so on. `type` is the catch-all for a value of the wrong kind, such as text where a number was expected.

| Failure | `rt$errors` key | `$[val]` resolves to |
| --- | --- | --- |
| base type-shape (wrong kind) | `type` | n/a |
| string `minLength` / `maxLength` | `minLength` / `maxLength` | the bound (`2`, `60`) |
| string `pattern` | `pattern` | n/a |
| number `min` / `max` | `min` / `max` | the bound |
| number `lt` / `gt` | `lt` / `gt` | the bound |
| number `integer` | `integer` | `true` |
| date/time `date` / `time` | `date` / `time` | n/a |
| `uuid` version | `version` | `'4'` |

**You get exactly the keys your type allows, and all of them.** A plain `name: string` can only fail as `type`; declare `minLength` and `maxLength` on the field and both keys join the node. TypeScript requires each key and rejects any key the field cannot fail, so a typo or a leftover key from an old rule shows up in your editor. Params that never fail validation (`isCurrency` and the `transform` block) never become keys.

::note
Errors **accumulate**: a value that breaks both `minLength` and `pattern` gives two messages, **one per broken rule**. For a single sentence covering the whole field, use the `rt$default` mode below.
::

## Message Placeholders

Templates are plain strings with `$[…]` tokens the renderer substitutes and the compiler validates:

| Token | Resolves to |
| --- | --- |
| `$[label]` | the node's `rt$label`, falling back to the raw field name |
| `$[val]` | the failed constraint's bound (e.g. `2` for `minLength: 2`) |
| `$[path]` | the dotted path to the field (`profile.email`) |
| `$[index]` | the array element index, for `rt$items` failures |

::note
`$[value]` (the *actual received value*) is out of scope for v1: the error carries no input value.
::

## Plural Messages

A count-carrying rule (`minLength`, `maxLength`, `min`, `max`, `lt`, `gt`) can hold one wording per plural form instead of a single string. The generator scaffolds the forms your language uses (an English map gets `one` and `other`) and you fill in the strings:

```ts
minLength: {
  one: '$[label] needs at least $[val] character',
  other: '$[label] needs at least $[val] characters',
},
```

The form is picked at runtime from the violated limit (the `3` in `minLength: 3`); `other` is the only required form. Every other rule (`type`, `pattern`, and the rest) stays a single string, and a single string on a count-carrying rule is still fine when one wording covers every count.

Each locale's file carries exactly the forms that language needs. See [Translations (i18n)](/runtypes/ai-integration/i18n).

## One Message per Field

Write `rt$default` as the node's only key and it becomes the message for every failure of that field. A node holds either the per-constraint keys or `rt$default`, never a mix, so a form can use `rt$default` for simple fields and per-constraint messages where precision matters. Like every other message, it stays translatable (see [Translations](/runtypes/ai-integration/i18n)).

## Rendering Messages

`createFriendlyText<T>(map)` returns a renderer with two methods. It needs nothing but the map and the errors:

<code-import path="packages/examples/src/enrich/friendly-render.ts" lang="ts" />

`errors()` groups failures by path, picks the template for the failed rule and fills in the `$[…]` tokens. Each result is a `FriendlyMessage`:

```ts
interface FriendlyMessage {
  path: string;     // dotted path to the field ('profile.email'); '' for the root
  label: string;    // the field's rt$label, or its raw last path segment as fallback
  message: string;  // the interpolated message
}
```

When a template is blank or missing, the renderer uses the raw field name as the label and a generic "is invalid" message.

::note
Error rendering works today. **Form-building UI is coming later.**
::
