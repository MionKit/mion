The lint plugin ships inside `@mionjs/devtools` and works with OXlint (its main target) and ESLint v9 flat config. The compiler that builds your code reports the problems, so your editor shows what the build shows.

## Lint Rules

The plugin has three rules, one per [level](/runtypes/diagnostics/error-levels). Every message starts with its code, like `[VL002]`: look it up in [All Diagnostics](/runtypes/diagnostics/all-diagnostics).

| Rule | Default | What it reports |
| --- | --- | --- |
| `mion/error` | `error` | Every Error and RuntimeError, the ones that stop the build. Also a tsconfig that does not load. |
| `mion/warning` | `warn` | Every Warning, and every error you lowered, marked `(downgraded)`. |
| `mion/info` | `off` | Every Info message: documented behaviour or advice. |

::tip
These rules are the same in every app and cannot turn a single check on or off. Change one error with a [comment or your tsconfig](/runtypes/diagnostics/error-levels): your editor and your build both follow it.
::

## Lint Plugin Setup

Extend the recommended config from `@mionjs/devtools` to turn on the three rules at the defaults above.

::code-group
```json [.oxlintrc.json]
{
  "$schema": "./node_modules/oxlint/configuration_schema.json",
  "extends": ["./node_modules/@mionjs/devtools/oxlint-recommended.json"]
}
```

```js [eslint.config.js]
import mion from '@mionjs/devtools/eslint';

export default [mion.configs.recommended];
```
::

## Lowering Errors in the Linter

The linter reads `downgradeErrors` from your tsconfig, so a code lowered there is a warning in your editor too. The build plugin's `downgradeErrors` option only applies to the build.

## Showing Info Messages

Turn on `mion/info` to see Info messages in your editor. The `levels` key in your tsconfig shows them in the [build](/runtypes/diagnostics/error-levels#showing-info-messages).

::code-group
```json [.oxlintrc.json]
{
  "rules": {"mion/info": "warn"}
}
```

```js [eslint.config.js]
export default [mion.configs.recommended, {rules: {'mion/info': 'warn'}}];
```
::

## Choosing the TypeScript Config

The plugin reads your full project `tsconfig.json`, so the linter checks types the way your build does: `lib`, `target`, `strict`, module resolution, custom conditions and path mappings all apply. By default it finds the config the way tsc does, searching upward from the directory the linter runs in. Point it at a different config with a setting:

::code-group
```json [.oxlintrc.json]
{
  "settings": {"mion": {"tsconfig": "tsconfig.lint.json"}}
}
```

```js [eslint.config.js]
export default [mion.configs.recommended, {settings: {mion: {tsconfig: 'tsconfig.lint.json'}}}];
```
::

::tip
A broken config is a `CFG001` error. Fix it and the next lint pass picks it up.
::

## Running the Linter from the CLI

The CLI reports the same problems, for CI jobs or scripts that do not run a node linter:

```bash
mion compile --no-emit
mion enrich src/.mion/enriched/friendly/src/models/user.ts --no-emit --json
mion enrich --no-emit --json
```

`compile --no-emit` reports the build's marker and serialization problems and writes nothing. `enrich --no-emit` on one file reports its tag, content and drift problems, and exits 1 on errors. Both hide Info messages unless your tsconfig sets `levels: 'all'`; `enrich --json` keeps them. With a directory, or no path, `enrich --no-emit` checks the whole mirror directory for drift.
