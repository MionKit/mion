## Named String Formats

Each format below also has a builder, named in lowercase (`TF.email()`, `TF.uuidv4()`). Date strings (`TF.StringDate` and friends) are on the [Date and Time Formats](/runtypes/type-formats/date-time) page.

| Group | Formats |
| --- | --- |
| Text | `TF.Alpha`, `TF.AlphaNumeric`, `TF.Numeric`, `TF.Lowercase`, `TF.Uppercase`, `TF.Capitalize` |
| Encodings | `TF.Base64`, `TF.Base32`, `TF.Base16`, `TF.JsonContent`, `TF.JsonContentBase64` |
| Ids | `TF.UUID`, `TF.UUIDv4`, `TF.UUIDv7` |
| Email | `TF.Email`, `TF.EmailAddress`, `TF.IdnEmail`, `TF.EmailPunycode`, `TF.EmailStrict` |
| Domains and hosts | `TF.Domain`, `TF.DomainUnicode`, `TF.DomainPunycode`, `TF.DomainStrict`, `TF.Hostname`, `TF.IdnHostname` |
| IP addresses | `TF.IP`, `TF.IPv4`, `TF.IPv6`, `TF.IPWithPort`, `TF.IPv4WithPort`, `TF.IPv6WithPort` |
| URLs | `TF.Url`, `TF.UrlHttp`, `TF.UrlFile`, `TF.Uri`, `TF.UriReference`, `TF.UriTemplate`, `TF.Iri`, `TF.IriReference` |
| JSON Schema keywords | `TF.StringDuration`, `TF.JsonPointer`, `TF.RelativeJsonPointer`, `TF.RegexString` |
| Payment | `TF.CreditCard` |

The JSON Schema formats work anywhere, not only in a schema. `TF.StringDuration` is a length of time (`P4DT12H30M5S`). `TF.Iri` and `TF.IriReference` are the URI shapes with non-ASCII characters allowed. `TF.RegexString` is a string that must compile as a regular expression, while the `pattern` option makes a value match one.

## Email Formats

`TF.Email` is the everyday shape a form field wants. `TF.EmailAddress` and `TF.IdnEmail` take the full address grammar: a quoted local part may hold spaces or an at sign, and the domain may be an address literal in brackets.

::tip
Every email format needs a dotted domain, so `joe@tld` fails even though a strict reading of the RFC allows it. Only `TF.EmailStrict` takes `localPart` and `domain` options, to limit each half of an address.
::

## Hostnames and Domains

`TF.Hostname` accepts a single label like `localhost`, where `TF.Domain` needs a dotted name. `TF.IdnHostname` also accepts a name written in its own script, such as `실례.테스트`. Both hostname formats decode and check a punycode label (the `xn--` form), so a label that only looks like one fails.

## IP Addresses

The IP formats accept only an address: `TF.IPv4` passes `127.0.0.1` and rejects `localhost`. To accept `localhost` too, use `TF.IPv4<{allowLocalHost: true}>` (builder `TF.ipv4({allowLocalHost: true})`). Loopback addresses like `::1` are ordinary addresses and never need it.

## Regex Patterns

Write a `pattern` as `{source: '...'}`, not a regex literal like `/x/`. To reuse one across types, register it with [`registerFormatPattern`](/runtypes/guide/pure-functions), then reference it by `typeof` in a type or pass the value straight to a builder. A registered pattern can also carry a `message`, which appears as the reported value when validation fails.

## Mock Values for Patterns

A `pattern` does not need `mockSamples`: declare none and the build generates valid values from the regex, fresh on every build (a literal seed on `createMockDataFn` keeps them fixed, see [Mocking](/runtypes/guide/mocking)). Declare your own samples for curated values, or when the build reports it cannot generate for a construct like lookbehind.

::tip
Declared samples always win and must fit any length bounds the type declares. They are checked at build time with the regular expression engine your app runs on, so a bad sample or a pattern with a syntax error fails the build.
::

## Unsafe Regex Patterns

By default, the build rejects a `pattern` that can match the same text more than one way, and quotes the part responsible. On an input that almost matches, JavaScript tries every combination: with `^(\w+\s?)*$`, a few dozen characters freeze the validator.

The check reads the pattern rather than timing it, so it gives the same answer on every machine and runtime. It reports a pattern only when it can point at two routes through the loop, so a pattern that merely nests quantifiers is fine.

::tip
If the check rejects a pattern that is safe, add `unsafePattern: true` next to its `source`.
::

## Transforms

A format checks a value; a transform rewrites it, such as trimming a name or lowercasing an email. Put it under the `transform` key, in the format's params or in the Transform wrapper around any string type.

<code-import path="packages/examples/src/guide/type-formats-transforms.ts" lang="ts" />

Every string format takes `trim`, `lowercase`, `uppercase`, `capitalize`, `replace` (first match) and `replaceAll`, and `TF.CreditCard` adds `stripSeparators`. The presets `TF.Lowercase`, `TF.Uppercase` and `TF.Capitalize` are plain strings with one transform each.

`TF.Email`, `TF.Domain`, `TF.IP` and `TF.Url` never lowercase on their own, because an email's local part and a URL path are case-sensitive. To lowercase one, write `TF.Email<{transform: {lowercase: true}}>`.

::tip
Transforms run in a fixed order: the replacements and the separator strip first, then trim, then the case change.
::

## Applying a Transform

A transform is never part of validation, parsing, encoding or decoding. Only two things apply one:

- `createFormatTransformFn` gives you the rewrite as a function, for a value you hold yourself.
- A mion route with `sanitizeParams` applies it to the request params after decoding and before validation, on the server and in the client. See [Sanitizing Params](/rpc/server/validation#sanitizing-params) on the mion site.

A route is sanitized on both ends, so a transform must give the same answer when applied twice. Trim, the case changes, `replaceAll` and `stripSeparators` do. `replace` only rewrites the first match, so a value with several matches changes again on the second pass. Prefer `replaceAll`, and keep one case change per field: lowercase followed by capitalize is not stable for a letter whose uppercase is two letters, such as the German sharp s.
