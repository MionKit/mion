RunTypes reports type problems while your project builds, each with a short code like `VL010`. The letters name the feature (`VL` is `createValidateFn`, `PJ` is `prepareForJson`) and the number the position: `001` to `009` are root errors, `010` and up are member-level warnings. Every code is listed in [All Diagnostics](/runtypes/diagnostics/all-diagnostics).

## The Three Levels

Every finding carries a level. The level answers one question: did the build produce the code, and does that code work.

::diagnostic-levels
::

An Error and a RuntimeError are both errors: they block a production bundle and make the `mion` command exit with a failure code. The difference is what happens while you develop. A RuntimeError is reported and your dev server keeps running, so a broken type never stops you working, and you can stand it down when the broken type is deliberate. An Error stops that piece of the build on the spot. Both print as `error`, the word your editor's problem matcher reads, so look the code up to tell which one you have.

::tip
Some RuntimeErrors describe a validator that passes everything. A type that could not be read becomes `any`, and a function built from `any` accepts every value. A missing import (`MKR007`), an unknown type name (`MKR013`) or a tsconfig `lib` with no base edition (`CFG002`) report that way. A deliberate `any` is only a warning.
::

## Downgrading a Code

List the codes you want reported as warnings in `downgradeErrors`. Every other code still fails the build.

```ts
mionVitePlugin({
  runTypes: {
    downgradeErrors: ['CTA003'],
  },
});
```

The finding still prints on every build, marked so you can tell it apart from a plain warning:

```
node_modules/some-lib/adapter.js(41,9): warning CTA003: ... (downgraded)
```

Use it for findings you cannot annotate: a type inside a package you do not own, or a problem in your project config. For a call in your own source, a comment on the line above it is better, and there is one for this job too (see [Downgrading a Code on One Line](#downgrading-a-code-on-one-line)). The option is documented in [Configuration](/runtypes/introduction/configuration#option-reference).

::tip
`'*'` downgrades every code at once, which suits adopting mion on an existing project. Name the codes once you know them. An Error cannot be downgraded, `'*'` included: the build produced no code for that piece, so naming one is refused with the reason.
::

## Expecting a Code on One Line

Put `@mion-expect-error` with the code on the line above the call. Only that finding on that line is removed:

```ts
// @mion-expect-error VL002
export const alwaysThrows = createValidateFn<symbol>();
```

It works like TypeScript's `@ts-expect-error`. When the finding goes away, the unused comment is reported as a warning (`EXP001`), so it cannot outlive the problem it was added for. Several codes go on one comment, separated by spaces or commas.

::tip
Always name the code. A bare comment covers anything reported on that line, and only your editor can then tell you it went stale, because the build does not run every check the editor does.
::

## Downgrading a Code on One Line

`@mion-downgrade-error` keeps the finding and stops it failing the build. Reach for it when the finding is right and you still want to read it, like a test that pins what a broken type does at runtime:

```ts
// @mion-downgrade-error VL002
export const alwaysThrows = createValidateFn<symbol>();
```

Placement, the code list and the stale check work like `@mion-expect-error`, and the finding prints as a warning carrying the same `(downgraded)` note. A comment that lowered nothing is reported (`DWN001`), as is one naming an unknown code, a code that always stops the build, or a code that is already a warning.

::tip
Use `@mion-expect-error` when the finding is noise at that line, and `@mion-downgrade-error` when it is worth seeing on every build.
::

## Standing a Code Down for a Whole File

Sometimes a whole file raises the same finding. A suite that checks what a broken type does at runtime can hit the same code on forty calls, and forty copies of the same comment help nobody.

Write the same comment as a block comment, before any code in the file, and it covers every line:

```ts
/* @mion-downgrade-error CES001 */
import {createCloneExactShapeFn} from '@mionjs/run-types';

// every CES001 in this file is now a warning, and none of them stops the build
```

This is how ESLint tells its two forms apart, so the shape should already look familiar. The rules:

| You write | Where | It covers |
| --- | --- | --- |
| `// @mion-expect-error VL002` | on its own line | the line below it |
| `/* @mion-expect-error VL002 */` | before any code | the whole file |
| `/* @mion-expect-error VL002 */` | anywhere lower down | the line below it |

Everything else works the same as the line forms. Both words take a file, several codes go on one comment, a comment that stood nothing down is reported (`EXP001` or `DWN001`), and a code that always stops the build is refused at file level too.

Leave the codes off and the comment covers every code in the file:

```ts
/* @mion-expect-error */
```

::tip
Name the codes when you can. A comment with no codes also hides findings you have never seen, including a real one introduced later, and it is the one thing on this page that can quietly let a problem through. It is worth it when a whole file is deliberate, and the per code form is what keeps the rest of the file honest.
::

Which of the three to reach for:

- **One call site is involved**: the line comment.
- **The file has one known finding, over and over**: the block comment with the code named.
- **The whole file is deliberate**: the block comment with no codes.

::tip
Adding the comment at the top does not turn the line comments below it into forty stale warnings. Each one still counts as doing its job. A line comment that was already stale stays reported, because the comment at the top makes it unnecessary, not correct.
::
