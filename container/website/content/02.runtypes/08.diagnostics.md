RunTypes flags type problems while your project builds, each as a short code like `VL010` or `PJ001`. The letters name the feature (`VL` is `createValidateFn`, `PJ` is `prepareForJson`), and the number marks the position: `001` to `009` are root errors, `010` and up are member-level warnings.

## The Three Levels

Every finding carries a level, and the level answers one question: could the build produce the code for this, and does that code work.

| Level | What it means | Can you stand it down |
| --- | --- | --- |
| Error | The build could not produce the code at all. Your tsconfig would not load, a batch could not be read, a type had no id to inject | No. Nothing you can set or write changes it |
| RuntimeError | The code is written, and it is broken when you call it. It throws, or it no longer checks what you asked for | Yes, with a comment or a setting |
| Warning | Worth knowing, nothing is wrong. Usually a member with no data form being left out | Nothing to stand down, it never stops anything |

An Error is rarer than you might expect, and it is about one thing, not your whole build. A tsconfig that will not load stops everything, but every other Error just leaves that one piece unbuilt while the rest of the build carries on. That is why you cannot stand one down: the call it belongs to throws either way, so not stopping buys you nothing.

Here is what each lane does with the two that fail.

| Where you are | An Error | A RuntimeError |
| --- | --- | --- |
| Your bundler (Vite, Rollup, webpack, and the rest) | Every finding is reported, then the build fails and produces no bundle. This applies when your dev server starts and when vitest boots your project, not just to production builds | Every finding is reported, then the build fails. You can stand a single code down |
| Your dev server, already running | The finding is reported and the server stays up, because you are mid edit. The build fails on the next full run | Same |
| The `mion` command line | It exits with a failure code, having written nothing for that piece | It writes its output and exits with a failure code, the way `tsc` does |

## Code That Builds And Is Still Broken

RuntimeError is the level worth understanding, because it describes something you would not expect: a build that succeeded and still handed you something that does not work.

It comes in two shapes. The loud one is a type with no data form at all, like a bare `symbol`. There is nothing to validate, so the generated function is written as one that throws:

```
suites.ts(4,29): error VL002: Type `symbol` can never be validated — the generated function will always fail.
```

The printed line says `error` for an Error and a RuntimeError alike. That is on purpose: it is the format your editor's problem matcher reads, and it only knows two words. Look up the code to see which of the two you have.

The quiet one is worse, because nothing looks wrong. A type that could not be read becomes `any`, and a function generated from `any` accepts every value. Your validator runs, passes everything, and tells you nothing. That happens when an import does not resolve (`MKR007`), when a type name does not resolve (`MKR013`), when the Temporal library is missing from your `lib` (`TMP001`), or when your `lib` names no base edition at all (`CFG002`).

A deliberate `any` is always fine. If you wrote `any`, or an alias like `type Loose = any`, then a function that accepts everything is exactly what you asked for, and you get a plain warning. Only a type that became `any` without you asking is a RuntimeError.

::tip
`CFG002` is about your tsconfig rather than your types. It fires when your `lib` setting declares no base ECMAScript edition, which happens with `lib: []`, with `noLib`, or with a by-feature entry such as `["esnext.disposable"]` written on its own. Without a base edition TypeScript never declares `Array`, so `number[]` checks as an empty object. A by-feature entry adds to an edition, it cannot replace one, so the fix is to name one: `["es2022", "esnext.disposable"]`.
::

## When You Cannot Fix It Today

Sometimes a broken type is the point of the code, or the fix is scheduled for later, and you still need to ship. There are two ways to stand a RuntimeError down, and neither turns checking off. An Error is out of reach for both.

### A Comment On The Call Site

Put `@mion-expect-error` on the line above, naming the code you expect. That finding is removed:

```ts
// These suites check what happens at runtime when a validator can never work,
// so the bad type is the point of the file, not a mistake.
// @mion-expect-error VL002
export const alwaysThrows = createValidateFn<symbol>();
```

It works like TypeScript's `@ts-expect-error`, including the part people forget: if the finding goes away, the comment itself is reported, so it can never outlive the problem it was added for.

```
suites.ts(3,4): warning EXP001: Unused `@mion-expect-error VL002`: nothing was reported on the line below it.
```

A stale comment is a warning here, not an error the way TypeScript has it. Your code is correct, only the comment is wrong, and that is not a reason to stop shipping.

You can name several codes on one comment, separated by spaces or commas.

::tip
Name the code. Leaving it off covers anything reported on that line, but only your editor can then tell you the comment has gone stale, because the build does not run every check the editor does. A named code is checked by both.
::

### A Setting, For Findings You Cannot Annotate

Some findings have no line of yours to comment on. They come from inside a package you do not own, or from your project config rather than your source. For those, name the code in `downgradeErrors` and it reports as a warning instead:

```ts
mionVitePlugin({
  runTypes: {
    downgradeErrors: ['CTA003'], // raised inside a dependency, so we cannot annotate it
  },
});
```

The finding still prints on every build, marked so you can tell it apart from a warning that was always a warning:

```
node_modules/some-lib/adapter.js(41,9): warning CTA003: ... (downgraded)
```

Every other finding still fails the build. That is what makes this different from switching checking off: naming one code buys nothing for the mistakes you have not made yet.

::tip
Use `'*'` to downgrade every code at once. It is meant for adopting mion on an existing project, where you cannot list codes you have not met yet. Once you know them, name them.
::

Errors are the one thing neither lever touches, `'*'` included. There is nothing to stand down: the build produced no code for that piece, so the call would throw whether or not you silenced the message. Naming one in `downgradeErrors` is refused outright, with the reason, rather than quietly protecting nothing.

See [Configuration](/runtypes/introduction/configuration#option-reference).

Each diagnostic is reported once per call site, and it covers the whole type you asked about, not just its outermost layer. If a class sits three levels down inside the type you encode, you still hear about it, reported at the line that pulled it in. A type is often compiled into several functions at once (an encoder and a decoder, say), and a problem the compiler notices while building one of them is the same problem it notices while building the others, so you see it a single time rather than once per generated function.
