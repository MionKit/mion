RunTypes flags type problems while your project builds, each as a short code like `VL010` or `PJ001`. The letters name the feature (`VL` is `createValidateFn`, `PJ` is `prepareForJson`), and the number marks the position: `001` to `009` are root errors, `010` and up are member-level warnings.

Severity decides what happens next. A Warning tells you something worth knowing (usually an expected drop) and never stops anything. What an Error does depends on who is running.

| Where | What an Error does |
| --- | --- |
| Your bundler (Vite, Rollup, webpack, and the rest) | Every finding is reported, then the build fails and produces no bundle. This applies when your dev server starts and when vitest boots your project, not just to production builds. |
| Your dev server, already running | The finding is reported and the server stays up, because you are mid edit. The build fails on the next full run. |
| The `mion` command line | It writes its output and exits with a failure code, the way `tsc` does. |

## When You Cannot Fix It Today

Sometimes an error is the point of the code, or the fix is scheduled for later, and you still need to ship. There are two ways to stand one down, and neither turns checking off.

### A Comment On The Call Site

Put `@mion-expect-error` on the line above, naming the code you expect. That finding is removed:

```ts
// These suites check what happens at runtime when a validator can never work,
// so the bad type is the point of the file, not a mistake.
// @mion-expect-error VL002
export const alwaysThrows = createValidateFn<symbol>();
```

It works like TypeScript's `@ts-expect-error`, including the part people forget: if the finding goes away, the comment itself becomes an error, so it can never outlive the problem it was added for.

```
suites.ts(3,4): error EXP001: Unused `@mion-expect-error VL002`: nothing was reported on the line below it.
```

You can name several codes on one comment, separated by spaces or commas.

::tip
Name the code. Leaving it off covers anything reported on that line, but only your editor can then tell you the comment has gone stale, because the build does not run every check the editor does. A named code is checked by both.
::

### A Setting, For Findings You Cannot Annotate

Some findings have no line of yours to comment on. They come from inside a package you do not own, or from your project config rather than your source. For those, name the code in `downgradeErrors` and it reports as a warning instead:

```ts
mionVitePlugin({
  runTypes: {
    downgradeErrors: ['CTA003'], // raised inside a dependency, so we cannot annotate it
  },
});
```

The finding still prints on every build, marked so you can tell it apart from a warning that was always a warning:

```
node_modules/some-lib/adapter.js(41,9): warning CTA003: ... (downgraded)
```

Every other error still fails the build. That is what makes this different from switching checking off: naming one code buys nothing for the mistakes you have not made yet.

::tip
Use `'*'` to downgrade every code at once. It is meant for adopting mion on an existing project, where you cannot list codes you have not met yet. Once you know them, name them.
::

Pure function errors are the one thing neither lever touches, `'*'` included. Those mean the build could not extract a function it was about to generate a file from, so carrying on would ship output with pieces missing.

See [Configuration](/runtypes/introduction/configuration#option-reference).

Each diagnostic is reported once per call site, and it covers the whole type you asked about, not just its outermost layer. If a class sits three levels down inside the type you encode, you still hear about it, reported at the line that pulled it in. A type is often compiled into several functions at once (an encoder and a decoder, say), and a problem the compiler notices while building one of them is the same problem it notices while building the others, so you see it a single time rather than once per generated function.

One error is worth calling out: `MKR007`. When an import in a file fails to resolve during the type scan, a type used at a marker call can quietly check as `any`, and functions generated from `any` would accept everything with no runtime signal that something went wrong. Instead, the build stops and names the file and the unresolved import, so you can fix the path (often a missing file extension) and rebuild. Its sibling `MKR013` covers the same trap when the failing piece is a type name rather than an import: a typo, a dependency without types, or an ambient declaration file the tsconfig include set does not cover. A deliberate `any` (written as `any`, or through an alias like `type Loose = any`) is always allowed.

`CFG002` is about your tsconfig rather than your types. It fires when your `lib` setting declares no base ECMAScript edition, which happens with `lib: []`, with `noLib`, or with a by-feature entry such as `["esnext.disposable"]` written on its own. Without a base edition TypeScript never declares `Array`, so `number[]` checks as an empty object and a generated validator would accept anything. A by-feature entry adds to an edition, it cannot replace one, so the fix is to name one: `["es2022", "esnext.disposable"]`.
