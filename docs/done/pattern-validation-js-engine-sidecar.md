# Pattern sample validation everywhere: a host JS engine driven by the Go resolver

## Problem

`mockSamples` for regex patterns are validated in three places today, and the union still leaves a hole:

1. **Module load (runtime JS)** — `registerFormatPattern` tests every sample with a real `RegExp` and throws (`packages/ts-runtypes/src/runtypes/formatPattern.ts:66-74`). Runtime-only; never sees inline `{source, flags, mockSamples}` params.
2. **Build lane (Go, RE2)** — the real validator: `validateSamples` → FMT001 and `validateSampleBounds` → FMT003 in `ts-go-runtypes/internal/cachegen/typefunctions/formats/string/pattern.go:119-179`, running wherever format emitters render — both `serve` and the tsc-like `compile` verb (`internal/compiler/batchcompile/compile.go:93,129` → `collectEntryModules`). RE2 semantics are bridged by `re2Pattern` (`pattern.go:365-381`), and `pattern.go:123` is the only `regexp.Compile` over user input in the tree.
3. **Lint lane (JS fallback)** — patterns RE2 cannot compile (lookarounds, backreferences) are recorded via `reportUncheckedPattern` (`pattern.go:355-363`) and shipped over a dedicated wire channel (`protocol.go:706-720` `UncheckedPattern`, `Response.UncheckedPatterns` `:626-630`) to `validateUncheckedPatterns` in `packages/ts-runtypes-devtools/src/eslint/lint-worker.ts:110-138`, which runs the real JS `RegExp` and reports FMT001 through the `runtypes/format` rule.

**The gap:** for a JS-only pattern, the build lane either fails closed with FMT004 or — with `allowUncheckedPatterns` — **silently skips the check** (`pattern.go:359-361`). The standalone `compile` verb has no lint lane at all, so on that path such samples are never validated by anything (pinned by `internal/compiler/resolver/format_sample_validation_test.go:212-240`). The devtools build lane itself validates nothing (zero `uncheckedPatterns`/FMT references in `unplugin.ts` / `vite.ts` / `scan-batcher.ts`).

Since a JS runtime is present on effectively every host that runs the binary (the plugin itself runs inside node; standalone users installed via npm), the Go resolver can drive one directly and validate everything itself — making `compile` fully sound and deleting the lint-lane fallback plus its wire channel.

## Design

**New package `ts-go-runtypes/internal/jsengine`** — a small engine the resolver calls to execute JS regex jobs (shipped shape):

```go
type TestResult struct{ CompileError string; Offenders []string }
type Engine interface {
    // Compiles source+flags on the real JS engine and tests every sample
    // (empty samples = pure compile check). error = the ENGINE could not
    // run; the pattern was not checked.
    TestPattern(source, flags string, samples []string) (TestResult, error)
}
```

- **Native impl (`//go:build !js`, `sidecar.go`)** — materializes the embedded sidecar to a temp file (content-hash-named, reused across runs) and lazily spawns ONE session-long child, mutex-serialized newline-JSON round-trips (`{v:1, jobs:[{id, op:'validate', source, flags, samples}]}` per line — the batch wire shape stays so the autogeneration todo adds `generate` without reshaping), 5s deadline per round-trip; any spawn/timeout/protocol failure is sticky (kills the child, later calls fail fast). Verdict memo lives inside the engine. There was no production `os/exec` in the tree before this — deliberately minimal machinery.
- **WASM impl (`//go:build js && wasm`)** — no subprocess: the host IS a JS engine. Validate via `js.Global().Get("RegExp").New(source, flags)` + `.Call("test", sample)` directly (same synchronous host-call shape as `cmd/ts-runtypes-wasm/main.go:100-102`). No sidecar, no randexp needed for validation.
- **Injection** — `resolver.Options` gains `JSEngine jsengine.Engine`; `cmd/ts-runtypes/main.go` constructs the native impl, `cmd/ts-runtypes-wasm/main.go` the wasm impl, tests inject fakes.

**The sidecar is a private workspace package whose bundle is committed and go:embed-ded** (user-confirmed direction). It is NOT template text like the existing JS-in-Go (`internal/cachegen/builtinpurefns/table.generated.go`); it is an executable program that must `import` npm packages. Resolution:

- **Authoring home: `packages/ts-runtypes-go-be-sidecar/` (`@ts-runtypes/go-be-sidecar`, `"private": true`)** — the repo's FIRST private workspace package (`packages/examples` turned out not to be a workspace member at all: no package.json, it is a bare typechecked folder). Kept out of `PUBLISHED_PACKAGE_DIRS` (`repo-contracts.test.ts:42-45`); registered as a root vitest project. TS source with its own vitest unit tests, and it falls inside `pnpm run format`'s `packages/**/*.ts` scope and the lint sweep for free (a loose `.mjs` under `ts-go-runtypes/` would sit outside all three). `randexp` (needed by the autogeneration follow-up) will be declared here as an exact-pinned per-package `dependency` when that todo lands; root-level stays devDeps-only per workspace policy, and `minimumReleaseAge` applies on add. Adding the workspace member required one `pnpm install --no-frozen-lockfile`.
- **Its `build` bundles `src/` into ONE self-contained, unminified ESM file** (vite 8 library mode — already the root devDependency; unminified keeps diffs reviewable and the drift gate meaningful). The package's own `dist/` stays gitignored like every package's — note the devtools dist is NOT committed either (`.gitignore:14` covers all `dist/`; the bootstrap builds it), so the committed-artifact convention being followed here is the drift-gated generated mirrors, not a committed dist.
- **The bundle IS committed to git**, at `ts-go-runtypes/internal/jsengine/sidecar.bundle.mjs`, where plain `//go:embed` picks it up — no generated Go string, readable JS diffs, and `go -C ts-go-runtypes test ./internal/...` keeps working with zero node tooling on a fresh checkout. A `sidecar` entry in the `CODEGEN` table (`scripts/rt.mjs:307` usage line, drift gate `:124`) runs the package build and copies the output there; CI's existing `pnpm rtx core codegen all --check` catches drift — the same committed-mirror discipline as the Go→TS `*.generated.*` files, pointed the other way.
- **Rejected:** loose `.js` files in the `@ts-runtypes/binary-*` packages (they ship exactly `lib/<exe>` + manifest + LICENSE + README, `scripts/release/build-binaries.mjs:108-136`; loose files break the copied-binary and `RT_BIN` cases and churn build-binaries/repo-contracts). Also rejected: inverting the relationship so node pulls files from Go — under the standalone `compile` verb no node process exists yet, so Go must be the spawner; embedding + temp-file materialization already IS "Go carries the files and hands them to node".

**Runtime discovery** (precedence): `--js-runtime <path>` flag > `RT_JS_RUNTIME` env > PATH probe for `node`, then `bun`. The devtools plugin always passes `--js-runtime` = `options.jsRuntime ?? process.execPath` at spawn (the plugin runs inside node, so the serve lane always has a runtime for free). Per the wire taxonomy in `docs/done/protocol-startup-config-audit.md` ("the wire carries events; the session carries config"), this is a spawn flag into `resolver.Options` — never a `protocol.Request` field. It is host-specific config (like `binary`/`cwd`, `unplugin.ts:16-23`), so **no tsconfig key**.

**Validation authority: the sidecar validates every pattern's samples — RE2 is removed from sample validation entirely.** The samples' one job is to satisfy the JS runtime validator (`emitPatternTest`'s hoisted `new RegExp`, `registerFormatPattern`'s load-time check), and RE2 only approximates it even on the shared subset: `.` excludes `\u2028`/`\u2029` in JS but not RE2; case folding under `i` diverges without `u` (Kelvin sign `K`); no-`u` JS matches UTF-16 code units where RE2 matches runes (`^.$` vs `'😀'`); JS `\s` includes `\uFEFF` while RE2's does not — today each of these is a silent false accept or a false FMT001. A fallback that validates differently depending on what happens to be installed would keep exactly that nondeterminism, so there is no fallback: `re2Pattern` (`pattern.go:365-381`) and the `regexp.Compile` at `pattern.go:123` (the only RE2 compile over user input in the Go tree; tool-owned regexes elsewhere are untouched) are deleted. Verdicts are memoized per session on `(source, flags, samples)` (validation is pure), so watch-mode rebuilds spawn nothing once warm.

**Failure semantics: a JS runtime is a hard requirement exactly when patterns exist.** If the engine cannot run (no runtime found, spawn failure, timeout, malformed output), every pattern-bearing site gets an Error-severity FMT004 reworded to "pattern validation requires a JS runtime (node or bun) — install one or pass --js-runtime", failing the build through the normal `failOnError` path; a project with zero patterns never needs the runtime. `allowUncheckedPatterns` loses its reason to exist and is REMOVED end-to-end: tsconfig key (`config.go:78-82`), `--allow-unchecked-patterns` flag (`main.go:155-156`, merge `buildconfig.go:75,110-111`, `resolver.Options` at `main.go:336`), `EmitContext.AllowUncheckedPatterns()` (`registry.go:61-71` + walker/emitter impls), the devtools option + spawn arg (`unplugin.ts:377` → `resolver-client.ts:559`), its `plugin-option-keys.ts` row + regenerated `tsconfig-plugin-keys.generated.ts`, and the `4.configuration.md:150` docs row (stale tsconfigs hit the existing unknown-key warning, `config.go:360-388`). Diagnostics severity semantics are unchanged (`internal/diagnostics/catalog.go:19-32`; Error halts via `surfaceDiagnostics` + `failOnError`, `unplugin.ts:427,455,647-648`).

## Plan

1. **Sidecar package + codegen.** New private workspace package implementing the protocol (newline-framed JSON: `{v:1, jobs:[{id, op:'validate', source, flags, samples}]}` per request line → `{v:1, results:[{id, offenders?, compileError?, error?}]}` per response line; `v` + op strings let the autogeneration todo add `generate` without reshaping), with its own vitest unit tests; `build` (vite lib mode) → single-file unminified bundle; `CODEGEN.sidecar` lane (via `scripts/core/gen-sidecar-js.mjs`) copies it to the committed `internal/jsengine/sidecar.bundle.mjs` for `//go:embed`. Both sides escape U+2028/U+2029 in wire lines (Go's encoding/json always does on requests; the sidecar mirrors it on responses) so the newline framing can never be split by content — a hazard the fuzz suite below actually caught.
2. **`internal/jsengine`** — interface, native impl (`sidecar.go`: discovery, temp-file materialization, ONE session-long child, mutex-serialized round-trips, engine-internal memo, sticky failure), wasm impl (`wasm.go`), nil-engine path for tests. Unit tests run against the real node on the host (the repo's test environment always has one).
3. **Wire into validation — JS engine only.** `validateSamples` (pattern.go) calls `ctx.JSEngine().TestPattern(...)` inline during emit — sites and per-walk dedup keep working exactly as before, and the engine's persistent child + memo give the one-spawn-per-session, spawn-free-rebuild properties the original queue/drain sketch aimed at. It also drops the old zero-sample early return, so every pattern gets a compile check; a JS-uncompilable source is FMT002 (invalid params: the emitted validator's `new RegExp` would throw at factory load — previously a silent runtime crash). `re2Pattern`, the user-input `regexp.Compile`, and `reportUncheckedPattern` are deleted; FMT004 (const renamed `CodeFMTMissingJsRuntime`) is the missing-runtime Error above, args [source, reason]. FMT003 bounds checking is pure Go (UTF-16 counting, no regex) and unchanged. `compile` gains full validation automatically (same render path — format emitters must be registered, i.e. the `formats/all` blank import); `enrich` stays off the validation path (no format emitters).
4. **Delete the JS fallback + wire channel.** `lint-worker.ts:110-138` + merge at `:157`; `protocol.go:706-720`, `:626-630`, MarshalJSON `:951-952`; `protocol.ts:549-554`, `:489-492`; `resolver-client.ts:275-277,404`; `dispatch.go:300-318` (`expandUncheckedPatterns`) + sink setup `:823-833`/`:262-286`/`:873`; `walker.go:199-212,421-432`; `typefunctions/module.go:74-88,513-514,677-684`; `emitter.go:518-531`; `registry.go:61-71` (both `RecordUncheckedPattern` and `AllowUncheckedPatterns` come off `EmitContext`); `render.go:39-42`; `resolver.go:154-160`. The lint lane still surfaces FMT001 — it now arrives as a regular diagnostic on the scan (routing via `diagnosticRouting.ts:276` unchanged).
5. **Flags/config/env.** `--js-runtime` StringVar on `sharedFlags` (`main.go:139` `registerSharedFlags`, used by serve `:400` + compile `:580`); `resolver.Options.JSEngine` construction in both mains; devtools: `PluginOptions.jsRuntime?` (`unplugin.ts`) + `plugin-option-keys.ts` row + `ResolverClientOptions` + `buildResolverArgs` push (`resolver-client.ts:556` idiom) — note the plugin-option-parity test treats host-only options specially (like `binary`); `RT_JS_RUNTIME` row in `scripts/lib/env.mjs` REGISTRY (scope `dev`) + `.env.sample` mirror. Update the FMT004 headline in `internal/diagnostics/messages.go` (missing-runtime wording; consider renaming the Go const to `CodeFMTMissingJsRuntime`, code string stays `FMT004`) and regenerate (`pnpm rtx core codegen diag`). Remove the whole `allowUncheckedPatterns` surface (full list in Design).

- **`internal/jsengine` unit tests (real node):** round trip, lookbehind, invalid syntax = CompileError, empty-samples compile check, JS-authority divergences (`^.$` rejects an astral emoji; `\s` accepts U+FEFF), memo (2 round-trips for 4 calls), discovery precedence (flag > env > PATH), sticky spawn failure, malformed output, shortened-deadline timeout.

## Fuzzing

With RE2 gone there is no second implementation to keep in parity, so no fallback-fidelity suite. What shipped is robustness: `pnpm rtx core fuzz sidecar` (suite `sidecar` in the FUZZ table; the test itself lives at `packages/ts-runtypes-go-be-sidecar/test/patternSidecarFuzz.test.ts` and also runs in the normal suite — one spawn, fast) throws seeded random garbage at the COMMITTED bundle under real node — arbitrary pattern sources and flags (including invalid regex syntax), pathological samples (astral emoji, BOM, C1 controls, NEL, and the JS line separators U+2028/U+2029), oversized batches — and asserts every request line gets exactly one well-formed response with exactly one verdict shape per job. On its very first run it caught a real hazard: a raw U+2028 inside a sample splits any newline-framed JS reader mid-line. Fix shipped in the sidecar itself (responses escape U+2028/U+2029, mirroring Go's request-side escaping); the Go client was never affected (`ReadBytes('\n')` is byte-based). The generate-side round-trip oracle lives in the autogeneration todo.
