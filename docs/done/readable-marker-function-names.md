# Readable Function Names in `InjectTypeFnArgs` Markers

## Problem

A marker names the functions it wants with short codes:

```ts
ids?: InjectTypeFnArgs<T, 'prs', 'verr'>
```

Nobody can read that. The docs already pay for it, they stop and translate:

> `pjs` and `pj` are the clone and mutate prepares, `rjs` and `rj` the matching
> restores (`rjs` drops undeclared keys, `rj` keeps them), `cj` and `cjr` are the
> compact encode and decode, and `sj` is the single-pass stringify.

**The mapping layer already exists.** Every `Operation` in
`ts-go-runtypes/internal/cachegen/operations/operations.go` carries three
separate strings:

```go
{Name: "validationErrors", FamilyTag: "verr", Public: true, FnKey: "verr", ...}
//     ^ hashed into fnHash  ^ written into generated code   ^ the marker token
```

`FnKey` is read by `operations.ByFnKey`, which turns a marker token into an
`Operation`, and by nothing else downstream. Cache keys come from `Name` (via
`FnHashFor`); generated code uses `FamilyTag`. The layer is there and is
currently set to an identity map for 22 of the 25 rows. Three rows already break
the identity (`jsonSchema`/`jsc`, `jsonEncoder` and `jsonDecoder` with no tag at
all), so "long token, short tag" is already a supported shape.

**Renaming the tokens costs zero generated bytes.** Verified end to end: entry
tuple slot 0 is the short `familyTag`, entry keys are `<fnHash>_<typeId>`, and no
emitter ever quotes a `FnKey` into JavaScript.

**Four operation names are wrong, and users already see them.** `Name` is meant
to be the honest description, but `prepareForJsonSafe` is the *clone* prepare and
`restoreFromJsonSafe` is the *strip* restore. That name is printed at users:

```go
// internal/diagnostics/messages.go:428
Headline: "Property `{0}` is a function: `prepareForJsonSafe` does not handle function values, so this property is silently not encoded.",
```

Five diagnostics say it. So the names get fixed in the same pass (step 1b), which
also keeps `Name` and marker token spelling the same everywhere.

Two things do carry the token and need handling:

- `RunType.Overrides` is keyed by `FnKey`, and `typeid.OverrideStructuralKey`
  writes that key straight into the structural type id. Step 2 cuts that.
- `<genDir>/api/manifest.json` lists `families: ["val","verr",…]` per method, and
  `mion api-check` string-compares client against server. Both sides regenerate,
  so this stays consistent, but it is a wire format and belongs in the plan.

**A wrong name is silent today.** `scan.go:1153`:

```go
op, known := operations.ByFnKey(fnKey)
if !known {
    return "", nil        // no error, no warning, no function generated
}
```

Proof it bites: `packages/run-types/test/features/injectTypeFnArgs-arity.test.ts`
and `packages/devtools/test/marker-diagnostics.test.ts` both use `'suk'` and
`'uku'` as filler tokens. Neither is a real key. The build accepts them and emits
handles for them.

## Plan

### 1. Give `FnKey` a readable value

`ts-go-runtypes/internal/cachegen/operations/operations.go` — change only the
`FnKey` field on each row. `Name` and `FamilyTag` stay exactly as they are, so
every fnHash, every cache key and every generated byte is unchanged.

| today | new marker token |
| --- | --- |
| `val` | `validate` |
| `verr` | `validationErrors` |
| `vst` | `validateStrict` |
| `vest` | `validationErrorsStrict` |
| `prs` | `parse` |
| `prss` | `parseStrip` |
| `prsf` | `parseFail` |
| `huk` | `hasUnknownKeys` |
| `uke` | `unknownKeyErrors` |
| `ces` | `cloneExactShape` |
| `fmt` | `formatTransform` |
| `tb` | `toBinary` |
| `fb` | `fromBinary` |
| `csr` | `classSerializerReg` |
| `pj` | `prepareForJsonMutate` |
| `pjs` | `prepareForJsonClone` |
| `rj` | `restoreFromJson` |
| `rjs` | `restoreFromJsonStrip` |
| `sj` | `stringifyJson` |

| `cj` | `compactForJson` |
| `cjr` | `compactFromJson` |
| `jsonEncoder` / `jsonDecoder` / `jsonSchema` | unchanged |

`FnKey` stays a separate field even where it now equals `Name`. It costs nothing
and it keeps the option of improving the public vocabulary later without touching
a hash.

While here: `scan.go:1170` and `:1187` reassign `fnKey = op.FnKey` after the
`checkUnknowns` and parse-`strategy` operation swaps, purely because
`operations.DemandFor` takes a key string. Add `DemandForOp(op, …)` and drop both
reassignments, so `FnKey` is read in exactly one place.

### 1b. Fix the four wrong operation names

Rename `Operation.Name` for the four rows whose name does not describe what they
do, so `Name` and token agree:

| old `Name` | new `Name` |
| --- | --- |
| `prepareForJson` | `prepareForJsonMutate` |
| `prepareForJsonSafe` | `prepareForJsonClone` |
| `restoreFromJsonSafe` | `restoreFromJsonStrip` |
| `unknownKeysToUndefinedWire` | `stripUnknownKeysWire` |

`Name` is the fnHash input, so **these four families get new fnHashes.** Nothing
else moves: the other 21 families keep their hashes, every `FamilyTag` is
untouched (`pj`, `pjs`, `rjs`, `ukuw` stay), and the generated code shape is
unchanged. The on-disk cache entries for those four invalidate, which is what a
cache is for, and consumers read hashes through `getFnHash`, so none re-pin.

**Do this first and run `go test ./internal/cachegen/operations/...` immediately.**
`mustBeCollisionFree` runs at package init over every variant, so a name that
collides at `FnHashLen = 4` panics on the spot. The documented remedy is bumping
`FnHashLen` to 5, which would churn every cache key in the repo, so find out
before building anything on top.

### 5. Teach mion that a family tag is no longer an fn key

The one genuine semantic break. `packages/core/src/runtypes/mionAdapter.ts:53`:

```ts
function byFamilyTag(injected: unknown[]): Partial<Record<FnHashKey, unknown>> {
  ...
  const tag = tuple[0];        // slot 0 is the SHORT family tag, e.g. 'pjs'
  if (typeof tag === 'string') out[tag] = tuple;
```

It keys by the runtime tag and types the result as `FnHashKey`. Those strings are
equal today; after step 1 they are not, and the lie compiles.

Fix: emit a `FAMILY_TAG_TO_FN_KEY` map from the same Go registry into
`fnHashes.generated.ts` (`cmd/gen-fn-hashes`), and translate inside `byFamilyTag`.

## What shipped, against the plan above

The plan held. Five things landed differently and are recorded here rather than
in the steps, so the steps still read as the reasoning behind them.

- **The new code is `MKR015`, not `MKR014`.** `MKR014` was already
  `CodeTypeIdCollision`.
- **`apigen`'s silent `continue` got a test, not a diagnostic.** The fn keys
  there are constants in our own Go source, not something a user writes, so a
  user-facing diagnostic pointing at their file would be wrong.
  `TestApiGen_EveryHardcodedFamilyResolves` asserts every key those lists can
  produce resolves to a public operation.
- **`byFamilyTag` became `byFnKey`.** It now translates the tag through the
  generated `FAMILY_TAG_TO_FN_KEY`, which is exported from `@mionjs/run-types`
  beside `getFnHash`, so mion speaks one vocabulary from the projection on.
- **Renaming the four operation names pulled more with it than listed**: the
  `constants.CacheModules` keys, three Go emitter types and their files
  (`json_prepare_safe.go` and friends), and `resolver/dispatch.go`'s family keys.
  All mechanical, all compiler-checked.
- **The generated-code audit checks emitted NAMES, not bare substrings.**
  Several readable names (`parse`, `validate`) are ordinary JavaScript that
  legitimately appears in a body, so the test looks for the two shapes a family
  name is actually emitted in: the `<family>_<hash>` identifier and a quoted
  family string.

Two fixtures were using fn keys that never existed (`'suk'`, `'uku'`, as filler
in arity tests). `MKR015` turned them into build errors, which is the clearest
evidence the old silence was a real gap; they are real families now.

## Tests

- **Go, registry invariants:** every row has a non-empty unique `FnKey`, and no
  `FnKey` equals any `FamilyTag`. That second one is the guard that stops the two
  vocabularies quietly merging back together.
- **Go, hash stability:** the pinned fnHash values in `operations/fnhash_test.go`
  and `packages/run-types/test/features/getFnHash.test.ts` must pass unchanged
  for all 21 families whose `Name` did not change. Exactly four move, and their
  new values get re-pinned. Anything else moving is a bug in the change.
- **Go, collision guard:** `mustBeCollisionFree` still passes at
  `FnHashLen = 4`. It runs at package init, so any Go test proves it.
- **Go, `MKR015`:** a call site naming a stale `'verr'` errors, and the
  did-you-mean names `'validationErrors'`.
- **Go, overrides:** an overridden type's id does not change when only `FnKey`
  changes, which is step 2's whole point.
- **Marker coverage rule:** both `getRunTypeId` call shapes as paired tests, per
  `ts-go-runtypes/CLAUDE.md`.
- **JS, generated-code audit:** extend
  `packages/run-types/test/features/generatedCodeAudit.test.ts` to assert no
  readable token ever appears in an emitted module. This pins the "keep generated
  code small" half of the request.
- **JS, mion adapter:** `packages/core/src/runtypes/mionAdapter.spec.ts` covers
  the tag to key translation, with a payload whose tags are short and whose keys
  are long.

## Out of scope

- Renaming `FamilyTag`. Every tag stays exactly as short as it is today, and the
  generated-code audit test is there to keep it that way.
- Renaming the other 21 operation names. Only the four that misdescribe their own
  behaviour change.
- Any change to generated code shape or the entry-tuple wire.
- A TypeScript union constraint on the marker's `F*` parameters. Declined: the
  marker stays open to any string and the new build error is the safety net.
- Back-compat aliases for the short tokens. Hard break, pre-1.0.
