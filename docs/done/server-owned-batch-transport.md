# The server compiler owns the batch transport, in every lane

## Problem

A batch is written in client code, but the server must know its id, its routes and its inline
`inputFrom` mappers. Before this change the CLIENT build produced that knowledge and pushed it into
the SERVER project, and only the bundler plugins did it. Every defect below followed from that.

- **Absolute imports into another project.** The client build wrote
  `<serverRoot>/.mion/rpc/batches.generated.js` with
  `import * as __mionMapper0 from "/Users/.../client/src/.mion/types/pf/rt/<hash>.js"` and
  `export const clientRoot = "/Users/..."`. The file was only valid on the machine that wrote it.
- **The gen dir was guessed.** The harvest assumed `<viteRoot>/.mion` while the resolver infers
  `<srcDir>/.mion` and echoes the real path as `outDir`. Reproduced on `packages/examples`: the
  module pointed at `packages/examples/.mion/types/pf/rt/<hash>.js` while the file lived under
  `packages/examples/src/.mion/types/`, and the server build failed with `[UNRESOLVED_IMPORT]`.
- **The server build depended on the client tree.** Nothing was copied; rollup inlined the mapper
  by following the absolute path, so the server only built while the client's gitignored `.mion`
  existed on the same disk.
- **The server root was guessed too**, from `server.viteConfig`, else the package above
  `server.startScript`, else the client root.
- **Windows.** The drive letter in `C:/...` matched the common `external: [/^[^./]/]`.
- **Only the bundler lanes got it.** `mion compile` emitted no batch module, and the one line that
  makes a server load the table was appended by a text regex in the vite plugin. The compile lane
  also transformed only files with marker sites, so a file whose only rewrite was a batch id was
  emitted untouched.
- **A client-only build in a shared root failed** on the vite plugin's "exists but no module was
  found to import it from" guard.

## What shipped

The server's resolver session owns the whole transport, so vite, Next and `mion compile` run the
same code.

### Generation (`ts-go-runtypes/internal/compiler/resolver/rpcgen.go`)

- `Options.ClientTsconfig` (flag `--client-tsconfig`, tsconfig plugin key `clientTsconfig`, plugin
  option `clientTsconfig`, preset option `client: {tsConfig}`). The flag resolves against the cwd,
  the tsconfig key against that tsconfig's directory. Set, the session builds the client program
  next to its own (`program.New` + `resolver.New`) and keeps it, rebuilding it when a stamped file
  (mtime + size of every source file and the tsconfig) changed. Unset, the own program is the batch
  source. A tsconfig that does not load fails generate naming the path.
- Inside `OpGenerate`, after the entry modules: collect the batch sites and the referenced inline
  mappers (`rt::` keys; a `mionjs::<name>` key is the by-name lane and needs no module) plus the
  pure fns those mappers call, render them with `purefunctions.CollectEntries` +
  `entrymodules.RenderGrouped` per entry whatever the `moduleMode`, and write
  `<outDir>/rpc/pf/<ns>/<fn>.js` beside `<outDir>/rpc/batches.generated.js`:

  ```js
  // GENERATED by mion (the batch transport). Do not edit.
  import {registerInputMapperTuple} from '@mionjs/core';
  import {replaceBatches} from '@mionjs/router';
  import {__rt_pf$2Frt$2F7WjIGwjbYODFWP} from './pf/rt/7WjIGwjbYODFWP.js';
  registerInputMapperTuple('rt::7WjIGwjbYODFWP', __rt_pf$2Frt$2F7WjIGwjbYODFWP);
  replaceBatches({"b_slDEnMOZXui9On":{"routes":["orders/getById","users/getById"],"mappings":[...]}});
  ```

  Named imports through `entrymodules.BindingName`, no `clientRoot`, no checksum (one process
  writes and reads the tree). Batches sorted by id, mappings as extracted. Write-on-change through
  `materializeModules`, stale mapper modules pruned, `rpc/` removed when there is nothing to serve.
- **Decided during implementation:** `rpc/` is generated only when the program creates a router
  (calls `createMionRouter`). A client-only program has nothing to serve the table to, so none is
  written and a stale one is removed. The transform still gives every client file its ids.
- New diagnostic **BAT007**: a batch names an inline mapper the batch source produced no pure
  function for. Defensive (the extractor keeps an impure mapper's entry and reports PFN/PFE codes
  instead), pinned by an internal renderer test rather than an end-to-end one.
- `protocol.Response` echoes `batchesModule`, `batchSourceFiles` (a separate batch source's batch
  and mapper files, for the dev watcher) and `routerInitFiles`; the router-init files also join
  `SiteFiles`, so a module whose only rewrite is the appended import still reaches the transform.

### Injection (`ts-go-runtypes/internal/compiler/routerinit/`)

- The router-init detector resolves the callee's symbol through any alias chain
  (`GetAliasedSymbol`: a renamed import, a namespace member, a barrel re-export) and requires the
  resolved signature to be declared by `@mionjs/router`, so a same-named local function never
  matches. Memoised per file like the batch cache.
- When the batch source holds a batch (`hasBatches()`, memoised; computed on demand so the compile
  lane, which transforms before it generates, decides like the bundler lane), every router-init
  module gets one point insertion at end of file: `import '<relative>/rpc/batches.generated.js';`
  in files mode, `import 'rtrpc:/batches.generated.js';` otherwise. `rtrpc:` is the sibling of
  `rtmod:`; both relativizers (`relativizeUserImports`, `RelativizeUserImports`) turn it into a path
  under `<outDir>/rpc`. Appended, never prepended, so the `go` and `edits` wire modes agree and no
  existing line moves.
- **Found and fixed on the way:** `batchcompile.Run` now generates before it transforms and unions
  the generate echo's `SiteFiles` into the rewrite set, so the CLI transforms a batch-only client
  file and a router-init module with no other marker. It also refuses to write an emitted file
  outside the tsconfig `outDir` (a program reaching files outside its `rootDir`, such as a `paths`
  entry into a sibling package, had them emitted beside their sources) and lists what it skipped.

### JS side (`packages/devtools`)

- `PluginOptions.clientTsconfig`, forwarded as `--client-tsconfig`; `onGenerate(info)` fired after
  every generate with `{outDir, batchesModule, batchSourceFiles, routerInitFiles}`; under vite the
  core plugin registers a separate batch source's files on the watcher and regenerates on a change
  (only files already holding a batch or a mapper are watched: a brand-new client file with the
  first batch needs a server restart).
- `MionPresetOptions = {runTypes, client?: {tsConfig}}`; `toRunTypesOptions(rt, client)` maps the
  pointer (as written, the resolver resolves it against its cwd). `server` is the vite preset's
  dev/test run-mode block only. Deleted: `createBatchHarvest`, `writeBatchesModule`,
  `renderBatchesModule`, `readBatchesModule`, `batchChecksum`, `batchesModulePath`,
  `resolveServerRoot`, `resolveGenDir`, `BATCHES_DIR`, `BATCHES_FILE`, the batch interfaces,
  `MionServerPointer`, `batchesImportPlugin` and its regexes, the `harvested` gate, the
  `mion-batches-root` plugin, the report wiring.
- `createBatchTransportSignals` folds the echo into what vite needs: `generated` (awaited by the
  child-process orchestrator), `batchesModuleOf` (the middleware's `add` listener), and the
  router-init invalidation when the module appears or vanishes.
- `withMion` rejects `server` with a hint and accepts `client`.
- `vitest-clean-gendir` sweeps `rpc/` too (it is regenerated on every generate).

### Repo wiring

`packages/test-server/vite.config.ts` names `../client/tsconfig.json`; the examples
(`vite-client.config.ts`, `vite-server.config.ts`, `vite-middleware.config.ts`) follow, the Next
batch example is deleted; `packages/test-server/README.md` says `build:lib` builds standalone; the
pre-publish e2e consumer gains a `compile` lane (`mion compile --tsconfig tsconfig.compile.json
--gen-dir .mion-cli`, then `compile-output.spec.ts` boots the emitted server under plain node and
runs the emitted client flow), wired into `scripts/release/e2e.mjs`.

`test/vitest-clean-gendir.test.ts`, `test/plugin-option-parity.test.ts`. `batch-checksum.test.ts`
is gone with the checksum.

End to end, in the container consumer lane only (`pnpm miondevx release e2e`, or the
`pre-publish-e2e` PR label), against the PUBLISHED packages and built before running: the vite
production build (`build-output.spec.ts`, table and mappers inlined) and the `compile` lane, where
`mion compile` builds the server with `--client-tsconfig client-app/tsconfig.json` (a separate
client project inside the consumer) and then that client, and `compile-output.spec.ts` checks the
table came from the client project alone, boots the emitted server under plain node and runs the
emitted client flow against it. Deliberately NOT in `pnpm test`: a first attempt as a workspace
vitest project built the framework dists inside the run, and a package build prunes the gen dir a
sibling test project is using.

## Out of scope

- Any change to how batch ids or mapper keys are hashed.
- Restricting the batch source to the built entry rather than the whole program.
- Watching a client file that holds no batch yet, or a watch mode for `mion compile`.
