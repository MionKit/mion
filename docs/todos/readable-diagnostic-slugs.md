# A readable slug for every diagnostic

## Intent

A code like `MRT001` or `VL002` tells the reader nothing, so a comment such as
`/* @mion-expect-error MRT001 */` needs a second comment to explain it. Give every diagnostic a
human readable slug, prefixed by the functional area it belongs to, and accept it anywhere a code
is accepted. Either form turns off or lowers the same error:

```ts
// @mion-expect-error rpc-handler-throws
// @mion-expect-error MRT003   (same thing)
```

From then on the repo uses slugs everywhere: comments, tsconfig `downgradeErrors`, docs and
examples. Codes stay valid input and stay in messages and the All Diagnostics page, so a code seen
in a log can still be looked up.

## Direction

The implementer plans the details. What was checked:

- **One place defines it.** Each code registers a `Definition` in the Go catalog
  (`ts-go-runtypes/internal/diagnostics/catalog.go`, codes in `codes_*.go`, about 110 codes). Add a
  `Slug` field; `register` already panics on a missing `Level` / `Scope`, so a missing or duplicate
  slug should panic the same way. Slugs are kebab-case, say what went wrong, and never change once
  shipped.
- **The prefix names the functional area**, one a user recognises from the docs, never the code's
  letters. A starting point for the mapping (confirm it with the owner before naming ~110 slugs):

  | Prefix | Codes | Example |
  | --- | --- | --- |
  | `rpc-` | MRT (routes), BAT (batches), MET (client API) | `rpc-handler-throws` |
  | `runtypes-` | VL, VE, PJ, PJS, RJ, RUK, JCP, FMT, TMP, NE, UPN, CTA, MKR, OVR | `runtypes-symbol-not-validatable` |
  | `purefn-` | PFE, PFN | `purefn-reads-outer-variable` |
  | `enrich-` | FT, MD, GE | `enrich-blank-label` |
  | `config-` | CFG | `config-tsconfig-not-loaded` |
  | `comment-` | EXP, DWN | `comment-unused` |

  The area comes from the catalog (a `Family` plus the code prefix), so one function derives it and
  a test checks every slug starts with its area's prefix.
- **Every reader accepts both.** Directive comments (`directiveCodes` in
  `ts-go-runtypes/internal/compiler/resolver/expecterror.go`, judged in
  `internal/diagnostics/expecterror.go`), the tsconfig and plugin `downgradeErrors` (Go
  `internal/diagnostics/downgrade.go`, its JS twin `packages/devtools/src/core/downgradeErrors.ts`).
  Normalize a slug to its code once, where the input is parsed, so matching, "unused comment"
  (EXP001 / DWN001) and "unknown code" (EXP003 / DWN003) all work unchanged. An unknown slug is
  reported like an unknown code.
- **The JS side gets slugs from the generated catalog**
  (`packages/devtools/src/core/go-generated/diagnosticCatalog.generated.ts`, written by
  `cmd/gen-diag-catalog`), never a hand-kept list.
- **Messages.** Decide whether the editor and build messages show the slug next to the code
  (for example `[MRT003 rpc-handler-throws]`). Showing it teaches the slug where people copy from.
- **Docs.** The All Diagnostics page (`container/website/content/02.runtypes/08.diagnostics/02.all-diagnostics.md`,
  generated by `scripts/core/gen-diagnostics-catalog.mjs`) lists the slug beside each code. The
  Error Levels page (`02.runtypes/08.diagnostics/01.error-levels.md`) and the linting pages use
  slugs in every example.
- **Move the repo over.** Every `@mion-expect-error` / `@mion-downgrade-error` comment and every
  `downgradeErrors` list in packages, examples, e2e apps and configs switches to slugs. Tests that
  pin code parsing keep testing both forms. Go directive tests follow the Marker test coverage rule
  in `ts-go-runtypes/CLAUDE.md` (both `getRunTypeId` shapes).
- **Guard it.** A Go test checks every catalog entry has a unique kebab-case slug that starts with
  its area's prefix.
  A repo check (like the ones in `packages/devtools/test/repo-contracts.test.ts`) fails when a
  directive comment or `downgradeErrors` list in the repo names a bare code.

## Docs

`02.runtypes/08.diagnostics/01.error-levels.md` (existing sections "Disabling Errors" and
"Downgrading Errors in Config": slugs in every example, one line saying a code works too),
`02.all-diagnostics.md` (a slug column), and the linting pages
(`02.runtypes/04.tooling/01.linting.md`, `01.rpc/07.devtools/01.linter.md`) where they show a
comment.

Before opening the PR, run the simplify-docs pass (the `docs-simplifier` subagent) over every page and example this change touched, review its report against the code, and commit it as its own commit.

## Done when

- Every diagnostic has a unique slug prefixed by its area, and a comment or `downgradeErrors` entry works with
  either the slug or the code, with tests for both forms in Go and JS.
- No directive comment or `downgradeErrors` list in the repo names a bare code, and a check keeps it
  that way.
- The docs show slugs in every example and list them beside the codes.
- The simplify-docs pass ran on every touched page and the simplify-comments pass on every touched
  source file, each committed on its own.
