# One API build hash, returned in a response header

## Problem

A client built with `bundleApi` carries compiled validators and serializers for the routes it calls.
It never asks the server anything, so when the server moves on (a route renamed, a param added, a
runtypes version bump) nothing notices. The client keeps calling with code compiled against an API
that no longer exists.

`mion api-check` catches this at build time, but only when both build outputs sit on the same
machine. A client already deployed against a server that changed afterwards has no check at all.

## Plan

### One hash for the whole API, computed by the build

Both builds already walk the same thing. `serverApiManifest`
(`ts-go-runtypes/internal/compiler/resolver/apigen.go:259`) writes every public method of every
`initRoutes(...)` call. On a client build, `resolveApiBundle` already holds the complete API tree
before it narrows to what the site calls:

```go
// apigen.go:357-359
		tree = peerTree
	}
	methods, missing := tree.Select(site.Ids)
```

So hash `tree` before `Select`, over the same `manifestRow()` fields `api-check` compares today
(`ManifestMethod`: type, paramsId, returnId, headersId, families, options, middleFnIds), sorted by
id. Both ends run the same Go code over the same rows, so there is no build-versus-runtime skew.
Type ids are already salted with the binary version
(`ts-go-runtypes/internal/cachegen/runtype/serialize.go:425`), so the runtypes version folds in for
free. Ids are 7 characters.

Emit no hash in two cases, where today's behaviour is the safe fallback:

- the server manifest has `Ambiguous` ids (the API declares a route twice with different types, so
  there is no single truth to hash)
- a client build has neither `api.tsConfig` nor a router import in its own program, so it walked the
  API type with its own lib and strictness settings and its ids may differ with nothing wrong

### Injection

Both ends already have a generated side-effect module carrying build constants, so a `setApiHash`
line goes into each and nothing new is plumbed:

```go
// apigen.go:181 — client, imported from every file that calls initClient
func renderApiLaneModule(mode constants.BundleApiMode) string {
	return "// GENERATED by mion (the bundleApi lane). Do not edit.\n" +
		"import {setBundleApiMode} from '" + apimeta.ClientModule + "';\n" +
		"setBundleApiMode(" + jsquote.Single(string(mode)) + ");\n"
}
```

Its server twin is `renderBatchesModule` (`rpcgen.go:283`), imported from every router-init module.

### Server, on the wire

A response header named after the existing `x-rpc-error` convention, set in the two places that
between them cover every response:

- `packages/router/src/routes/serializer.routes.ts:95`, the `alwaysRun` end middleFn, which already
  sets `content-type` and runs on normal, not-found and batch chains
- `packages/router/src/lib/dispatchError.ts:13`, `getRouterFatalErrorResponse`, which adapters call
  directly and which bypasses the chain

No adapter filters custom headers. The only filter anywhere is uws's CR/LF/NUL check
(`packages/platform-uws/src/uwsHttp.ts:265`), which a 7-character hash passes.

### Client

`setApiHash` stores the build's hash in a light module beside
`packages/client/src/lib/bundleApiMode.ts`. Every response reads the header. Three outcomes:

| Header | Build hash | Action |
| --- | --- | --- |
| absent | any | nothing, no information |
| present | absent | nothing, this client was not built with a hash |
| present | differs | stage two |

A missing header is never a mismatch. That matters because a browser client on another origin cannot
read a custom response header unless the server sends `Access-Control-Expose-Headers`, which mion has
no way to do today. Until it does, the check is a no-op cross-origin, and it must fail silent rather
than fail loud.

### Stage two, only on a mismatch

The client loads the metadata lane and makes one request to `mion@methodsMetadataById`, sending its
own per-method ids:

```ts
export interface MethodIdCheck {
  id: string;
  paramsId: string;
  returnId: string;
}
```

`mionGetRemoteMethodsDataById` (`packages/router/src/routes/client.routes.ts:42`) takes that list and
returns only the rows whose ids really differ. The server holds `paramsJitHash` and `returnJitHash`
on every executable, so the comparison is free. An id the server no longer declares falls into the
existing `errorData` path and answers `rpc-metadata-not-found`, which is the honest answer.

The client installs the returned rows, drops the stale bundled ones (`getMethod` prefers the bundled
shelf, `packages/client/src/lib/methods.ts:28`), and reuses `retryWithProperSerialization` once if
the original call failed. Under `bundleApi: 'bundled'` the fetched lane is stubbed out
(`packages/devtools/src/core/unplugin.ts:987`), so the install needs its own small module behind a
new `imports` entry, holding `addRoutesToCache`, `addSerializedJitCaches` and
`import '@mionjs/run-types/formats'`, and nothing from the metadata store.

The mismatch is reported once as an `RpcError` in the call's undeclared slot, beside
`takeBundledApiError()` at `packages/client/src/client.ts:280`.

## Tests

Go (`go -C ts-go-runtypes test ./internal/...`): a server build and a client build of the same
fixture API produce the same hash; a changed param type changes it; no hash when the manifest has
`Ambiguous` ids; no hash for a client build with neither `api.tsConfig` nor a router import.

Router: the header rides a normal response, a not-found response, a batch response and an adapter
fatal response; `mionGetRemoteMethodsDataById` with an id list returns only the differing rows, and
answers `rpc-metadata-not-found` for an id it no longer declares.

Client bundled lane (`packages/client/test/bundled/bundled.spec.ts`): a matching hash sends no extra
request and `isMetadataFromServerLoaded()` stays false; a changed hash makes exactly one extra
request, replaces the bundled rows, retries the failed call and reports the mismatch in the
undeclared slot; a missing header changes nothing. The mixed lane gets the same coverage for its
bundled ids.

Both lanes are existing vitest projects already in the `mion-rest` batch, so
`scripts/core/test-batches.mjs` needs no change. The Marker test coverage rule does not apply, no
`getRunTypeId` call shape changes.

## Fuzzing

Not a candidate. A protocol handshake with no cheap round-trip, determinism or trusted-source oracle.

## Out of scope

- **The fetched client's cache.** A client with no `bundleApi` gets no generated lane module and so
  no build hash. Storing the server's hash beside its metadata cache and purging on change would
  replace today's guess-after-a-serialization-error, and is worth doing, but it is a different
  change.
- **Making the header readable cross-origin.** Until mion can send `Access-Control-Expose-Headers`,
  the check does nothing for a browser client on another origin. The fail-silent rule above is what
  keeps that harmless.

## Done when

- A bundled client whose hash matches the server's pays nothing: no extra request, no extra body
  bytes, no storage.
- A bundled client whose hash differs recovers in one extra request, which carries its per-method ids
  so the server returns only what really changed.
- A bundled client that never meets a mismatch still ships no metadata store.
- A client with no hash, or a server that sends none, behaves exactly as it does today.
- The simplify-docs pass ran on every touched page and the simplify-comments pass on every touched
  source file, each committed on its own.
