# Should the generated cache split into a client and a server half?

## Intent

A fullstack build writes ONE gen dir (`.mion/`) for the whole program, client and server together. Each bundle
stays apart only because the files are split fine enough that a bundler pulls in just what a file imports:

- `types/rt/<hash of the source path>.js`: one runtype data module per source file with reflection sites.
- `types/<fnHash>_<typeId>.js`: one module per compiled function (default `moduleMode`).
- `types/pf/`, `rpc/`, `api/`: pure fns, the batch table and mappers, the bundled client routes and manifests.

Because of that, the mion presets refuse `moduleMode: 'allSingle'` (`toRunTypesOptions` in
`packages/devtools/src/options.ts`) and MET014 warns when a fullstack tsconfig sets it: one module per family
for the whole program would put every server type in the client bundle.

`allSingle` may be cheaper (fewer files to write, resolve and bundle, less work per module), and a client that uses
runtypes heavily might be better off with its own cache, shaped for it, than with a slice of a shared one. Nobody
has measured either. Investigate and pick the architecture.

## Direction

The implementer investigates, writes up the pros and cons, picks one, and plans the change. Options to weigh, at
least:

- **Keep one gen dir, fine-grained files** (today). Rows two files share are written in both modules: on
  private-test-server that measured 1,632 rows written against 1,336 distinct, 83 KB over 7 modules.
- **One gen dir per side** (`client/` and `server/`, each with its own `types/`), so each side could use
  `allSingle` again. Needs a rule for which side a source file belongs to (the bundle that imports it? the
  environment Vite builds it in?) and for a file both sides import.
- **Per-environment generation**: the Vite client and `ssr` environments, and the Next server and client
  compilations, each ask for their own modules.

Questions to answer with numbers, not guesses:

- Build time and generated bytes for each option on a real app (the private-test-server, the pre-publish consumer,
  `container/benchmarks/compiletime`). Is `allSingle` actually less processing?
- Client bundle size and first-load cost, for a client that uses runtypes lightly and one that uses them heavily.
- Dev-server cost: HMR invalidation, the Next broker's stamp (it hashes `types/rt/` modules), module count.
- How each option fits `mion compile`, which writes plain files, not bundles.
- Whether `api-check`, the pure-fn artifact (`mion-pure-fns/`) and `test-skip`'s module keys need to change.

Constraints: one program per build stays (client and server must keep computing the same ids), and nothing may
let a server-only type reach the client bundle; the Vite test "keeps the reflected types of each side out of the
other bundle" in `packages/devtools/test/vite/viteEnvironments.spec.ts` pins that.

## Done when

- A short write-up of the options with measured numbers lands in this spec, with the chosen architecture and why.
- If the choice changes the layout: it is built, the bundle-split test still passes, and `allSingle` is either
  allowed again where it is safe or still refused with the reason restated.
- The simplify-docs pass ran on every touched page and the simplify-comments pass on every touched source file,
  each committed on its own.
