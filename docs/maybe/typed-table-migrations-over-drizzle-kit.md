# Schema migrations written as table versions in code, SQL from drizzle-kit

## Intent

drizzle-kit migrations feel like a black box. The schema file only shows the current state, and the history
lives in generated JSON snapshots plus a journal that nobody reads. A rename is answered at a terminal prompt
and only survives as SQL, so `generate` stops in CI. Two branches that both generate the next step break the
snapshot chain. Steps apply by timestamp, so a step merged late but created early can be skipped.

The idea: the history lives in source code as typed table versions, and the migration SQL is generated by
following the source, not from saved migration files. Keep full drizzle and drizzle-kit compatibility:
our types and step list decide WHAT changed, drizzle-kit's code interface writes the SQL.

```ts
// builder form: alterTable() returns the AlterTable type, as pgTable() returns PgTable
const users = pgTable('users', {name: text({notNull: true}), age: text(), bio: text()});
const usersV2 = alterTable(users, {age: integer({notNull: true, default: [0]})}, {drop: ['bio']});

// type form: the same type, written by hand; drop, then add or override by key
type Users = PgTable<'users', {name: Text<{notNull: true}>; age: Text; bio: Text}>;
type UsersV2 = AlterTable<Users, {age: Integer<{notNull: true; default: [0]}>}, {drop: ['bio']}>;

export const history = migrations([
  step('0001_init', [Users, Posts]),
  step('0002_age_int', [UsersV2], {using: {users: {age: '"age"::integer'}}}),
]);
```

The override value is a column type (`Integer`), not a format (`Int32`): the database needs the SQL type.

## Direction

⚠️ Before implementing anything, discuss the architecture, the types (`AlterTable`, the step list) and the
builders (`alterTable()`, `migrations()`, `step()`) with the user and get their approval. The shapes below are
ideas from a first conversation, not decisions.

The implementer plans the details. What was checked:

- **Table versions as types already work.** `PgTable<'users', {...}>` and its runtime twin
  `tableFromType<T>()` (`packages/drizzle-orm-pg-core/src/table.ts`), walker in
  `packages/drizzle-orm/src/fromType.ts`.
- **`alterTable()` and `AlterTable` follow the strategy of every other builder.** The function records the call
  (over `createRtTable`, `packages/drizzle-orm/src/table.ts`) and its return type IS `AlterTable<...>`, so the
  builder result and the hand-written type are one type, as `pgTable()` and `PgTable<...>` are today. `AlterTable`
  resolves to a normal `PgTable` (keep the `names` map and `extras` in step with dropped and added columns), so
  models, validation, `tableFromType` and `toDrizzle` work unchanged. Same pair for mysql and sqlite. Both forms
  need the usual equality tests (builder table deep-equals the type-road table and raw drizzle).
- **History needs an explicit ordered step list.** Reflection resolves `UsersV2` to the finished table, so its
  link to `Users` is gone. Each step is diffed against the previous version of the same table in the list.
  The list also orders changes across tables (a foreign key after both tables exist).
- **drizzle-kit's code interface does the SQL.** Tested by hand with drizzle-kit 0.31.11 over our builder tables:
  `toDrizzle(v)` into `generateDrizzleJson({users: ...}, prevId)`, then `generateMigration(prev, cur)` returns
  the SQL lines. Create, add column, type change and not-null came out right. mysql, sqlite and singlestore have
  matching `generate*DrizzleJson` / `generate*Migration` functions. drizzle-kit is not a dependency today.
- **Gaps our step list must cover**, found in that test:
  - Renames: a table that loses and gains a column in one step makes drizzle-kit prompt, and outside a terminal
    it throws `Interactive prompts require a TTY terminal`. Worked fix: the step declares the rename, the tool
    renames the column in the previous snapshot so drizzle-kit sees no change, and adds
    `ALTER TABLE ... RENAME COLUMN` itself. An undeclared drop plus add in one table must be refused.
  - A type change plus a new default in the same step loses `SET DEFAULT` (the snapshot carries it; looks like a
    drizzle-kit bug). Needs a fix-up pass or a test that pins it.
  - text to integer gets no `USING` cast, which postgres refuses. The step's `using` option supplies it.
  - Data changes (backfill before a new not-null column) need a custom SQL step.
- **Known limits of the type form.** Enum and custom columns are refused by the type walker (they need a runtime
  handle), so pg enums need a type spelling before they can be migrated this way.
- **Output stays drizzle-compatible.** A `mion` command (generate + a `--check` that fails when the latest table
  types differ from the last step) writes the SQL files in drizzle's layout, so drizzle's own `migrate()` can apply
  them. drizzle-kit's `meta/` snapshots and journal are not needed: snapshots are rebuilt from code on every run.
  Where it lives (Go `mion` command next to `drizzle-migrate`, or a JS script) is the implementer's call.
- **Costs to measure.** Each `AlterTable` adds type-check work: measure it in `packages/private-type-budget`.
  Old versions stay in code; a way to squash an old range into one starting step is worth planning.
- Postgres first, then mysql, then sqlite (most sqlite alters rebuild the table, which drizzle-kit handles).

## Done when

- `alterTable()` and `AlterTable` (all three dialects) give one plain table type from both forms, with type tests,
  equality tests and a measured type cost.
- A step list over table versions generates the same SQL as drizzle-kit for the cases it gets right, plus
  declared renames, `using` casts and custom SQL steps, with no terminal prompt anywhere.
- `--check` fails in CI when the latest table types and the last step disagree.
- The generated files apply with drizzle's own `migrate()` against a real postgres in the drizzle e2e lane.
- The simplify-docs pass ran on every touched page and the simplify-comments pass on every touched source file,
  each committed on its own.
